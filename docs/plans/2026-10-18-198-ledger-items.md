# Keep the ledger's items as ops in the vault

Each change to an item is one JSON line in `ledger/ops/<yyyy-mm>-<machine>.jsonl`, written once and merged by union,
so every ask, chase and close keeps its history; the index folds each item from its own lines. Its id is its add op's
ULID, and its A- number is held by that add. Two PRs: the op format, the writer and `vault check`, then the index.

## Goal

- Done: every field todo.py keeps on an item is kept as ops, each saying who made it (kind, title, who, stream,
  source, opened, due, state, until, closed, triage, description, notes, materials, outcome, the log with `by`).
- Out: meetings, points, streams and an item's `meeting` (#199); the `ledger` tool, `docket ledger batch` and history
  counts (#201); the import (#202); the pages (#203 on); a forget over ops (#212), for which a door is kept open.

## Design

### The op line

One op per change, one line in the file (wrapped here):

```json
{"schema_version": 1, "id": "01JAB3W8Q4X5M2Z7K9R0T6YVNC", "item": "01JAB3W8Q4X5M2Z7K9R0T6YVNC", "op": "add",
 "day": "2026-10-18", "at": "2026-10-18T09:14:02Z", "machine": "desk", "by": "claude", "via": "cli", "number": 302,
 "fields": {"kind": "reply", "title": "Send Ada the dates", "who": "Ada", "stream": "pilot", "source": "chat:C0X/1"}}
```

| Key | What |
|---|---|
| `id`, `item`, `after` | the op's ULID (Ids); the item's id, its add's `id`; the item's latest op the writer saw |
| `day`, `at` | the owner's day in `vault.yaml`'s zone, always; the UTC second, absent when only the day is known |
| `machine`, `batch` | the writer's, as the file name says; the first op id of its write, so a write undoes whole |
| `by`, `via`, `note` | `user` (todo.py's `me`), `claude` or `sync`; `cli`, `page`, `tool`, `import`; the why, any op |

A line that doesn't read is a problem and is skipped; `schema_version` 2 is a later Docket's. An unknown key, name in
`fields` or op kind is kept and changes nothing, so a later Docket can add one; kinds, verdicts and streams are checked
when written. The fold never reads the clock: every date comes from `day`, `opened` too unless the add sets it.

| Op | Carries | What it does |
|---|---|---|
| `add` | `number`; `fields`: kind, title, who, stream, source; opened, due, description, notes, outcome | a new item |
| `set` | `fields`, any of add's; `null` clears an optional one | the plain fields; notes and outcome whole |
| `log` | `note`, required | a log line, nothing else |
| `triage` | `verdict`: discuss, claude, me, chase, or `null` | an open or snoozed item open with it, or cleared |
| `snooze` | `until`, a day | snoozed; triage cleared |
| `done`, `drop` | `note`, required for drop | closed on its day; triage and until cleared |
| `reopen` | - | open again; closed, until and archived cleared |
| `material` | `ref` and `label`, or `remove: true` | a URL, a locator, or a path with `/` from the host repo's top (the vault's in a repo of its own) |
| `archive` | - | a closed item out of the day's lists |
| `undo`, `renumber` | `of`, an op of the same item; `number` | that op left out of the fold; a new number (Ids) |

- todo.py's `notes --append` and `done --outcome` are the writer's: notes whole, a `set` of the outcome first. An op
  that doesn't apply to the state it meets (a second `done`) changes nothing; the writer refuses one, as todo.py does.
- The log is every op in order, its `note` or a line rendered from it (`due: - -> 2026-10-21`); an imported op other
  than `log` shows none, since the import brings the old log as `log` ops.
- Undo: the fold reads undos from the latest back, each leaving out the op it names unless undone itself, then
  replays the rest. An undone undo is a redo, an undone add hides the item, a renumber can't be undone. The undo's
  write also undoes the ops of the same kind the undone one left nothing to do, so a second `done` doesn't take over.
- Archive is a flag, not a move: the item leaves Today, the Queue and the Ledger's default lists; search, `show` and
  history keep it. The sync writes it 14 days after a close, and skips an item whose archive was undone.

### Files and merging

- `ledger/ops/<yyyy-mm>-<machine>.jsonl`, the month of the op's `day` (DR-0141, as the curate log's DR-0460). A write
  has one day and replaces one month file through a temp file and a rename, so it lands whole or not at all; one that
  spans months is refused, and #202 imports a month at a time, skipping ops whose ids the ledger holds. It commits
  `Ledger: done A-0281, triage A-0302 on desk`, never a title, signed by `console.who()`.
- Two clones write their own files; `*.jsonl merge=union` keeps both sides of a merge or a rebase. The fold sorts by
  id, so any order gives one ledger: a line twice is one op, one id on two texts keeps both, by text. A committed line
  changes only by a forget's apply (#212), its id and keys kept, its text a marker, `state/forgotten.jsonl` saying so.

### Ids and numbers

- Order is a hybrid logical clock in ULID form: a fresh ULID or, when that isn't above the highest op id the ledger
  holds, its next millisecond with fresh random bits; within a batch, the op before plus one. An edit made after a pull
  sorts after what it pulled, and two clones on one host, one machine name, pulling from a clock ahead, still differ.
- An item's id is its add's ULID, for good. Its number is in the add, one past the highest any item has held, as
  todo.py numbers from `meta.next_id`, so imported numbers carry on (#202).
- A clash, two clones apart both giving out A-0301: the claim, add or renumber, that sorts first keeps it, and the
  next write anywhere renumbers the other. `A-0301` then finds its holder and names the one before, and a write by it
  is refused until the item is named by id. No clone gives out a number it has seen held, and no number moves later,
  as the design's numbers handed out by the fold would.

### The fold into the index (PR 2)

| Table | What |
|---|---|
| `items` | each item's state: every field, `state`, `archived`, its number, the add's `by`, its last op |
| `item_log` | every op: item, id, after, day, at, by, via, kind, its keys as JSON, its log line, the undo of it |
| `item_numbers` | each number and the items that held it, now or before |
| `ledger_files` | each op file's size, modification time and sha256, as `run_files` and `doc_files` |

- A file that only grew, its old bytes the same, is read from where it stopped; the items its new lines name fold
  again from `item_log`, with every holder of a number an add or renumber claims. Anything else folds the whole
  ledger, 50,000 ops in about a third of a second. Two rebuilds give one database; schema 11. The writer updates the
  index from `ledger_files` before it mints an id or a number. `docket ledger show <A-0302|id>` prints an item.

### Text and the check

- An op's text passes the gate's rules for derived text (DR-0195): redaction writes a match as its marker; a
  never-store keyword, or `who` naming someone on the people list, refuses the write, never naming the value. A
  `source` or a material `ref` that a redaction rule matches (`token=`, `user:pw@`) refuses it: no marker in a locator.
- `docket vault check` names: a file in `ledger/ops/` misnamed, a link or not UTF-8; a line that doesn't read or is in
  the wrong file; one id on two texts; an op with no add or before it; an undo of another item's op or a renumber; a
  number two items hold; a committed line changed or gone that the forgotten list doesn't explain; wrong attributes.

## Risks

| Risk | Answer |
|---|---|
| a clock runs ahead, and every later id follows it | accepted: the order stays right, `at` keeps the time |
| two machines edit one item's notes apart | the later op wins, `after` shows they were apart, both stay in history |
