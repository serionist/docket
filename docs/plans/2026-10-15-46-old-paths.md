# Resolve old note paths through the index, and parse only what read shows

## Goal

`docket doc read notes/calls/2026-09-10-supplier-call.md@12:08` finds its legacy note in one indexed lookup, and the
read parses only the docs it shows, so an action ledger full of old-path locators reads fast. Today the old-path match
is the cheap part: the same read parses every doc in the vault up to three times and loads the source's whole raw log
up to three times.

On an invented vault of 203 legacy notes (about 4 KB each, each covering one of 203 recordings of 240 segments, 6.5 MB
of raw in one source), best of five on the maintainer's desktop:

| Read, in process | Today | After |
|---|---|---|
| `read(<old path>)` | 160-185 ms: two parses of every doc, 90 ms each | about 20 ms |
| `read(<old path>@12:08)` | 320-430 ms: three parses and one raw load | about 100 ms, 90 of it the raw load |
| `read(<source>:<old path>@12:08, view="both")` | 650 ms: three parses and three raw loads | about 100 ms, the same one raw load (from the parts) |
| `docket doc read <old path>@12:08`, the whole process | 745 ms | about 470 ms, 360 of it starting Python |
| the same four with 600 recording notes added (803 docs) | 720, 1,240, 1,490 and 1,330 ms | about 100, 220, 220 and 570 ms |

The old-path match itself takes under 0.1 ms; the index's lookup about 1 ms. "After" is timed from a sketch of the
queries on the same vault, not from built code; the command's line adds the 350-370 ms a `docket doc read <doc id>`
spends outside its read. With the `old_paths` table alone, read would still parse every doc
for `superseded_by` and the citing lines: one parse of three saved.

- In scope: the `old_paths` table, filled by rebuild and update; `read` asking the index for an old path's note, the
  docs that supersede the one it shows, and the docs that cover the record it reads, when the index is current; one
  parse and one raw load per call when it isn't; the tests that run every read test through both routes.
- Out of scope: reading a record's raw by its place in the index (the raw load above, about 15 ms per MB of a source's
  raw here), and with it the rid check of a `<source>:<old path>` locator without a time, which loads that source's
  raw: both are #76; `verify` by old path (Decided below); `docket import notes` itself, which reads every legacy note
  once per run.

## Design

| Module | Change |
|---|---|
| `index/schema.py` | the `old_paths` table; `SCHEMA_VERSION` 3 |
| `index/build.py` | `Indexer.index_doc_file` writes a legacy note's rows, `drop_doc_file` drops them; the doc-hash comparison `status()` makes becomes a helper the lookup shares |
| `index/lookup.py` (new) | the index opened for a read when it is current for `processed/`, and the three questions read asks it |
| `vault/legacy.py` | `keys(locator)`: the folded paths and the file name an old path's candidates have, beside `find()` |
| `recall.py` | `read` asks a per-call doc source: the index when current, else one parse of every doc; one `RawLookup` per call |

### The table

```sql
CREATE TABLE old_paths (
  doc TEXT NOT NULL, path TEXT NOT NULL, folded TEXT NOT NULL, name TEXT NOT NULL, PRIMARY KEY (doc, path)
) WITHOUT ROWID;
CREATE INDEX old_paths_folded ON old_paths (folded);
CREATE INDEX old_paths_name ON old_paths (name);
```

- One row per entry `legacy.old_paths([doc])` gives for a doc the index reads: `path` as the doc keeps it, `folded` its
  `casefold()`, `name` the casefold of its last part. Folding happens in Python, so SQLite compares with `=` and `IN`
  only and never applies case rules of its own.
- Rows come and go with their doc's file, as `doc_covers` does: an update that re-reads or drops a file re-reads or
  drops its rows, so update and rebuild end with the same table (DR-0115).
- A table of its own, not the design's `crosswalk`: that links record ids to record ids, while this maps a path to a
  doc and needs its lookup columns.
- Schema 3 makes every existing index stale: the next search, the service's start or `docket index update` rebuilds it
  once, and reads meanwhile take the parse route. If #60 also bumps the schema, whichever merges second takes 4.

### When read asks the index

`lookup.current(vault)` opens the index as search does and, in one read transaction, compares every `*.md` under
`processed/` with `doc_files` by sha256, the comparison `status()` and `update` already make. Equal, it returns the
connection; otherwise None, and read parses every doc once for the call, as today but once.

| The index is | Read |
|---|---|
| current | parses only the docs it shows or cites |
| missing, another schema, other languages, unreadable, or without FTS5 | parses every doc once |
| any doc added, changed or removed since its last update | parses every doc once |

- Read never updates, rebuilds or waits for the index, so it never writes and never sits behind a rebuild. Search
  (`docket search` updates first), the service (at start, after each of its writes, before each search) and `docket
  index update` keep it current. After `docket import notes` from the command line, reads take the parse route until
  one of them runs.
- Only `processed/` decides: the old paths, a doc's `supersedes` and its `covers` come from its file alone, so new raw
  runs or entity files don't send a read to the parse route.
- The read transaction keeps an update from committing between the hash comparison and the questions; a doc written on
  disk in between is the race a parse has today too.

### The index narrows, today's code decides

Each question takes candidates from the index and runs the code read runs today on them, so a current index can only
give the same answer as a parse:

| Read asks | From the index | Then |
|---|---|---|
| which legacy note an old path names | rows whose `folded` is the locator's folded path or one of its suffixes after a `/` or `:`, or whose `name` is its file name when the file-name step applies | `legacy.find()` on those rows, as on all of them |
| which docs supersede the one it shows | `docs` rows whose `supersedes` isn't empty | the same filter, in the order a parse lists them |
| which docs cover the record it reads, and which are superseded | `doc_covers` for the rid; `docs.supersedes` | those docs parsed, sorted by path as `DocStore.all()` sorts, through the same citing-lines and legacy-note code |

- Why the old-path candidates are enough: an exact or case-folded match has the locator's folded path; a suffix match
  is a suffix after a `/` or `:` (the one-part candidates the problem names among them); a file-name match has the
  file name as its last part. `keys()` sits beside `find()` in `legacy.py`, so a change to DR-0131's steps changes
  both in one place, and a test holds them together on every locator the tests know.
- Two notes claiming one old path: both rows are there (the key is the doc and the path), so `find()` names both, as
  today: "could be any of A, B; give more of its path".
- Windows: `normalize()` turns `\` into `/`, composes to NFC and drops `./` before any query, and the stored paths are
  NFC with `/` (DR-0130). A drive letter or a leading `/` only ever matches as a suffix. Nothing touches the file
  system beyond the vault's own `processed/`.

### One parse and one raw load per call

Inside one read, the parse route parses every doc once and shares it among the old-path lookup, `superseded_by`, the
citing lines and the legacy notes covering a record. One `RawLookup` serves the rid check, the doc's covered records,
the recording a time is placed in and the spans, so `<source>:<old path>@12:08` loads its source's raw once, not three
times.

### The service and the web app

No change: the MCP `read` tool, `GET /api/read` and the Search page's panel all call `recall.read` through
`service/calls.py`. The panel's record view waits for an index update before it reads, so it takes the index route;
an old-path panel and the tools don't wait, and take it when the index is current.

### Decided

Taken under the autonomy grant, each `proposed` for the maintainer's review.

| Decided | Not taken | Entry |
|---|---|---|
| an `old_paths` table of its own: doc, path, folded, name, folded in Python | the design's `crosswalk`: it links record ids; every old path into Python on each read: linear in the notes | DR-0320 |
| read asks the index only when every doc file matches `doc_files` by hash, in one read transaction | trust the index and check the one doc it names: a note imported since could match better, and the answer would differ from a parse; size and modification time: an edit that keeps both reads a stale answer, and the hash is what update compares | DR-0321 |
| read never updates, rebuilds or waits for the index | update first, as `docket search` does: a read would write, and wait minutes behind a rebuild | DR-0321 |
| the index narrows and today's code decides, for old paths, `superseded_by`, the citing lines and the legacy notes covering a record | DR-0131's steps as SQL: a second copy of the rules; the table alone: one parse of three saved | DR-0322 |
| one parse and one `RawLookup` per read call | as now: up to three parses and three raw loads | - |
| `verify` stays as it is: a doc's id or its path in `processed/` | `verify` by old path, as the issue's Resolve row says: `verify` takes no old path today, a legacy note has no anchors so it would return no lines, and it would extend DR-0131's one-way door to a second tool | - |
| `docket import notes` leaves the index alone | an update after its commit: the import would also build or rebuild an index it never needs | - |

## Doors and data

None of AGENTS.md's one-way doors: the locator grammar and its steps (DR-0131), the MCP tools' parameters and results
(DR-0150) and the vault's files stay as they are, and nothing in the vault is written. The index is a per-machine cache
(DR-0115): schema 3 rebuilds it once, from the vault, on each machine.

| Where | After the upgrade |
|---|---|
| `docket search`, the service's start | its update finds schema 2 and rebuilds |
| `docket doc read`, the MCP `read` tool | the parse route until that rebuild, once per call |
| `docket index status` | says it needs a rebuild |

## Steps

1. The table: `old_paths` in `schema.py`, schema 3; `Indexer` writes and drops its rows with the doc; the hash
   comparison as a helper `status()` uses. Tests: `test_index_build.py` (two legacy notes, one with two old paths and
   one sharing a path with the other, give their rows; two rebuilds give the same table), `test_index_update.py` (an
   import, a hand edit of a note's `old_paths` and a deleted legacy doc, each followed by an update, equal a rebuild),
   `test_index_schema.py` (a schema 2 index is stale, and `update` rebuilds it).
2. `legacy.keys()` and `index/lookup.py`. Tests: `test_legacy.py` (narrowed and whole give the same doc or the same
   error for every locator), `test_index_lookup.py` (current, missing, stale, unreadable, a doc changed, a doc added,
   a doc removed).
3. `recall.read` through the per-call doc source and one `RawLookup`. Tests: `test_recall.py` and
   `test_recall_legacy.py` through both routes, and the rows under Tests.
4. The docs below, then `finish-work`: `uv run gate full`, a draft PR, `review-code` until it is clean.

## Tests

On temp vaults made with `Vault.init`, temp config and state dirs, the failing keyring and `DOCKET_VAULT` unset, as
`conftest.py` sets them; invented names only (Ben Sample, Cleo Test, Ada Example).

- A `route` fixture in `test_recall.py` and `test_recall_legacy.py`: `parse` reads with no index; `index` brings the
  index up to date before each read and makes `DocStore.all()` fail, so a read that parses every doc fails the test.
  Every read test in both modules runs both ways and asserts the same result: this is the issue's same-result test,
  and it covers `superseded_by`, the citing lines and a record's legacy notes as well as every old-path locator #11
  tests. The templates gain their index, built once per session.
- `test_legacy.py`: `test_the_index_narrows_to_the_same_answer`, over every locator in `test_each_lookup_step` and
  `test_nothing_or_several_is_said_never_guessed`, the root `README.md` cases, the flat notes repo and the two suffixes
  of one length, plus `NOTES\MAIL\2026-09-11-OFFER.md`, an NFD name and `Straße.md` against `STRASSE.md`: `find()` on
  the rows an in-memory `old_paths` table gives equals `find()` on all of them, doc or error text.
- `test_recall_legacy.py`, new: two legacy notes claiming one old path name both on either route; a legacy note edited
  on disk after the update to drop its old path takes the parse route and doesn't resolve; with a stale index,
  `read(f"calls:{CALL}@12:08", view="both")` calls `DocStore.all()` once and loads the `calls` raw once (counted).
- `test_index_lookup.py`: `current()` is None with no index, a schema 2 index, a file that isn't SQLite, a doc
  changed, added or removed since the update, and the connection otherwise; it never writes the index file (its bytes
  and modification time stay).
- Changed: `LOGICAL_TABLES` in `docket_testkit.py` gains `old_paths`, so every update-equals-rebuild test compares it.
- Coverage stays at the `docket` floor of 100%.

## Risks

| Risk | Status |
|---|---|
| The hash comparison grows with the docs: about 0.1 ms each here, so 2,000 docs cost about 200 ms a read | accepted: four to five times under a parse; size and modification time, shared with update, are the next step if it shows |
| A stale index sends every read to the parse route until something updates it, as after a command-line import | accepted: one parse a call, not three, and the service keeps the index current |
| The raw load stays the biggest part of a timed read: about 15 ms per MB of the source's raw here, more for a year of hour-long recordings | accepted: reading a record by its place in `records` and `record_versions` is #76; the plan's numbers show what it would take off |
| `<source>:<old path>` without a time still loads that source's raw for the rid check | accepted: #76 takes it off |
| A bug in the narrowing gives a current index another answer than a parse | resolved: both routes run every read test, and `keys()` is held to `find()` on every locator |
| Superseded docs and citing lines come back in another order | resolved: the index route sorts by path as `DocStore.all()` does, and the route tests compare whole results |
| A read holding its transaction while it hashes delays an update's commit by that long | accepted: tens of ms against the update's 5 s busy timeout |
| On Windows a rebuild can't replace the index file while a read holds it open | accepted: the rebuild already retries for 5 s, and a read holds it for ms |
