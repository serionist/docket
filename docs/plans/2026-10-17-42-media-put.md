# Store media through the gate, encrypted per file

`media_put(rid, path or url)` stores a record's audio or file. Docket fetches it within DR-0108's limits, encrypts it
with age to a key made for that file alone, and stages it beside its record. It is dropped with the record, and
committed to `media/` in LFS when the record is in raw. Keys never enter the vault. Each clone keeps its keys sealed
in its private folder, a second machine gets them from an export the owner moves by hand, and one reader decrypts in
memory, saying why when it can't.

## Goal

| The issue's part | This plan |
|---|---|
| Tool | MCP `media_put(rid, path, url)` and `docket media put <rid> <path-or-url>`: one media file per rid, for a record staged or in raw |
| Fetch | a path under the source's `media_folders` or Docket's drop folder, after links; a URL over https to a host in the source's `media_hosts`, every resolved address global, the connection made to a checked address, at most 3 redirects each checked again, 512 MiB at most |
| Settings | `media_hosts` and the new `media_folders` say where a source's media may come from, and nothing else. Adding one by command asks at the console, by hand waits for its commit, removing one applies at once |
| Gate | `staging/_media/<source>/<rid hash>.<ext>.age`, never committed; dropped when no version of its record is left in staging or raw; committed when its record is in raw |
| Holds | refused under a held id, and under a release with cuts until #157; a release with no cuts stores it |
| Encryption | pyrage (age, X25519): a fresh identity per file, the file encrypted to it alone; deleting the key forgets the file |
| Keys | key files sealed in the clone's private folder; their seal in the OS keychain, or in a file in Docket's per-user folder when the owner chooses it; `docket media keys export` and `import`, at the owner's console |
| Read | `docket.media.read(vault, rid)` decrypts in memory for the service and the worker, or says why not: not stored, held, not downloaded, no key. The Recording page shows each reason |
| Tests | every refusal, each with its own test (Tests, below) |

- In scope: the fetcher, the staged media and its sweep, promotion, the key store, export and import, the reader, the
  CLI's `docket media` group, the MCP tool, `media_folders`, the settings in force for both lists, the Recording page's
  reasons, `docket vault convert` carrying the key store over, the Plaud reference skill's media step, the docs.
- Out of scope:
  - cutting a released recording's audio: #157. Until then such media is refused.
  - the player, range requests and the media route: #159's second part, on this reader.
  - decoding audio, Whisper: #157 and #158. `media_put` stores bytes and sniffs only a type.
  - `docket forget` and retention: their own issue. This plan gives them `keys.delete`.
  - automatic backup to a folder: see Open for the maintainer.
  - a proxy, and a TLS-intercepting network: no fetch through either (Risks).
  - attachments inside a mail record: an attachment whose bytes matter is a record of its own under its message, as a
    transcript is under its recording; its rid gets the media.

## Design

### One media file per rid

| Where | Path | In git |
|---|---|---|
| waiting | `staging/_media/<source>/<rid hash>.<ext>.age` | never: `staging/` is ignored, and nothing commits from it |
| stored | `media/<source>/<yyyy>/<mm>/<rid hash>.<ext>.age` | LFS, by the vault's own `.gitattributes` |

- `<rid hash>` is staging's `rid_hash`: 32 hex of sha256 of the rid. The design's `<id>` can't be the native id in a
  file name: Plaud's has a slash, a mail's an `@` and brackets. `<yyyy>/<mm>` is the record's `ts` in UTC.
- `<ext>` comes from the bytes, never the URL or the file name: mp3, m4a, ogg, opus, wav, flac, webm, aac, pdf, png,
  jpg, else `bin`. The type is all `media_put` reads of the content.
- `_media` can't be a source's name (DR-0125), and staging's scan reads `*/*.json`, so an older Docket reading this
  staging folder ignores the media files.
- A put for a rid with staged media replaces it, deleting the old file and its key. A put for a rid with media in
  `media/` is refused: replacing stored media is forget's work, then a new put.

### The gate

Media has no state of its own. It follows its rid:

| The rid | Its media |
|---|---|
| a version staged, pending or ready | waits |
| in raw, at a promotion | moves to `media/` and is committed after the run's commit, in the same lock: `Media: <source>, N file(s) from <machine>` |
| in raw, at a promotion, with git-lfs missing or its filter off in the repo | waits, with the problem named. Records still promote |
| no version left in staging and none in raw (classified private, swept as private or never-store, left out by a release) | deleted at the next sweep, with its key, and counted, never named |
| covered by a hold that came after the put | waits and is never promoted, as a held record does |
| covered by a release with cuts that came after the put | deleted at the sweep, with its key: uncut audio never reaches git |

The sweep already runs at every gate call. It also lists `staging/_media/`, which is cheap. `docket staging list` and
the Staging page add how many media files wait.

### media_put's checks, in order

1. The rid parses, and a version of it is staged or in raw. Otherwise: "no record X staged or in raw; media follows
   its record, so stage the record first".
2. Its source is in the settings in force, on, and not private. The record's latest version matches no never-store
   value now: the audio can't be screened, so its record's text decides.
3. Holds and releases, read as the gate reads them and failing closed: a hold refuses; a release with cuts refuses
   ("its audio waits until Docket can cut it"); a release with no cuts goes on. A hold beats a release (DR-0201).
4. No media for the rid in `media/`.
5. The fetch, below, into a temp file in Docket's private folder.
6. Seal and stage, below. The plain temp file is deleted on every path.

The fetch runs outside the vault lock. The lock is taken only to check and write staging, on the service's writer,
so a slow download never blocks the gate.

### The fetch

| From | Allowed when |
|---|---|
| a path | it resolves, after every link, to a regular file under one of the source's `media_folders`, or under Docket's drop folder (`<state dir>/drop/`). Not a OneDrive placeholder. A file put from the drop folder is deleted once stored; one from a media folder is left as it is |
| a URL | `https`, a host exactly in the source's `media_hosts` |

- DNS, then the check: every address the host resolves to is global (`ipaddress`'s `is_global`, with an IPv4-mapped
  IPv6 address checked as IPv4). One private, loopback, link-local (169.254.169.254 too), CGNAT, multicast or reserved
  address refuses the whole host, even if others are fine.
- The connection goes to a checked address, with the host as SNI and for certificate checks (an `http.client`
  connection whose `connect` dials that address). There is no second lookup to rebind, and no proxy: environment
  proxies are ignored.
- Redirects: at most 3, each answered by the same checks (https, a listed host, global addresses).
- Size: 512 MiB. A `Content-Length` over the cap refuses before the body is read; a body that grows past it is cut
  off and its temp file deleted.
- Time: 15 s to connect, 60 s without a byte, 15 minutes in all.
- A URL is never logged, stored or put in an error: a signed URL is a credential. Errors name the host only.

`media_folders` is a new optional key on a source in `vault.yaml`, a list written like a folder source's `folder`:
relative to the consuming repo or under `~/`, never absolute (DR-0481's rule). `schema_version` stays 1, as for
DR-0124's keys. A folder on another drive goes through the drop folder.

### The settings in force

`inforce._source` treats both lists as it treats `tools`: what HEAD and the file both list. An entry added by hand
waits for its commit, and an entry removed applies at once. `loosens()` then flags an addition, so:

| Change | How |
|---|---|
| add a host or a folder | `docket media host add <source> <host>`, `docket media folder add <source> <folder>`: `settings.rewrite` asks at the owner's console (DR-0517); by hand, it applies once committed (DR-0521) |
| remove one | `docket media host remove`, `docket media folder remove`: written at once, nothing asked |
| the Settings page | shows each source's hosts and folders, with the commands; it makes none of these changes (DR-0506 is unchanged) |

### Encryption

- pyrage, MIT, the Rust age implementation, exact-pinned like `mcp`, with the same platform marker as `sqlite-vec`
  (no wheel for Windows on Arm or musl). On a machine without it, `media_put` and the reader say so; everything else
  works.
- Per file: `x25519.Identity.generate()`, then `encrypt_file` to that identity's recipient alone. There is no second
  recipient, no machine key and no master key, so deleting the identity forgets the file (design §5.5).
- A file's key id is the sha256 of its age header: the bytes up to and including the `---` MAC line. It is unique per
  file, stable when the file moves from staging to `media/`, and readable from the file itself. No vault id, no
  manifest.

### The key store

```
<private>/media/store.json            {"schema_version": 1, "id": "<random>", "store": "keyring" | "file"}
<private>/media/keys/<key id>.age     one key: {"identity", "path", "at"}, sealed with age to the store's recipient
```

- `<private>` is the clone's Docket folder in its git dir (`.git/docket/`, or the host's for a folder vault). It is
  never in the tree and never in git, and a copy of the repo folder carries only sealed files.
- The seal is a store identity:

  | `store` | Where the store identity lives |
  |---|---|
  | `keyring` | the OS keychain, as `docket` / `media-store:<id>`: one entry per clone, not one per file |
  | `file` | `<state dir>/media-stores/<id>`, readable by the user only, outside any repo and any synced folder Docket knows |

- Chosen once, at the first put on a clone: the keychain when a write and a read-back work there, as the service token
  is chosen. When they fail (CI, a Linux box without Secret Service), the put is refused with
  `docket media keys init --store file`. A file store is weaker than a keychain, so the owner chooses it; it is never
  a silent fallback. CI's tests run with the file store under their temp folders.
- Order at a put: the encrypted file to a temp name, then its key file, then the rename into staging. A crash leaves
  a temp file, which the next sweep clears, or a key for no file, which decrypts nothing.
- `keys.delete(key id)`: the gate's drops now, and forget later.
- `docket vault convert` moves `<private>/media/` with the rest of the private folder, or a converted vault would lose
  every key.

### A second machine, and the backup

Nothing about keys travels in git: not a key, not a wrapped key, not a recipient. A folder vault's history is never
rewritten, so anything put there stays for good.

- `docket media keys export <file>`: at the owner's console only (`console.problem`: refused in Claude Code's shell, a
  pipe or a redirect). Docket draws a passphrase (24 letters in groups of 4), shows it once, and writes every key of
  the clone into one file sealed with age's scrypt passphrase mode: `{"schema_version": 1, "keys": [{"id", "identity",
  "path", "at"}]}`.
- `docket media keys import <file>`: at the console, asks for the passphrase, and adds the keys it lacks. A key whose id
  it has is skipped and counted.
- The bundle is the backup. Every export holds every key, so the newest one is enough. `docket media status`,
  `docket vault status` and the session-start dashboard say how many keys no export has held yet. They count against
  `<private>/media/exported.json`, which lists key ids and no keys.
- Forgetting a file later deletes its key here. An export made before still holds it, and forget will say so. This is
  the cost of any backup.

### One reader

`docket.media.read(vault, rid) -> Media`, used by the service and imported by the models' worker, which opens the
vault itself as it does today. Nothing plain is written to disk: it decrypts into memory, bounded by the cap.

| `Media.state` | When | The Recording page says |
|---|---|---|
| `ok` | the bytes and their type | (the player comes with #159) |
| `not-fetched` | no media for the rid, staged or stored | #164's "No audio stored yet" |
| `held` | a hold covers the rid, or a release with cuts does | "The audio waits with the recording's hold" / "until Docket can cut it" |
| `not-downloaded` | an LFS pointer is in place of the file | "The audio is stored but not downloaded here: git lfs pull" |
| `no-key` | the file is here, its key isn't | "The audio is stored, but this machine has no key for it: docket media keys import, from an export made where it has one" |

`no-key` and `held` go into #164's `NO_AUDIO`, with `not-downloaded`, each with its sentence and test. The page reads
the state with `Media.state_of(vault, rid)`, which checks the header and the key file without decrypting.

### The source's run

Once a source lists a media host or folder, `run_open`'s steps gain one step after ingest: for each recording with
audio, `media_put(rid, url)` with the URL the source's tool gave. The Plaud reference `SKILL.md` names the call that
gives the audio. Which host Plaud's audio comes from is learned on the first real run (Open).

### Alternatives

| Not chosen | Why |
|---|---|
| a keychain entry per file | thousands of entries, no listing to export from, slow on macOS |
| keys derived from one master secret | deleting a key would forget nothing: it can be derived again |
| each file also encrypted to every machine's key, or wrapped keys committed | a key in git, even wrapped, stays in a folder vault's history for good |
| machines syncing keys over the network | both online at once, and a new listening surface |
| a key store in the user's synced folder, automatically | a good next step, but where it goes is the owner's call (Open) |
| our own age on `cryptography` | rolling our own crypto, for a format pyrage covers |
| `httpx` for the fetch | pinning a checked address with the right SNI means fighting its transport; `http.client` does it in a few lines |
| media staged without encryption, encrypted at promotion | plain audio would sit on disk for as long as the record waits |

## Doors and data

| Door (AGENTS.md) | Change |
|---|---|
| the MCP tools' names and parameters | adds `media_put(rid, path, url)`. One-way: Claude's calls and skills depend on it |
| the vault's format | `media/<source>/<yyyy>/<mm>/<rid hash>.<ext>.age`, the design's layout with `<id>` defined |
| `vault.yaml` | `media_folders` on a source: optional, `schema_version` stays 1 |
| staging's files | `staging/_media/`, beside the sources' folders |
| a file users keep | the export bundle, schema_version 1; a later Docket reads every earlier one |

- Existing vaults: nothing moves. `media/` is empty everywhere today, and `media_hosts` is in vault.yamls but nothing
  reads it.
- The key store isn't a vault door: it lives on each machine. A lost store with no export loses that clone's media for
  good, which is the point of the design. Its format is versioned all the same.
- The PR title names the doors: "Add media_put and the media layout (one-way doors)".

## Steps

1. pyrage pinned, with its marker; `docket.media.crypto`: seal, open, header id. Test: round trip, a header id stable
   across a move, a wrong identity refused.
2. `media_folders` in `SourceConfig`; `inforce._source` for both lists. Test: an added host waits until committed, a
   removed one applies at once, `loosens()` flags an addition.
3. `docket.media.fetch`: the path rules, then https with the address check, the pinned connection, redirects, cap and
   timeouts. Tests against a local TLS server with a generated certificate and an injected resolver (Tests, below).
4. The key store: `store.json`, `init --store`, the keychain read-back, key files, `delete`. Test: keychain failing
   without a file store refuses, file store under the test's state dir.
5. `docket.media.put`: the checks in order, the seal-and-stage order, replacing staged media. Tests: each refusal.
6. The gate: the sweep's media rules, media promotion after the run commit, git-lfs missing. Tests: each drop takes its
   media, media never in a commit from staging, promotion commits it to `media/` under LFS.
7. The reader and `state_of`; the Recording page's reasons. Tests: each state, and the page's sentence for each.
8. `docket media` CLI (put, host, folder, keys init, export, import, status) and the MCP tool. Tests: the console's
   refusals and the passphrase round trip, with the console fixture the release tests use.
9. `run_open`'s step, the Plaud reference skill, `docket vault convert` moving the store. Tests: the step appears only
   with a host or folder; convert keeps the keys.
10. Docs: the decisions, the design's media lines, the README's media section, the glossary, the CHANGELOG.

## Tests

| Refusal or rule | Test |
|---|---|
| no record staged or in raw | put names it, nothing written |
| source private, off, or not in force | each refused |
| the record matches a never-store value now | refused |
| a held id, on the rid or its container | refused; a hold arriving after the put keeps it unpromoted |
| a release with cuts | refused; one arriving after the put deletes the staged media and its key |
| a release with no cuts | stored |
| media already in `media/` | refused |
| a path outside the media folders, a link out of one, a placeholder | each refused |
| `http://`, a host not listed, a host with one private address among public ones | each refused before connecting |
| loopback, link-local, metadata 169.254.169.254, CGNAT, IPv4-mapped IPv6 | each refused |
| a redirect to a private address, to http, to an unlisted host; a 4th redirect | each refused |
| a `Content-Length` over the cap; a chunked body over it | refused before reading; cut off, temp gone |
| a URL with a token in its query | never in the log, the error or staging |
| classified private, swept private or never-store, left out by a release | the media and its key go with the record |
| promotion | the media commits to `media/` after its record; no commit ever holds `staging/` |
| git-lfs missing | media waits with its problem, records promote |
| keychain failing, no file store | refused, naming `docket media keys init --store file` |
| export or import in Claude Code's shell, or from a pipe | refused, nothing written |
| export, then import on a second clone | the second clone reads the media |
| no key; an LFS pointer; held | `read` says `no-key`, `not-downloaded`, `held`; the page says each |
| a crash between key and rename | the next sweep clears the temp; the key decrypts nothing |

Against: invented vaults from `docket_testkit` (a Plaud-shaped record staged and in raw), generated audio-like bytes
with an mp3 or Ogg header, a local HTTPS server on port 0 with a certificate made by `cryptography` in the test, and
the resolver injected so a test host maps to a chosen address. No test reaches the network or the real keychain.

## Risks

| Risk | Status |
|---|---|
| A clone lost with no export loses its media for good | accepted, by design; status, vault status and the dashboard count keys no export holds |
| An export is as strong as its passphrase and where it is kept | accepted; the passphrase is drawn, 24 letters, never typed by Claude |
| The file store keeps the seal on the same disk | accepted; the owner chooses it, and it lives outside any repo |
| GitHub's LFS quota (1 GiB free) fills with audio | accepted; the README says so; `lfs.fetchexclude` keeps a clone light |
| No proxy, no TLS interception: some networks can't fetch | accepted for #42; a path through the drop folder works there |
| pyrage has no wheel for Windows on Arm or musl | accepted; media is off there, said plainly |
| A file's type sniffed wrong | resolved: only the extension and the served type depend on it |
| Plaud's audio host is unknown until a real run | open: needs the maintainer |
| A TOCTOU between resolving a path and reading it | accepted: the threat is the user's own account, and the file is read once, opened after the check |
