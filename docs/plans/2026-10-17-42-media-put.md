# Store media through the gate, encrypted per file

`media_put(rid, path or url)` stores a record's audio or file. Docket fetches it within DR-0108's limits and encrypts
it while it reads, with age, to a key made for that file alone, so no plain copy is ever written. It stages it beside
its record, screens it again at every gate call, and commits it to `media/` in LFS once the record is in raw. Keys never
enter the vault: each clone keeps its own sealed in its private folder, a second machine gets them from an export the
owner moves by hand, and one reader decrypts in memory, saying why when it can't.

Two PRs: the first stores and reads media on one machine; the second carries keys to another.

## Goal

| The issue's part | This plan | PR |

| Settings | `media_hosts` and the new `media_folders` say where a source's media may come from, and nothing else. Adding one by command asks at the console, by hand waits for its commit, removing one applies at once | 1 |

| Holds | refused under a held id, and under a release with cuts until #157; a release with no cuts stores it; a hold or a release with cuts arriving later deletes it | 1 |

## Design

### One media file per rid

| Where | Path | In git |
|---|---|---|
| waiting | `staging/_media/<source>/<rid hash>.<ext>.age`, and `<rid hash>.json` beside it | never: `staging/` is ignored, and nothing commits from it |
| stored | `media/<source>/<yyyy>/<mm>/<rid hash>.<ext>.age` | LFS, by the vault's own `.gitattributes` |

- `<rid hash>` is staging's `rid_hash`: 32 hex of sha256 of the rid. The design's `<id>` can't be the native id in a
  file name: Plaud's has a slash, a mail's an `@` and brackets.
- `<yyyy>/<mm>` is fixed once, at the promotion that stores the file: the `ts`, in UTC, of the record's version that is
  in raw then. A later version with another `ts` never moves it.
- Stored media is found by `media/<source>/*/*/<rid hash>.*.age`: any month, any extension. Nothing computes a month
  to find a file, so a `ts` that changed between versions can't hide one. Two matches are a problem the reader names,
  never a guess.
- `<ext>` comes from the first bytes, never the URL or the file name: mp3, m4a, ogg, opus, wav, flac, webm, aac, pdf,
  png, jpg, else `bin`. The type is all `media_put` reads of the content.
- The sidecar holds `schema_version`, the rid, the key id, the type, the size and when it was put: no content. The
  sweep needs the rid, which the hash can't give back.
- `_media` can't be a source's name (DR-0125), and staging's scan reads `*/*.json` two levels down, so neither an
  older Docket nor today's record scan reads the media folder.
- A put for a rid with staged media replaces it, deleting the old file, its sidecar and its key. A put for a rid with
  media in `media/` is refused: replacing stored media is forget's work, then a new put.

### The checks

The same four checks run at the put, before the fetch and again after it, at every sweep, and at promotion, under the
settings in force then. Media that fails one at the sweep or at promotion is deleted with its sidecar and its key, and
counted, never named.

A media file's records are its rid's record and every record whose rid sits under `<rid>/`: rid nesting only. For
Plaud's audio, put on `plaud:<id>`, that is the recording, its transcript and its notes. What a speaker said is in the
transcript, and a cut by hand is made on it, so the checks read the whole family, never the rid's record alone.
Thread and container stay out: a Slack reply names its thread starter as its thread, and a reply's drop must not
withhold the starter's file. Holds keep their own coverage (DR-0121).

A mail mapper that makes attachment records should copy the message's author, recipients and container onto each, so
a never-store sender or recipient reaches the attachment's record, and with it the attachment's media.

| Check | Fails when |
|---|---|
| 1. its record | no version of the rid is staged or in raw |
| 2. its source, its text and the owner's decisions | the source isn't in force, is off or is private; any version of one of its records, staged or in raw, matches a never-store value; staging's `_withheld.jsonl` holds the rid's hash (below); staging's `decided` holds the hash of the rid or of one of its records (classified private, or promoted with cuts); or one of its records has a version staged with cuts or in raw cut |
| 3. holds and releases | a hold covers the rid's record (its rid, thread or container, as holds cover); a release with cuts does; or a release leaves a version of one of its records out (the gate's own `_left_out`). A release with no cuts that keeps the records passes; a hold beats a release (DR-0201) |
| 4. one file per rid | media for the rid is already in `media/` |

A put also needs this clone to have ingested the rid's source: its cursor file holds the source. Otherwise it is refused
with "this machine hasn't ingested <source>; put its media where it runs", since the marks below are this clone's
alone.

A version dropped for a never-store match, or classified private, leaves nothing staged or in raw for check 2 to read,
and its rid may not be the media's (a transcript under the recording). So each such drop leaves a durable mark:

- `staging/_withheld.jsonl`: one line per rid, `{"rid": "<32 hex>"}`, for the dropped version's rid and each
  `<rid>/` ancestor of it, so the mark reaches the rid the media is put on. Appended when `stage` or the sweep drops a
  version for a never-store match, and when `classify(..., "private")` drops one; written before the version is
  deleted. A hash the file holds already isn't appended again: the set is read for check 2 anyway, and a record sent
  again on every sync would otherwise grow the file each time.
- Append-only, fsynced, and safe against a torn last line, as `_decided.jsonl` is; a line that doesn't read is skipped,
  as `decided` skips one. Hashes only, never content, on this clone's disk, never in git.
- Nothing removes an entry. When a value comes off a never-store list, its entries stay: they were written for audio
  whose transcript named the value, and that audio still holds it. A later rule could lift one at the owner's console;
  #42 adds none.
- A private source and a release need no mark: the settings in force and the release logs fail them for as long as
  they hold.
- It is one clone's, and never committed: a clone that never staged the dropped version has no mark. A put on a clone
  that hasn't ingested the source is refused (above), and a clone that does ingest it stages and drops the same
  version under the same `vault.yaml`, so its mark follows. The case left is in Risks.

- Every check reads something durable: `vault.yaml` in force, the raw log, staging's files, its `decided` keys and
  its `_withheld.jsonl`, the hold lists and the release logs. Nothing depends on a drop remembered in memory, so a sweep
  killed halfway, a classification made between sweeps or a record intake drops loses nothing.
- A version in raw can't keep media alive. With v1 in raw and v2 staged with its audio:
  - the owner classifies v2 private: `decided` and `_withheld.jsonl` hold it for good, so check 2 fails at every later
    sweep and at every later put;
  - a speaker added to never-store drops v2: the drop deletes the media in the same step (below) and marks the rid in
    `_withheld.jsonl`, so a later put fails check 2 even when v1 is clean;
  - the source sends v2 naming a never-store speaker, intake drops it, and the run's media step puts the audio again:
    the mark from intake fails check 2, and nothing is staged;
  - a release leaves v2 out: check 3 fails while the release log says so.
- A version cut by hand, on the transcript or any record of the family, fails check 2 as well: the cut took a stretch
  out of the transcript, and the audio still holds it. #157 can let such media in once it cuts the audio by the same
  times.
- The audio itself can't be screened before #157 and #158 decode it, so its record's text and the owner's decisions
  decide for it.
- At the put, checks 1 to 4 run once before the fetch, so nothing is downloaded for a refused rid. They run again under
  the vault lock after the fetch, before the file goes into staging, because the fetch can take 15 minutes and the
  settings, the holds or staging can change meanwhile.

### The gate

| The rid | Its media |
|---|---|
| a version staged, pending or ready, and every check passing | waits |
| in raw at a promotion, every check passing again | moves to `media/`, then is committed after the run's commit, in the same lock: `Media: <source>, N file(s) from <machine>` |
| in raw at a promotion, git-lfs missing or its filter off in the repo | waits, with the problem named. Records still promote |
| any check failing, at a sweep or at promotion | deleted with its sidecar and its key |
| a version of one of its records dropped: classified private, swept (private, never-store, decided, left out) or dropped at intake | deleted in the same step, before the version |

- A drop finds the media to delete from the dropped version: staged media on its rid or any `<rid>/` ancestor of it. It deletes that media, its key and its sidecar first, marks `_withheld.jsonl` when the
  drop is for never-store or private, and deletes the version last, inside the same lock:
  in `classify(..., "private")` before `remember` and the delete, in the sweep before each delete, and in `stage` for a
  record dropped in memory. A crash between the two leaves the version without its media, and the version meets the
  same rule again: the next sweep drops it, or the owner classifies it again. A crash before both leaves both, and the
  next call does the same again.
- Orphans in `staging/_media/`, at every sweep: an `.age` with no sidecar, a sidecar with no `.age`, and the key of
  each, found by the file's header or the sidecar's key id. They are deleted, and whatever can't be read is deleted
  too, never kept: an orphan is never promoted. Encrypted temp files a put left in Docket's private folder go by name.
- Media moves to `media/` by a rename; its sidecar stays in staging until the commit lands, then goes.
- A commit that fails moves back to staging, where its sidecar still is, each file HEAD doesn't hold. One that
  landed and then raised keeps its files where HEAD has them; no clean-up deletes the key of a file HEAD holds.
- A crash between the rename and the commit leaves a file in `media/` that git doesn't track. The next promotion
  commits such files first, as it does an interrupted run (`uncommitted_runs`), after the four checks, read through the
  sidecar still in staging. A file there with no sidecar is never committed; the promotion names it as a problem.
- The sweep runs at every gate call and lists `staging/_media/`, which is cheap. `docket staging list` and the Staging
  page add how many media files wait.

### The fetch

| From | Allowed when |
|---|---|
| a path | it resolves, after every link, to a regular file under one of the source's `media_folders`, or under Docket's drop folder (`<state dir>/drop/`). Not a OneDrive placeholder. A file put from the drop folder is deleted once stored; one from a media folder is left as it is |
| a URL | `https`, a host exactly in the source's `media_hosts` |

- DNS, then the check: every address the host resolves to must be allowed, or the whole host is refused, even if some
  addresses are fine. An address is allowed when it is global (`ipaddress`'s `is_global`) and isn't an IPv6 form of an
  IPv4 address: `::ffff:0:0/96` (mapped), `::/96` (compatible), `64:ff9b::/96` and `64:ff9b:1::/48` (NAT64),
  `2002::/16` (6to4) and `2001::/32` (Teredo) are refused outright, since `is_global` says yes to some of them on
  Python 3.12 and each can reach an IPv4 address the check never saw.
- The connection goes to a checked address, with the host as SNI and for certificate checks (an `http.client`
  connection whose `connect` dials that address). There is no second lookup to rebind, and no proxy: environment
  proxies are ignored.
- Redirects: at most 3, each answered by the same checks (https, a listed host, allowed addresses).
- `Accept-Encoding: identity` on every request, and a response with any other `Content-Encoding` is refused, so the cap
  counts the bytes stored and nothing is inflated.
- Size: 512 MiB by default, `media.max_bytes` in the machine's `config.yaml`. A `Content-Length` over the cap refuses
  before the body is read; a body that grows past it stops the read, and the partial encrypted file is deleted.
- Time: 15 s to connect, 60 s without a byte, 15 minutes in all.
- A URL is never logged, stored or put in an error: a signed URL is a credential. Errors name the host only.

`media_folders` is a new optional key on a source in `vault.yaml`, a list written like a folder source's `folder`:
relative to the consuming repo or under `~/`, never absolute (DR-0481's rule). `schema_version` stays 1, as for
DR-0124's keys. A folder on another drive goes through the drop folder.

### The settings in force

`inforce._source` treats both lists as it treats `tools`: what HEAD and the file both list. An entry added by hand
waits for its commit, and an entry removed applies at once. `loosens()` then flags an addition, so:

| Change | How |
|---|---|
| add a host or a folder | `docket media host add <source> <host>`, `docket media folder add <source> <folder>`: `settings.rewrite` asks at the owner's console (DR-0517); by hand, it applies once committed (DR-0521) |
| remove one | `docket media host remove`, `docket media folder remove`: written at once, nothing asked |
| the Settings page | shows each source's hosts and folders, with the commands; it makes none of these changes (DR-0506 is unchanged) |

### Encryption, while reading

- pyrage, MIT, the Rust age implementation, exact-pinned like `mcp`, with the same platform marker as `sqlite-vec`
  (no wheel for Windows on Arm or musl). On a machine without it, `media_put` and the reader say so; everything else
  works.
- Per file: `x25519.Identity.generate()`, then `encrypt_io(reader, writer, [recipient])` to that identity's recipient
  alone. There is no second recipient, no machine key and no master key, so deleting the identity forgets the file
  (design §5.5).
- The reader is Docket's own: it reads the response or the file in chunks, keeps the first bytes to sniff the type,
  counts the cap, and raises past it. The writer is a temp file in Docket's private folder, holding only ciphertext.
  pyrage 1.4.0 has `encrypt_io` and calls a Python reader's `read`; the build checks this first, and the fallback, if
  it can't, is plain temps named `media-plain-*.tmp`, cleared by name at every sweep.
- A file's key id is the sha256 of its age header: the bytes up to and including the `---` MAC line. It is unique per
  file, stable when the file moves from staging to `media/`, and readable from the file itself.

### The key store

```
<private>/media/store.json            {"schema_version": 1, "id": "<random>", "store": "keyring" | "file"}
<private>/media/keys/<key id>.age     one key: {"identity", "path", "at"}, sealed with age to the store's recipient
```

- `<private>` is the clone's Docket folder in its git dir (`.git/docket/`, or the host's for a folder vault). It is
  never in the tree and never in git, and a copy of the repo folder carries only sealed files.
- The seal is a store identity:

  | `store` | Where the store identity lives |
  |---|---|
  | `keyring` | the OS keychain, as `docket` / `media-store:<id>`: one entry per clone, not one per file |
  | `file` | `<state dir>/media-stores/<id>`, readable by the user only, outside any repo and any synced folder Docket knows |

- Keychain only by default. At the first put on a clone the keychain is used when a write and a read-back work there;
  when they don't (CI, a Linux box without Secret Service), the put is refused naming
  `docket media keys init --store file`, which opts that machine in. It is never a silent fallback. CI's tests opt in
  under their temp folders.
- Order at a put: the encrypted file under a temp name (its header names the key), then its key file, then its sidecar,
  then the rename into staging. A crash leaves an encrypted temp file, which the sweep clears by name, or a key for no
  file, which decrypts nothing. The identity is held in memory only until its key file is written.
- `keys.delete(key id)`: the gate's deletions now, and forget later.
- `docket vault convert` moves `<private>/media/` with the rest of the private folder, or a converted vault would lose
  every key.

### A second machine, and the backup (PR 2)

Nothing about keys travels in git: not a key, not a wrapped key, not a recipient. A folder vault's history is never
rewritten, so anything put there stays for good.

- `docket media keys export <file>`: at the owner's console only (`console.problem`: refused in Claude Code's shell, a
  pipe or a redirect). Docket draws a passphrase (24 letters in groups of 4), shows it once, and writes every key of
  the clone into one file sealed with age's scrypt passphrase mode: `{"schema_version": 1, "keys": [{"id", "identity",
  "path", "at"}]}`.
- `docket media keys import <file>`: at the console, asks for the passphrase, and adds the keys it lacks. A key whose id
  it has is skipped and counted.
- Where the export goes is the owner's choice at export time. The README names the options: a password manager entry
  with the file attached, a USB stick, a synced folder.
- The export is the backup. Every export holds every key, so the newest one is enough. `docket media status`,
  `docket vault status` and the session-start dashboard say how many keys no export has held yet. They count against
  `<private>/media/exported.json`, which lists key ids and no keys.
- Forget, when it comes, deletes a key here, but a key reaches further than this clone: into every export made before
  and into every clone that imported one. Forget has to reach those clones, for example through a committed list of
  forgotten key ids that each clone applies at its next gate call (ids only, so nothing secret enters git), and to
  say that exports made before still hold the key. That is forget's issue to build; this plan keeps keys addressable
  by id so it can.

### One reader

`docket.media.read(vault, rid) -> Media`, used by the service and imported by the models' worker, which opens the
vault itself as it does today. Nothing plain is written to disk: it decrypts into memory, bounded by the cap.

| `Media.state` | When | The Recording page says |
|---|---|---|
| `ok` | the bytes and their type | (the player comes with #159) |
| `not-fetched` | no media for the rid, staged or stored | #164's "No audio stored yet" |
| `held` | a hold covers the rid, or a release with cuts does | "The audio waits with the recording's hold" / "until Docket can cut it" |
| `not-downloaded` | an LFS pointer is in place of the file | "The audio is stored but not downloaded here: git lfs pull" |
| `no-key` | the file is here, its key isn't | "The audio is stored, but this machine has no key for it", and, once PR 2 is in, how to import one |

`no-key`, `held` and `not-downloaded` go into #164's `NO_AUDIO`, each with its sentence and test. The page reads the
state with `Media.state_of(vault, rid)`, which checks the header and the key file without decrypting.

### The source's run (PR 2)

Once a source lists a media host or folder, `run_open`'s steps gain one step after ingest: for each recording with
audio, `media_put(rid, url)` with the URL the source's tool gave. The Plaud reference `SKILL.md` names the call that
gives the audio. Which host Plaud's audio comes from is learned on the first real run.

### Alternatives

| Not chosen | Why |
|---|---|
| checking media only at the put | a version in raw would keep media alive that the gate since refused, and promotion would commit it |
| the sweep remembering, in memory, which rids it dropped a version of | lost when a sweep is killed, and blind to `classify` and to intake, which drop outside the sweep |
| keeping held media waiting until the hold comes off | a release with cuts would then need it deleted anyway; deleting on a hold is the safe default until #157, which should revisit it, since a cut release needs the audio and it would be put again |
| a keychain entry per file | thousands of entries, no listing to export from, slow on macOS |
| keys derived from one master secret | deleting a key would forget nothing: it can be derived again |
| each file also encrypted to every machine's key, or wrapped keys committed | a key in git, even wrapped, stays in a folder vault's history for good |
| machines syncing keys over the network | both online at once, and a new listening surface |
| our own age on `cryptography` | rolling our own crypto, for a format pyrage covers |
| `httpx` for the fetch | pinning a checked address with the right SNI means fighting its transport; `http.client` does it in a few lines |
| download to a plain temp, then encrypt | plain audio on disk, however briefly, and in the way of every crash |
| the month from the latest version's `ts` at each read | a `ts` changed between versions would point at a month the file isn't in |

## Doors and data

| Door (AGENTS.md) | Change |
|---|---|
| the MCP tools' names and parameters | adds `media_put(rid, path, url)`. One-way: Claude's calls and skills depend on it |
| the vault's format | `media/<source>/<yyyy>/<mm>/<rid hash>.<ext>.age`, the design's layout with `<id>` defined and the month fixed at storing |
| `vault.yaml` | `media_folders` on a source: optional, `schema_version` stays 1 |
| staging's files | `staging/_media/`, the media and its sidecar, beside the sources' folders; `staging/_withheld.jsonl` beside `_decided.jsonl` |
| a file users keep | the export bundle, schema_version 1; a later Docket reads every earlier one (PR 2) |

- Existing vaults: nothing moves. `media/` is empty everywhere today, and `media_hosts` is in vault.yamls but nothing
  reads it.
- The key store isn't a vault door: it lives on each machine. A lost store with no export loses that clone's media for
  good, which is the point of the design. Its format is versioned all the same.
- PR 1's title names its doors: "Add media_put and the media layout (one-way doors)".

|---|---|
| no record staged or in raw | put names it, nothing written |
| source private, off, or not in force | each refused at the put; each deletes staged media at the sweep |
| a version matching a never-store value | refused at the put; deletes staged media at the sweep |

| a put on a clone whose cursor file doesn't hold the source | refused, naming where to put it |

| a version cut by hand, staged or in raw | the media goes, and a put for the rid is refused |
| a sweep stopped between the media's deletion and the version's | the media is gone; the next sweep checks the version again and drops it |
| an `.age` with no sidecar; a sidecar with no `.age`; either unreadable | each deleted at the sweep with its key, never promoted |
| a held id, on the rid or its container | refused; a hold arriving after the put deletes the media at the sweep |
| a release with cuts | refused; one arriving after the put deletes the media at the sweep |
| a release with no cuts | stored |
| a check failing during the fetch (a hold added, the source made private) | the put stages nothing and deletes its key and temp |
| media already in `media/` | refused at the put; a staged duplicate deleted at the sweep |
| a path outside the media folders, a link out of one, a placeholder | each refused |
| `http://`, a host not listed, a host with one private address among public ones | each refused before connecting |
| loopback, link-local, 169.254.169.254, CGNAT, `::ffff:` mapped, `::/96` compatible, `64:ff9b::/96` NAT64, 6to4, Teredo | each refused |
| a redirect to a private address, to http, to an unlisted host; a 4th redirect | each refused |
| a `Content-Encoding: gzip` answer | refused; every request sent `Accept-Encoding: identity` |
| a `Content-Length` over the cap; a chunked body over it; a cap set lower in `config.yaml` | refused before reading; cut off, the partial file gone; the setting honoured |
| no plain copy | during a put, no file under Docket's folders or staging holds the source's bytes |
| a URL with a token in its query | never in the log, the error or staging |
| promotion | the media commits to `media/` after its record; no commit ever holds `staging/` |
| a failed media commit | the files are back in staging with their sidecars |
| a crash between the rename and the commit | the next promotion checks and commits the untracked file |

Against: invented vaults from `docket_testkit` (a Plaud-shaped record staged and in raw), generated bytes with an mp3
or Ogg header, a local HTTPS server on port 0 with a certificate made by `cryptography` in the test, and an injected
