# Set up the development harness

## Goal

Every later change to Docket runs one loop (issue, plan, review, gate, PR, review, merge) with checks that an agent or
a person can't skip. In scope: the router docs, the docs regime and its tool, the gate, the git hooks, the four
work-loop skills, the uv workspace with a first package and the plugin skeleton, and GitHub (CI on three systems,
CodeQL, Dependabot, forms, the ruleset's required checks). Out of scope: any app code beyond `docket --version`; the
design document, which comes in its own change.

## Design

The work loop is WriteableFileProviders' (start-work, review-plan, review-code, finish-work, a REVIEW.md, plans and
reviews as records), with Docket's review rule: not a bug hunt, a finding needs a reproducible scenario, another round
only after a blocker or major (DR-0009). The docs regime follows the YAML-entries model (DR-0005), written fresh in
Python as `tools/devkit` with a schema file (`docs/docs-regime.yaml`) driving a generic reader, checker and canonical
emitter. The gate is one Python command with three lanes (quick, full, os) so the pre-push hook, finish-work and CI run
the same steps (DR-0006). Private names are checked against a deny list outside the repo (DR-0008).

Alternatives: porting home-server's docs CLI (built around its own task board; most of it would be rewritten);
pre-commit hooks for the checks (a second runner beside the gate, and Windows-hostile); a separate kit repo (DR-0003).

## Doors and data

It names the first one-way doors (the `docket` package and command, the plugin's and the marketplace's names) in
`AGENTS.md`. No user data exists yet.

## Steps

1. The founding commit on main (licence, README, text settings); the ruleset making main PRs-only; milestones, labels
   and the board.
2. The workspace, the devkit (docs tool, gate, hooks, board helper) with its tests.
3. The router docs, the regime and its first entries (written with the tool), the skills and lenses.
4. GitHub: CI, CodeQL, Dependabot, forms, the PR template; the deny list as a CI secret.
5. `gate full` locally, the PR, `review-code`, CI green; then the gate's jobs become required checks; merge.

## Tests

`tools/devkit/tests`: the emitter's round trips over tricky values, comment placement, every writer verb, refusals
(problems added, file changed on disk, stray comments), citations, the content check (files, paths, commits, masked
output), commit and PR-title rules, coverage floors, the harness step. `packages/docket/tests`: the CLI. CI runs
`gate full` on Linux and `gate os` on Windows and macOS.

## Docs

AGENTS.md, REVIEW.md, CONTRIBUTING.md, SECURITY.md, CHANGELOG.md, docs/docs-regime.md, docs/plans/README.md,
docs/reviews/README.md; the entries DR-0001 to DR-0011, CV-0001 to CV-0010, the first terms.

## Risks

- The gate is new code and could pass what it should refuse: its own tests cover each refusal, and the review reads it
  as a sensitive area. Accepted.
- Claude Code's CLI in CI could break the full lane on an update: it is pinned, and Dependabot doesn't move it.
  Accepted.
