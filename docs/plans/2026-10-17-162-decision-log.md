# Keep a decision log that Claude proposes into and only the user confirms

## Goal

A decision is a processed doc about one thing decided, hung on a project, topic or stream entity (design §3.5). Claude
proposes candidates from the notes; only the user's click on the Briefs page confirms or rejects one. A later decision
supersedes an earlier one and both stay. A contradiction is marked, and the user picks.

- In scope:
  - the decision doc and what doc_put checks;
  - the status rules and their one writer;
  - the supersede and contradict links;
  - what every read shows;
  - the `decisions` MCP tool and CLI;
  - the plugin's `decision` skill;
  - the decisions on the Briefs page;
  - never-store.
- Out of scope:
  - writing into a stream's own `decisions.yaml`, which waits for an export;
  - "same as D-12", which adds evidence to an existing decision;
  - streams as ledger objects (phase 3): until then a decision hangs on a project, topic or stream entity;
  - an OS prompt (#143).
- Built on #160/#166 (refs and flags) and #161 (briefs, with the page from #172).
- Two PRs:
  - **The first:** the doc, its checks, the reads, the tool and the skill. It is useful on its own: candidates collect,
    and nothing reads them as decided.
  - **The second:** the page's decisions and the confirm writer, the only way a status changes.

## Design

### The decision (DR-0563)

```markdown
---
id: decision:2026-10-13-dashboard-before-pilot
type: decision
covers:
  - calls:rec-0101
by: claude-opus-5.5, decision 2026-10-14
entities: [fleet-management, ben-sample]
status: proposed
subject: fleet-management
replaces: [decision:2026-09-30-pilot-first]
---

# Proposed: the charging dashboard ships before the pilot

- Ben said the dashboard goes first, on the fleet review. [r:calls:rec-0101@00:40-01:39]
- Built from the review's minutes. [d:minutes:2026-10-13-fleet-review@1#12=0a1b2c3d]
```

| Rule | What doc_put checks |
|---|---|
| Id | `decision:<yyyy-mm-dd>-<words>`, the date it was said; the page sorts by it |
| Subject | `subject` names one existing entity of type project, topic or stream, which `entities` holds too |
| Status | `proposed` on every put. `confirmed` and `rejected` are written only by the page (DR-0564) |
| Title | `# Proposed: <the decision, one sentence>`. The page's rev writes `# <it>` on confirm and `# Rejected: <it>` on reject, so an editor, GitHub or an older Docket never reads a candidate as decided |
| Lines | every content line ends with raw anchors, refs or both, as a brief's do (#166) |
| `replaces` | confirmed, current decisions on the same subject that this one supersedes once confirmed |
| `contradicts` | confirmed, current decisions on the same subject that this one says otherwise than |
| `supersedes` | refused on a decision. The page's confirm moves `replaces` into it, so the generic supersede (search, flags, `superseded_by`) only ever sees a confirmed replacement, on this machine and on an older one |
| Revs | a proposed decision takes new revs through doc_put, for wording or more evidence. A confirmed or rejected one takes none: a change is a new decision that replaces it |
| Not again | a candidate whose every anchor and ref a rejected decision on the same subject already holds is refused, so "not a decision" isn't proposed again |

The new frontmatter keys are `status`, `subject`, `replaces` and `contradicts`, all checked only for the `decision` type.

### Proposed never reads as decided (DR-0565)

| Where | What it shows |
|---|---|
| A search hit on a decision | its state before its title: proposed, rejected or superseded decision; a confirmed, current one just "decision" |
| `read`, CLI and MCP | `status`, `current` and `superseded_by` beside the doc |
| `decisions` and `docket decision list` | each decision with its status and whether it is current |
| A brief | cites only current decisions (confirmed and not superseded): doc_put refuses a ref to any other, and a later supersede flags the line (#166's `superseded`), so the brief goes stale |
| The Briefs page | proposed ones under "Waiting for you", never among the decided |
| The file | the title's prefix |

The `decisions(entities=None, status=None)` tool is read-only. For each decision it gives:

| Field | What |
|---|---|
| `id`, `subject`, `title` | the decision's id, its subject entity, and its title without the prefix |
| `status`, `current` | proposed, confirmed or rejected; current when confirmed and not superseded |
| `rev`, `rev_time`, `by` | its last rev, that commit's time (UTC), and who wrote it |
| `replaces`, `contradicts`, `supersedes` | its own links |
| `superseded_by`, `contradicted_by` | the links back, from the index |
| `flagged` | how many of its lines cite a line that changed |
| `cite` | the title line's `[d:]` token when it is current; null otherwise, so a brief can't cite another |

As a whole it also gives `hidden`: the decisions it left out because a never-store list holds their subject.

### History and contradictions

- **Supersede.** The newer decision's `supersedes` names the older; the index's `superseded_by` links the older back.
  The older never takes a rev: its text, sources and revs stay readable, and `verify` works on it as on any doc.
- **Contradicts, decided by Claude.** The decision skill reads the subject's current decisions and makes a call for each
  candidate:
  - `replaces` when the speaker changes an earlier decision ("we moved it to Monday");
  - `contradicts` when someone says otherwise without changing it;
  - neither when the candidate stands alone.

  Docket checks only the form: the target exists, is confirmed and current, and has the same subject. Docket stores the
  link and never infers a contradiction.
- **Marked, nothing else changes.** A candidate with `contradicts` changes no other doc. The confirmed decision keeps its
  rev, text and status, and the briefs citing it stay current. The index derives `contradicted_by` for the page.
- **The user picks**, on the page (DR-0566):

| Pick | The candidate's next rev | The confirmed decision |
|---|---|---|
| The new one replaces it | confirmed; `supersedes` takes the old one, and `contradicts` drops it | superseded, readable, linked back |
| The old one stands | rejected; `contradicts` is kept | current; the page shows it was contradicted, with the candidate's sources |
| Not a contradiction | confirmed; `contradicts` drops it | current |

A candidate with only `replaces` gets Confirm (which supersedes) or Reject.

### Confirming (DR-0564)

The user confirms or rejects with a click on the Briefs page. A skill round lines the candidates up and recommends, then
ends with the page's link, where the user clicks. Each click is the decision's next rev, written by the service:
`by: <owner>, Briefs page`, in a commit `Decision: <id> confirmed on the Briefs page`.

What stops Claude from confirming on its own: in a skill round Claude has no way to write a status at all.

| Door | Why it can't set a status |
|---|---|
| `doc_put`, through MCP or the CLI | refuses any status but `proposed` on a decision, and refuses `supersedes` |
| A hand edit | the take-in refuses one that changes `status`, `supersedes`, `replaces` or `contradicts`, and leaves it on disk, as a keyword stop does |
| The file on disk | a decision's status and links are read from its last commit, so an edit no commit holds, Claude's Edit tool included, changes nothing |
| The skill | pre-approves only read-only tools, and has a rule that only the user decides; it never calls a candidate decided |
| The page | the confirm is a same-origin form post with the browser's session, checked by the Guard, run on the writer thread, and refused when the decision changed since the page showed it |

**The floor.** Claude could still:
- drive the page in a browser;
- post the page's form with a session it got from the token;
- commit a file with git itself.

Each of these is a deliberate step outside every door Docket gives it: the same floor as DR-0382's console code. A
browser agent the user tells to click is the user acting.

**Not chosen:**
- **A console-only command with a code typed back (DR-0202).** It is the stronger floor, but it costs a code per batch
  for a weekly routine, and decisions would be read there without their sources side by side. The console guards what
  lets private data in, and a decision doesn't.
- **A token the page shows and the user types into the skill round.** It stops nothing a click doesn't, since reading
  the page for the token is the same act as clicking (DR-0382), and it adds a token store.
- **An MCP or CLI confirm that isn't pre-approved, so Claude Code asks.** Auto mode and allow rules remove that prompt.

### The page (DR-0566), the second PR

| Part | What it shows |
|---|---|
| A brief's page, for a project, topic or stream | Decisions, newest first: each current one with the ones it superseded folded under it (`<details>`, no script); "Waiting for you": proposed ones, contradictions first, each beside the decision it contradicts or replaces; rejected ones folded |
| An entity with decisions and no brief | opens at its `brief=brief:<id>` URL too: "No brief yet", then its decisions. Today that URL is a 404 |
| The list | how many decisions wait, per entity, with links |
| Each decision | its title, status, date and lines, its anchors linked as a brief's are, and "Verify" to open it on the Search page beside its raw |
| Buttons | Confirm and Reject; on a candidate that contradicts, the three picks. Each posts to `/briefs/decision` with the decision's id and the rev shown, and answers 303 to the same page with `done=<what>` |

The URL gains `done`, which is optional.

### Candidates: the `decision` skill

The plugin's `decision` skill:

1. `decisions(entities=[subject])`: the subject's current, proposed and rejected decisions.
2. Reads the notes and minutes since its last round (`search`, `read`, `verify`) for statements that look decided, each
   with who said it and its cite.
3. Makes a call for each: propose it, propose it with `replaces` or `contradicts`, or skip it as a wish, an opinion, a
   question, or already decided.
4. `doc_put`s each candidate as proposed; Claude Code asks the user.
5. A round: one table of waiting candidates, each with its call and why, then the Briefs page link.

It never confirms, and never says a proposed one is decided. A sync run's closing steps gain one line, as briefs did:
after the run's notes are written, `decisions()` counts what waits; say so once, and propose candidates from the new
notes only when the user asks.

### Never-store, as briefs (#170)

| Rule | Where |
|---|---|
| No decision on a subject `brief_form.held` holds, or with such an entity in `entities` | doc_put refuses it |
| No line, title, ref, own id, `replaces` id or `contradicts` id names a listed person in any shape | doc_put's people screen, shared with briefs (`person_listed`, `person_phrases`) |
| A hand edit that names a listed person | the take-in refuses it, as for briefs |
| A list that gains a value later | the page and the tool leave out decisions on a held subject and count them as hidden; a line a list now names opens nothing; a URL that opens one opens nothing |

### Older machines

- An older Docket reads a `decision` doc, with `status`, `subject`, `replaces` and `contradicts`, with a warning
  (DR-0109).
- The title's prefix keeps a candidate from reading as decided there.
- `supersedes` only ever sits on a confirmed decision, so an older Docket's generic supersede is right.
- An older machine shows a superseded decision as current until it updates: update every machine before confirming
  decisions.

## Steps

The first PR:

1. **The doc.** The type, its keys and form checks, the rules for revs and for not proposing again, never-store, the
   take-in's refusal, and status read from the last commit. Tested by `test_decisions.py`.
2. **The reads.** The index columns, status in search and `read`, the `decisions` tool and `docket decision list`, and
   briefs citing only current decisions. Tested by `test_decisions.py` and `test_service_mcp.py`, which pins the fields.

The second PR:

4. **The page.** `DocStore.decide`, the only status writer, and the page's Decisions part with its form posts. Tested by
   `test_web_briefs.py` and the browser test.

## Tests

| Test | What it proves |
|---|---|
| Proposed is never decided | a candidate reads as proposed in a search hit, in `read`, in `decisions` and on the page; a brief citing it is refused; its file's title says Proposed |
| Status has one writer | doc_put refuses `confirmed`, `rejected` and `supersedes` on a decision, through MCP and the CLI |
| A hand edit | a status changed on disk reads as its last commit has it; the take-in refuses it and leaves it on disk |
| Supersede keeps both | confirming a candidate that replaces another keeps both docs: the old one readable with `superseded_by`, the new one with `supersedes`; a brief citing the old one is flagged and goes stale |
| A contradiction is marked, nothing else changes | a candidate that contradicts leaves the confirmed decision's rev, text and status alone, and the briefs citing it current; the page shows both, and each of the three picks writes only the candidate's next rev |
| Revs | a proposed decision takes a new rev for wording; a confirmed or rejected one takes none |
| Not again | a candidate citing only what a rejected decision cites is refused |
| The form | a missing or wrong-typed subject, a bad id, a title without its prefix, an unanchored line, and `replaces` or `contradicts` naming a decision that isn't current or is on another subject are each refused |
| Never-store | a held subject gets no decision; the people screen's shapes are refused; the tool and the page hide a subject listed later and count it |
| The page | renders without JavaScript; a click confirms, rejects or picks, as the decision's next rev by the owner; a rev changed since the page showed it is refused; `done` says what happened |
| The tool | the `decisions` fields and `hidden` |

All of these run on the test kit's vaults, with invented people.

## Risks

| Risk | Answer |
|---|---|
| A process running as the user confirms on purpose: a browser, a session from the token, git | accepted: the same floor as DR-0382. #143's OS prompt can cover the page's confirm later if a wrong confirm ever matters |
| Claude misses a contradiction, or marks one that isn't | Claude proposes and the user picks. A missed one shows when the user reads the subject's decisions side by side on the page |
| An older machine shows a superseded decision as current | update every machine before confirming decisions; the title's prefix keeps candidates right everywhere |
| Reading status from the last commit costs a git read | one `git cat-file --batch` per index update and per page view, cached by blob id |
| A subject entity is merged away | its decisions list as orphaned, as briefs do, naming the survivor unless it is held; moving them over is a new decision each |
| The streams' `decisions.yaml` files stay separate | out of scope: an export later, once the log has a week of real use |
| A confirm is final, and a wrong one stays | a wrong confirm is replaced by a new decision, and both stay; nothing is overwritten (design §3.5) |
