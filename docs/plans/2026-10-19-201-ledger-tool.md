# Open the ledger to Claude: the ledger tool

Two MCP tools: `ledger` reads, read-only, so a skill pre-approves it; `ledger_batch` writes one all-or-nothing batch
through `store.write`, a dry run first, its ops the writer's changes with 12 of todo.py's 20 op names, `as`/`$x` and
`by` on any op. `docket ledger` mirrors both. Two PRs: the batch, then the reads after #199's meetings index.

## Goal

- Done: every todo.py verb `/sync` and `/tasks` use has a read or a batch op, for the skills (#209, #210) and the
  pages (#203 to #206); history questions answer from counts, not log words.
- Out: the skills, the import (#202), meetings from calendar records and links by time (#200), the dashboard (#207).

## Design

### Two tools

| Tool | Annotations | Takes | Does |
|---|---|---|---|
| `ledger` | read-only, closed world | `view`, `ref`, `since`, `until`, `who`, `stream`, `kind`, `state`, `k` | one read, below |
| `ledger_batch` | as `run_open`: writes, not idempotent | `ops`, `by` (`claude`), `dry_run` (false) | one write through the writer, `via: tool` |

- Named as today's: a noun reads (`briefs`), a noun and a verb writes (`doc_put`). One tool with an action is
  read-only or not as a whole, so a skill would pre-approve writes or prompt on every read.
- Trust model (#191), no new guard: `by: user` for what the owner said in chat, `claude` for what Claude did, `sync`
  in a sync. Claude Code's prompt on `ledger_batch` is the one in place; skills pre-approve `ledger`.

### The reads

| `view` | todo.py | Takes | Gives |
|---|---|---|---|
| `snapshot` (default) | `snapshot --from --days` | `since`, `until`: yesterday to today + 6 | open and snoozed items; meetings in the window or with an open point, their points and open items; streams |
| `show` | `show`, `link`, `notes`, `material list`, `meeting show`, `stream list` | `ref`: A-, M-, an id, a stream | one object whole: fields, notes, materials, points with ids, linked items, history, counts |
| `queue` | `queue`, `list --json` (untriaged) | - | the untriaged open items, then the rest by verdict (discuss, claude, me, chase), each by due |
| `list` | `list --kind --stream --who --state` | `who` (a part), `stream`, `kind`, `state` (open, snoozed, done, dropped, all), opened in the window, `k` (50) | counts over all that match, then the first `k` |
| `meetings` | `meeting list`, `meeting match <time>` | `since`, `until` as days or times: today to today + 6 | meetings overlapping the window; match is a window around a time |
| `suggest` | `meeting suggest` | `ref`: an M- number | DR-0629's read, each with why |

What a read returns, shaped for Claude's context:

- Counts first, then a line per row, as todo.py prints: `A-0012 [reply] Ada: Send the dates (12d, due 10-21, 2d
  late) [pilot] @M-0003 <chase>`, the snapshot's with its `source`; `M-0040 10-20 10:00-10:30 Pilot sync, Ada, 2 open
  (A-0012 A-0015)`; `#2 open Ada: the dates -> A-0012 (proposed)`.
- Titles cut at 72; locators never. Ids only where a number names nothing (a clash), and on points everywhere.
- Notes, description, outcome, attendees and the history only in `show`. No read quotes a record: the source is a
  locator and `read` opens it.
- History counts from the ops, never the log's words: an item's times chased (its standing triage ops to chase),
  snoozes, due moves, reopens, days open; `list`'s by state, overdue, chased and median days to done. "How many asks to
  Ada went unanswered" is `list who=Ada kind=waiting state=all since=2026-09-01`. #202 writes the old log's chases,
  snoozes, due changes and reopens as those ops, so the counts reach back to September; the export script does too.
- The structured result, `LedgerRead`, has the same rows with their fields.

### The batch

A list of changes, each `{"op": ...}`, checked in order against the ledger as the ones before left it. One refusal
refuses all, naming its place, op and why. `dry_run` writes nothing and goes on past a refusal: it lists every one it
can and marks the changes that hang on a refused one's `$name`, so one dry run finds three look-alikes.

| todo.py batch op | `ledger_batch` op | What moves |
|---|---|---|
| add, done, drop, snooze, reopen, log, triage, set, notes, point_set, point_item, rollover | the same | `id` and `meeting` are `item`; add's fields go in `fields`; log's `text` is `note`; a point is `point`, its n or id |
| material_add, material_rm | material | `ref`, `label`; `remove: true` |
| meeting_add | meeting | `fields`; #200 writes them from the calendar, keyed by event |
| meeting_set | set | `item: "M-0040"` |
| meeting_link | material on the meeting; set an item's `fields.meeting` | - |
| point_add, point_keep | point, keep | `item: "M-0040"`; point's `fields`: text, item, proposed |
| point_rm | undo | `of`: the point's id; `expect` goes, an id never shifts |
| verbs `stream set`, `archive` | stream, archive | `archive` with no item archives what is due |
| - | undo | `of` an op, or `batch` a write |

- `as`, a lowercase name, on add, point_item (the new item), meeting (the meeting, new, set or joined) and point (the
  point). `$x` in a later op's `item`, `point`, `of`, or `fields`' `item`, `meeting`, `continues` stands for its id,
  so it holds through a number clash. `$y` not named earlier, or a name twice, refuses; `$5` in a title stays text.
- A point's n reads against its meeting as the batch began: removing #2, then answering #3, answers the old #3.
- `by` on any op, else the batch's: the tasks skill logs what Claude did and what the owner decided in one write.
- `done` and `drop` take `outcome`, written as a `set` before the close; `notes` takes `append` or `set`, written as a
  `set` of the whole text (DR-0611 said so).
- `add` refuses a look-alike as todo.py: an open item, or an earlier add of the batch, with (the same source or the
  same who) and 60% of the shorter title's words of four letters or more; `force: true` adds it. The same source
  alone only names the other item.
- A keyless `meeting` with the start and subject of one that stands is refused, naming it: no mail invite doubles one.
- `archive` with no item: items closed 14 days back, meetings started 14 days back with no open point, an undone
  archive skipped. The sync writes it last; no write archives by itself. `rollover` names the meetings that are over
  with open points and no next meeting, as `meeting rollover` did, for the sync to say.
- The result, `BatchResult`: per change, what it wrote or "nothing to change"; each `as` with its number (`$x =
  A-0302`, `$p = M-0040#3`); the batch id for an undo of the whole; the commit.

The writer's part, in `store.py`: a `_Batch` over `_Write` takes `as`, `$x`, `by`, `outcome`, `force`, `notes`,
archive-due and the key checks, then calls `_Write.change`; `Written` gains names, ops per change, labels, remarks
and refusals; `Held` two reads, look-alikes and closed before a day. An import's add is never a look-alike.

### The CLI

| Command | Mirrors |
|---|---|
| `docket ledger batch [FILE] [--by] [--dry-run]` | `ledger_batch`, `via: cli`: a JSON array or JSON lines with `#` comments, from FILE or stdin, UTF-8 with or without a BOM, as todo.py read them |
| `docket ledger snapshot`, `show <ref>`, `queue`, `list`, `meetings`, `suggest <M->` | each view: its parameters as options, its text, or `--json` the result model, every row with no `k`, for the week-in-step diff; all direct to the vault under its lock, as `ledger show` today, so they work with the service down |

## Doors and data

Set for good, each PR's title naming its part, each `cost: one-way`:

- the names `ledger` and `ledger_batch` and their parameters, enums and defaults (DR-0637, DR-0638); results only
  gain fields;
- the batch's op names and keys, and `by` on any op (DR-0639); `as` and `$name` (DR-0640). A golden file holds them.

`medium`: archive-due (DR-0641), look-alikes (DR-0642), a read's shape (DR-0643). `cheap`: the counts (DR-0644), the
CLI (DR-0645). Not doors: the lines' words, the index. Data: none; nothing writes ops before #202's import.
