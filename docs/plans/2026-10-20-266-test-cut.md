# Cut the test suite's time while every PR still runs on all three systems

## Goal

This plan cuts a PR's tests from 76.7 runner-minutes to about 29 (-62%) and this PC's `gate os` from 9.8 to about 3.3
minutes (-66%). That is short of the 80% #266 asks for: under the review's keep rule only 206 tests can go, so the cut
comes from where tests run and what each costs, and the rest of the time is the OS-sensitive tests every PR keeps on
Windows and macOS. Reaching 80% means running fewer of those per PR, the owner's call (What would reach 80%).

| Measure | Before | After, projected | Target |
|---|---|---|---|
| CI test runner-minutes per run | 76.7 | about 29 (-62%) | 15.3 (-80%): not reached |
| this PC, `uv run gate os --only tests` | 9.8 min (the owner's run: 9.6) | about 3.3 min (-66%): the OS-sensitive files and the smoke set | 2 min: not reached |
| this PC, the whole suite (`gate os --all`) | 9.8 min | about 4.9 min (-50%) | reported |
| push to green, a PR's median | 9.1 min | about 5.5 min | reported |
| the nightly full matrix | none | about 64 runner-minutes a night | reported |
| coverage | 99.34% on Windows, 99.32% on Linux; floors 100% for docket, 88% for devkit | the same: the cut keeps every line | floors unchanged |

- In scope: the CI matrix and a nightly run; the gate's selection, shares and floor guard; the test kit; 206 tests
  dropped beside the kept tests that assert the same; 34 timed tests moved to the nightly; fewer git calls in the core
  (PR C, which #234 left for later); docket processes in tests.
- Out of scope: the Models, the OS prompt and service, Checks, Web and Browser (Linux) jobs (16.8 runner-minutes a run);
  this PC's own settings (Defender's scanning of git.exe and the temp folders); git-lfs in the tests (DR-0221 stands).

## Design

### The projection

Each PR in the order of the split, priced at each CI system's own costs: a test's time here split into git calls and
the rest, the calls at that system's price, the rest at its fitted factor, scaled so each file adds up to what CI
recorded for it.

| After | Linux | Windows | macOS | All | Shares L / W / M |
|---|---|---|---|---|---|
| today (the model gives 77.0) | 10.5 | 42.5 | 23.7 | 76.7 | 4 / 12 / 6 |
| PR 2: the OS-sensitive files and the smoke set on Windows and macOS | 10.7 | 19.1 | 11.7 | 41.6 | 4 / 4 / 2 |
| PR 4: the timed tests on big vaults nightly | 9.7 | 18.9 | 11.6 | 40.2 | 4 / 4 / 2 |
| PR 5: PR C | 8.4 | 17.1 | 10.9 | 36.5 | 3 / 4 / 2 |
| PR 6: docket processes in process | 8.4 | 17.1 | 10.9 | 36.5 | 3 / 4 / 2 |
| PR 7: fixtures, the kit's commits without hooks | 7.6 | 14.5 | 10.2 | 32.3 | 3 / 3 / 2 |
| PR 8: the 206 drops | 6.5 | 14.5 | 10.2 | 31.2 | 2 / 3 / 2 |
| PR 9: a share's own files, no empty timed run | 6.0 | 13.3 | 9.7 | 29.0 (-62%) | 2 / 3 / 2 |

Each lever alone, the shares held: the OS matrix 35.4 runner-minutes, the timed tests 1.4, PR C 2.8 (Windows 1.8,
macOS 0.7), fixtures 2.2, the kit's commits 0.65, the drops 0.06, PR 9's closers about 2.2. This PC: the whole suite
from 10,793 worker-seconds to about 7,800.

The two closers the review suggested measured small on CI's own step times: `uv sync` takes 1 to 2 s on every runner
with setup-uv's cache, so a cached venv saves nothing, and the Linux shares' full-history checkout takes 2 s. Neither
is taken. What is: a share imports only its own test files (collection is 4.6 s for all 241 files here, 0.8 s for one,
paid by every worker and by the timed run again), and a share with no timed test skips the timed run's second pytest.
About 25 s a Windows share and 15 s elsewhere, estimated; PR 2 measures the matrix at once, so the gap is known early.

### The OS matrix

| Run | Linux | Windows | macOS |
|---|---|---|---|
| every PR and every push to main | the whole suite, covered; the floors | the OS-sensitive files, the smoke set and the small timed tests | the same |
| nightly on main, `workflow_dispatch`, a PR labelled `full-matrix`, a `v*` tag | the whole suite uncovered with every timed test, beside the covered run | the whole suite with every timed test, and every page in Chrome | the same |

- `tools/devkit/test-systems.json` lists the OS-sensitive files, each with its reason: 107 of 241, 3,218 tests,
  generously. The appendix lists them. Since the list is per file, a system-dependent case added to an unlisted file
  isn't caught by the list itself: the gate fails an unlisted test file that names `sys.platform`, `os.name` or
  `platform.system`, skips by system, or makes links, file modes or file times, and `review-code` asks the question
  for the rest.
- The smoke set is one new file, `test_smoke.py`, marked `smoke`, on a copy of the fixture vault: one case per CLI
  command group, read from the CLI itself so a new group fails until it has one; the service started as a process on
  a free port and every MCP tool called through it, the tool list held to the golden names; a sync run with an ingest;
  a forget at the faked console; the ledger's import; a media put and its promotion in an LFS vault pushed to a bare
  remote. One browser test loads every page of both apps in the system's own Chrome and fails on a console error or a
  CSP violation; it runs only where `DOCKET_TEST_BROWSER` names a browser, as the browser files do, so `gate os` on the
  owner's PC never starts Chrome. About a minute on Windows, 50 s on macOS.
- The small timed tests (The timed tests) are in the selection on all three, whatever file holds them.
- `gate os` runs the selection by default, on this PC too, and `gate os --all` the whole suite; the nightly passes
  `--all`.
- The nightly is a workflow of its own: `schedule` on main, `workflow_dispatch`, `pull_request` with `labeled` and
  `synchronize` and an `if` on the `full-matrix` label, so a push to a labelled PR runs it again, and `v*` tags. It
  has a concurrency group of its own, so it never cancels a PR's run. Only a scheduled run that fails opens an issue:
  one per distinct set of failing tests, labelled `nightly`, or a comment on the open issue for the same set. PR 1
  makes the label.
- A release needs the full matrix green on its commit. There is no release workflow yet, so this binds the first one.
- Before, 66 of a run's 77 test runner-minutes went to Windows and macOS, half of it on files that run the same code
  on every system.

| Job | Before, per PR | After, per PR | The nightly |
|---|---|---|---|
| Linux tests | 10.5 in 4 shares | 6.0 in 2 | about 7.5: uncovered, with every timed test |
| Windows tests, the smoke set included | 42.5 in 12 | 13.3 in 3 | about 34 in 8, with every timed test and every page in Chrome |
| macOS tests, the smoke set included | 23.7 in 6 | 9.7 in 2 | about 23 in 5, the same |
| all | 76.7 | about 29 (-62%) | about 64, once a night |

The nightly adds about 64 runner-minutes a day; the cut saves about 48 on each of the 109 runs a day, so the nightly
gives back about 1% of it. A PR has about 21 jobs instead of 36, four of them on macOS, so the five macOS runners stop
queueing, which is what pushed some PRs to 25 or 34 minutes. Push to green is then about the slowest job: a macOS
share at about 4.9 minutes, a Windows one at about 4.4.

| the only test of a line on Windows, or on Linux | 309 | 573 |
| redaction | 264 | 386 |
| runs a line no other kept test runs | 94 | 338 |

- Every case of a parametrized guard stays, and every test in an OS-sensitive file: a test there checks what the
  system decides, which coverage on one system can't see.
- A test goes only when a kept test asserts what it asserts and the kept tests run every line it runs, on Windows and
  on Linux. 203 of the 206 are cases of a parametrized test whose kept case asserts the same; 3 are tests whose every
  assert a kept test makes word for word. The appendix names each with the test that keeps it.
- Every one of the 79 CLI commands and 53 route handlers keeps a test that runs it.
- The kept suite measures what today's does: 99.34% on Windows, 99.32% on Linux, docket and devkit each unchanged.

### PR C: fewer git calls in the core

| Call | Where | In the suite | After |
|---|---|---|---|
| `diff --cached` after the add | `Git.commit` | 3,215 | only when the commit exits non-zero: nothing new staged returns None as today |
| `ls-files -u` | `Vault.refuse_unmerged` | 3,661 | the index file's stage bits, read in `gitfiles.py`, below |
| `config --get-regexp ^user` | `Git._has_identity_once` | 1,769 | gone: the commit runs with `user.useConfigOnly=true` and, only when it fails for want of an identity, again with the fallback |
| `diff HEAD` beside `status` | the ledger's `pending` | 735 | one status gives both |
| `cat-file`, `show` of a blob | `forgotten`, `docstore`, `inforce`, `show_at_head`, the index build, convert | about 1,900 | one `cat-file --batch` per `Git`, below |
| `rev-parse`, `remote`, `config` of a folder | `toplevel`, `home.rev_parse`, the host's hooks dir, remotes and LFS state | about 2,100 | asked once per process and folder, kept while `.git/config` is unchanged |
| `whoami /user` | the Windows SID in `owner_only` | 318 | once per process, for the default runner only; an injected runner asks every time |

- A Docket commit goes from six calls to three: `status -- raw`, `add`, `commit`. A doc put from seven to four, a
  promote from eight to four, a curate add from eight to five, a `vault.yaml` write from six to three, a ledger write
  from eight to four.
- The identity: today every test commit takes the fallback, since `TEST_GITCONFIG` has no `[user]`; with the new
  order each would pay a failed commit first. So `TEST_GITCONFIG` gets a `[user]` with the fixture owner's name and
  address, the fallback's own, and `test_vault.py`'s author check still holds; a new test runs a commit with no
  identity configured and sees one failed commit, then the fallback. A machine with no identity pays one failed commit
  per write (about 40 ms on Windows); PR 5's decision and its CHANGELOG line say so.
- The index reader reads versions 2, 3 and 4. It asks git above a few MB, since version 4's prefix compression means
  reading every entry; it reads past the TREE, REUC, UNTR, FSMN, EOIE and IEOT extensions and asks git on `link` (a
  split index) or `sdir` (a sparse one), on any other version, and on any read error.
- The batch reader belongs to the vault: the CLI closes it when its command ends, the service at the end of each
  call, and convert, the forget's rewrite and sync close it before they run, as `forget/rewrite.py` already closes
  what it opens, so no `cat-file` holds a pack file open under a repack on Windows.
- About 12,700 of the suite's 33,136 git processes go: 1,230 worker-seconds here, 2.8 runner-minutes a run on CI.
- What Docket commits stays: paths, messages, identity, hooks off. `test_git_calls.py` holds each new list.

### docket processes

Each of the 12 spawns tests the process itself: the console's UTF-8 through a pipe, a non-ASCII argument, two rebuilds
under two hash seeds, the server. The suite already runs the CLI in process (`main([...])`) everywhere else. The trim
moves the setup halves of three pipe tests in process (an init, a doc put, an import): about 10 worker-seconds. It is
its own PR, as asked, and a small one.

### The timed tests

| Per PR on all three systems, alone after the rest | Nightly, on the label and on a tag, on all three |
|---|---|
| a redaction's linear time, a child left holding its output, a write's STATUS.md render, a rerank's budget, the parse route's priority, an hour's call's spots, a worker killed at its timeout, a hostile archive's cap, an update while the worker is busy, a write's wait for its vault | the index's 100,000 chunks, the ledger's 5,000 items, the curate miner, recall on 50 MB of raw, the scan of 5,000 files, the day pages, the service's search, the ledger's import and calendar catch-up at size, a week's hundred events, a report among hundreds of entities |
| 15 s here | 200 s alone here, and their vaults' 400 worker-seconds |

No line runs only in the tests that move, on Windows or on Linux, so the covered run keeps its coverage without them.
A PR that changes the index, the ledger, search or the scan takes the `full-matrix` label.

### Fixtures and the kit's commits

- About 40 files spend more than half a second of setup per test, mostly a copy each of a vault the test only reads
  (`test_web_ledger.py`, the Briefs, Settings and a11y pages, `test_status_render.py`, `test_search_rerank.py`,
  devkit's `test_docs.py`): those tests share one module copy, read-only, held by DR-0531's template check.
- The kit's own setup commits (`sh(..., "commit")`) run the repo's hooks, git-lfs's post-commit among them. Each of
  them passes `-c core.hooksPath=<a file under DOCKET_TEST_HOME>`, the same trick as Docket's own commits; not in
  `TEST_GITCONFIG`, where `git lfs install --local` would break on it. `test_hooks.py`'s helper keeps the hooks.

### The floors

They stay: docket 100%, devkit 88%, per module, rising with the measure. The cut keeps every line on both systems,
and DR-0750 lets a floor come down only for a cut of 80% or more. What changes (DR-0747): the gate fails a change that
sets a floor below its merge base's unless its PR cites a decided decision that sets the number.

## Doors and data

None moves. PR C changes how Docket asks git, not what it writes: the commits, their paths, messages and identity
stay. A machine with no git identity pays one failed commit per write before the fallback, which CHANGELOG.md says.
The rest is tests, the test kit, the gate and CI. Every test that pins a door's format stays.
