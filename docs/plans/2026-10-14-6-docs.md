# Add processed docs with anchors, doc_put, read and verify

## Goal

Claude can write a summary into the vault only when every line points at the raw it came from, and anyone can read
the summary and check each line against that raw in one call. It is the rule the design is built on: a summary is an
index into the raw, never a replacement for it.

- In scope: the processed doc's frontmatter and types; the anchor grammar; the transcript segment contract
  (`docket/vault/segments.py`); `doc_put`, `read` and `verify` as a Python API; `docket doc put | read | verify`.
- Out of scope: the index tables (`docs`, `doc_anchors`, `derived_from`) and search (#7), which build on the resolver
  here; the MCP tools (#8); Plaud's own segment reader (#10); importing legacy notes (#11), though the `legacy-note`
  type is accepted; flagging what was built on a changed doc (needs `derived_from`, phase 2); deleting and forgetting
  docs (phase 2); checking `entities` against `entities/` (they load with #7).

## Design

Five modules in `packages/docket/src/docket/vault/` and one facade; no new dependency.

| Module | What it does |
|---|---|
| `segments.py` | `Segment`, the per-source reader registry, the default reader of `native["segments"]` |
| `anchors.py` | the anchor and locator grammar: a line's anchors, `format_anchor()`, a locator; no I/O |
| `processed.py` | `DocMeta` (the frontmatter), `ProcessedDoc` (parse and render), the id and path rules, which lines need anchors |
| `spans.py` | resolves an anchor against a record into a `Span`: the segments, paragraphs or text it points at |
| `docstore.py` | `DocStore`: `put`, `get` (current or an earlier rev), every doc's frontmatter, the docs covering a rid |
| `docket/recall.py` | the API the service (#8) wraps: `doc_put`, `read`, `verify` and their Pydantic result models |

`doc_put` and `verify` share `spans.py`, so what put accepted, verify can show; #7 fills `doc_anchors` from the same
resolver. Of #4's modules only `vault.py` changes: it gains `Vault.writing()`, a context manager that takes the lock
and then runs the vault's recovery check (`_recover()`), the same guard `Vault.commit` and `Vault.sync` run. The store
reads stored docs only inside it, and every doc commit goes through `Vault.commit`.

### The doc

A markdown file with YAML frontmatter, readable in any editor:

```markdown
---
id: recording-note:2026-10-14-supplier-call
type: recording-note
rev: 1
covers:
  - calls:rec-0042
by: claude-opus-5.5, sync 2026-10-14T16:07
supersedes: []
entities: [ben-sample, northwind]
---

# Supplier call

- Ben put the consultant at 10 million forints for the quarter. @12:08
- Cleo asked for the offer in writing by Friday. @14:30-14:52
```

| Field | Rule |
|---|---|
| `id` | `<type>:<slug>`; the slug is lowercase letters, digits and inner hyphens, at most 80 characters, never a Windows device name (`con`, `nul`, `com1`) |
| `type` | recording-note, thread-summary, digest, minutes, brief, correction, legacy-note; the same as the id's prefix |
| `rev` | the doc's revision from 1, set by `doc_put` (Versions below) |
| `covers` | the rids it summarizes, each in the raw log; at least one, except in a legacy note |
| `by` | who or what wrote it, then optionally a comma and the run: `<who>[, <run>]` |
| `supersedes` | other docs this one replaces (minutes replacing a recording note): each exists, never itself, no cycle |
| `entities` | entity slugs; not checked against `entities/` until it loads (#7) |

- Path: `processed/<type>/<yyyy>/<mm>/<slug>.md` when the slug starts with a date `yyyy-mm-dd`, else
  `processed/<type>/<slug>.md` (a brief per person). It follows from the id, so finding a doc needs no scan.
- Read with YAML's base loader, so every value is text (`no`, `on` and `2026` stay slugs). Written by Docket's own
  renderer in the order above, a value double-quoted when a standard YAML reader wouldn't give it back unchanged.
- Strict on write: an unknown key or type is refused. Lenient on read: one from a newer Docket is kept with a warning,
  so an older machine still reads a newer machine's docs.
- The body is kept as written, with LF line endings and one final newline.

### Anchors

Every content line ends with its anchors. The grammar:

```
line-end  = anchor *( 1*WSP anchor ) *WSP          ; the end of a line, after whitespace or at its start
anchor    = short / record
short     = "@" times                              ; only in a doc that covers exactly one record
record    = "[r:" rid-text [ "@" times / "#" parts ] "]"
times     = time [ "-" time ]                      ; offsets from the record's start; the second not before the first
time      = 1*2DIGIT ":" 2DIGIT ":" 2DIGIT         ; h:mm:ss, minutes and seconds 00-59
          / 1*2DIGIT ":" 2DIGIT                    ; m:ss or mm:ss, seconds 00-59, minutes up to 99
parts     = number [ "-" number ]                  ; paragraphs of the record's text, from 1
number    = %x31-39 *DIGIT
rid-text  = 1*( any character but whitespace and "]" )
```

| Form | Points at | Example |
|---|---|---|
| `@mm:ss`, `@h:mm:ss`, `@a-b` | a time or a stretch of the one covered record | `@12:08`, `@1:02:15`, `@14:30-14:52` |
| `[r:<rid>@mm:ss]` | a time or a stretch of any covered record | `[r:calls:rec-0042@12:08]` |
| `[r:<rid>#n]`, `#n-m` | paragraphs n to m of a record's text, blocks split by blank lines | `[r:mail:<x1@example.invalid>#2]` |
| `[r:<rid>]` | the whole record: a message, a mail, an event | `[r:chat:C0TEST/1791000001.000100]` |

- `rid-text` is the rid with `%` written `%25` and `]` written `%5D`, and its last `@` or `#` written `%40` or `%23`
  only when the rid's own tail would read as a position. The parser splits at the last `@` or `#` whose rest is a
  whole `times` or `parts`, then decodes those four codes and nothing else. `format_anchor()` writes it, so a mail rid
  stays readable.
- Lines that need none: blank lines, headings, thematic breaks, fenced code with its fences, HTML comments, a table's
  header and separator rows. A table body row ends its last cell with its anchors. A legacy note's body isn't read for
  anchors at all.
- A trailing token that starts like an anchor (`@` and a digit, `[r:`) but doesn't parse is refused, not read as
  text; so is `[<letters>:...]` with letters other than `r`, kept for later anchor kinds.
- An anchor's rid is in `covers`, and it resolves against the record's latest version: a time inside the record's
  range, a paragraph that exists, or the record itself.
- A locator, what `read` takes: a doc id, a doc's path inside the vault, or a record part: `r:calls:rec-0042@12:08`,
  the same in brackets, or a bare rid. A bare form whose prefix is a doc type is a doc; `r:` always means raw.

How the resolver counts, the same for a doc's lines and a record's text:

| What | Rule |
|---|---|
| line ends | CRLF and a lone CR read as LF first; a line is the text between two LFs, nothing else (not `str.splitlines()`, which also splits on U+2028, `\x0c` and `\x1c` to `\x1e`) |
| a blank line | only spaces, tabs and no-break spaces (U+0020, U+0009, U+00A0); the no-break space counts because HTML mail turned to text writes empty lines with it |
| a paragraph | a run of non-blank lines; a run of blank lines is one break, and blank lines at the start and the end don't count |
| a record's time range | from the smallest `start_ms` rounded down to the second, to the greatest `end_ms` rounded up (segments overlap, so the last to start isn't always the last to end); gaps between utterances count |

### Segments

The contract every transcript meets, so anchors resolve the same way for any source:

- `Segment` (Pydantic, frozen): `start_ms`, `end_ms` (integers from the record's start, `0 <= start <= end`),
  `speaker` (text or null), `text`.
- `register_segments(source, reader)`, a reader being `Callable[[RawRecord], list[Segment]]`, the way
  `records.register_projection` works; the Plaud connector (#10) registers its own.
- `segments(record)` uses the source's reader, else the default: `native["segments"]` as a list of `{start_ms,
  end_ms, speaker?, text}`, the shape Docket's own transcripts (Whisper, phase 2) will write. No such key: no
  segments. A malformed list: a `DocketError` naming the rid, so a time anchor on it is refused with the reason.
- Segments come back sorted by start, overlaps (two people talking) kept. A reader is pure, because the index (#7)
  stores what it returns.

### doc_put

`doc_put(vault, text)` reports every problem at once, each with its line number in the text as put and the start of
that line. What the raw log decides is checked first, without the lock, since raw records are written once:

1. The frontmatter parses and passes `DocMeta`, strictly; `supersedes` doesn't name the doc itself.
2. Every rid in `covers` is in the raw log.
3. Every content line ends with anchors; every anchor parses, names a covered rid, and resolves.

What the stored docs decide is checked inside `vault.writing()`: the lock, then the recovery check, which undoes a
rebase a killed sync left and refuses while the user is in a rebase, merge, cherry-pick or revert, or on a detached
HEAD. No stored doc is read before it:

1. The stored rev is n of the last `Doc: <id> rev <n>` commit (Versions below), whether or not the file is still
   there.
2. A hand edit goes in first. When the doc file differs from what that commit wrote (edited and not committed,
   committed by hand, or auto-committed by an editor's git plugin), it is committed as `Doc: <id> rev <n+1> (edited
   by hand)`, with only its `rev` line changed and its anchors left to verify. If that commit fails, the file is
   unstaged and the user's bytes go back as they were. A file deleted by hand isn't taken in; the put below writes
   the next rev. A doc file whose frontmatter no longer parses refuses the put and names the file.
3. The rev: an id with no `Doc:` commit is new and its put carries no rev; any other id carries the stored rev, even
   when its file is gone, and any other rev is refused ("it is at rev 4 now; read it again"). So two sessions that
   read rev 2 can't both write rev 3, two new docs can't share an id, and a put made before a hand edit never
   overwrites it.
4. Every id in `supersedes` exists, and the chain has no cycle.
5. A put whose content, `rev` aside, equals the stored doc is a no-op.
6. The doc is written at the stored rev + 1 through a temp file in `.git/docket/tmp/` and `os.replace`, and committed
   through `Vault.commit` as `Doc: <id> rev <n>`. If the commit fails, `git reset -q -- <path>` unstages it and the old
   bytes go back (or the new file goes) before the error is raised, so neither the working tree nor git's index holds
   a doc git doesn't.

### Versions

A changed doc is the next revision of the same file, and git history holds every earlier one.

- That is the design's "a correction is a new version of the doc": the rev goes up, `git log -p` shows exactly what
  the correction changed, and whatever pins `(id, rev)` (`derived_from`, phase 2) can tell it is stale.
- A rev is the commit whose message has the line `Doc: <id> rev <n>`, in its subject or its body, one line per doc, so
  an import (#11) can commit many docs at once; the `rev:` line in the file is a copy for the reader. A hand commit
  that keeps `rev: 3` never makes a second rev 3, and a doc deleted by hand and rebuilt goes on from its last rev, so
  an `(id, rev)` pin always names one text.
- `read(..., rev=n)` returns the blob that commit wrote.
- `supersedes` names a different doc this one replaces, never a doc's own earlier revision.
- A new file per version was not taken: briefs and digests are rebuilt after every sync, and their folders would
  fill with stale copies that editors, grep and Claude Code's search all show.

### read and verify

| Locator | `summary` | `raw` | `both` |
|---|---|---|---|
| a doc | the doc with its lines numbered, and the docs that supersede it | every covered record in full | both |
| a record, with or without a position | the lines of current docs whose anchors point at it, near the position | the span the position points at, or the whole record | both |

- `around` (default 0) counts in the record's own unit: minutes either side of a time, paragraphs either side of a
  paragraph, messages either side in the record's thread (its container when it has none), in time order.
- `verify(vault, doc, lines=None, window=60)`: each anchored line, or the lines asked for by their file line number as
  an editor shows it, next to the spans its anchors point at. A point in time shows the segments overlapping the next
  `window` seconds, a stretch the segments overlapping it, a paragraph or a record its text.
- A span says how many versions its record has, so a reader knows when a summary may predate an edit. An anchor that
  no longer resolves (a forgotten record) comes back with its problem, never as an exception.
- Raw and doc text come back as data fields; nothing in read or verify acts on what the text says. A path locator
  that resolves outside `<vault>/processed/` is refused.
- Records are found by reading only the rid's source folder (`raw/<source>/`), once per call, until #7's index.

### The API and the command

| Python, `docket.recall` | Command |
|---|---|
| `doc_put(vault, text) -> PutResult`; `DocRefused` carries the problems | `docket doc put <file or ->`: the id, rev and path, or every problem and exit 1 |
| `read(vault, locator, view="summary", around=0, rev=None) -> ReadResult` | `docket doc read <locator> [--view] [--around] [--rev]` |
| `verify(vault, doc, lines=None, window=60) -> VerifyResult` | `docket doc verify <doc> [--line N ...] [--window S]` |

The names match the MCP tools the design lists, so #8 maps them one to one. The `doc` group sits in `cli.py` after
`vault`, apart from #5's `staging`.

- `doc put` reads its file, or stdin through `sys.stdin.buffer`, as UTF-8 bytes and drops a BOM; never the locale's
  encoding, which on Windows turns `é` into `Ã©`. Output is UTF-8 through `cli.main`'s `utf8_console()`.
- The commands print C0 and C1 control characters and DEL, other than newline and tab, escaped (`\x1b`), so raw text
  can't drive the terminal (OSC 52 sets the clipboard). The Python API returns the text unchanged.

## Doors and data

This adds one-way doors to the vault's format: docs Claude writes into users' vaults depend on them. Each becomes a
decision in `packages/docket/index.yaml` with `cost: one-way`, `proposed` until the maintainer confirms it:

| Decision | Holds |
|---|---|
| The processed doc's format (format) | the frontmatter fields and their rules, the types, the id grammar, the path rule, strict write and lenient read |
| The anchor and locator grammar (anchors) | the grammar, the rid encoding, which lines need anchors, how an anchor resolves, how lines, blank lines and paragraphs are counted |
| The transcript segment contract (segments) | `Segment` and its units, the default `native["segments"]` shape, the reader registry |
| Doc versions are revisions in git history (versions) | a rev is the commit with a `Doc: <id> rev <n>` line in its subject or body, the rev check under the lock, a hand edit taken in as a rev, `supersedes` only for another doc |

- `AGENTS.md`'s one-way doors gain these four next to DR-0019 to DR-0021.
- Existing vaults: `processed/` holds only its `.gitkeep`, so nothing migrates.
- Raw records are untouched: `segments()` reads `native` and never writes it.

   wins for its own source only; the registry is restored after each test.
2. `anchors.py`, with `test_anchors.py`: a table of valid and invalid tokens (`@0:05`, `@75:12`, `@1:02:03`, `@1:60`,

   a whole record; a time anchor on a record without segments; the latest version used and the versions counted;

5. `Vault.writing()`, `docstore.py` and `recall.doc_put`, with `test_docstore.py`: a doc accepted and committed;
   each refusal (frontmatter, a covered rid not in the log, an anchor's rid not in `covers`, a time past the end, a

   cyclic `supersedes`) and several reported at once; a no-op put makes no commit; rev 2 written and `git log` shows
   both; two stores on one vault, the second's put paused after its unlocked checks while the first commits at the

   a failed hand-edit commit leaves the user's bytes as they were and nothing staged; a doc deleted by hand: a put

## Risks

- Lookups read a source's run files on every call: slow on a year of raw until the index (#7). Accepted.
- A record gets a new version after a doc cites it (an edited message): anchors resolve against the latest, and
  verify shows the count. Accepted.
- Two machines put the same doc at the same rev before they sync: the rebase conflicts, `sync()` aborts it and keeps
  the local commits (DR-0022), and the user resolves it. Accepted: a machine processes what it harvested.
- Claude wraps a bullet, or ends a line with a full stop after its anchor: refused, with the line and the reason; the
  recall skill (#12) teaches the form. Accepted.
