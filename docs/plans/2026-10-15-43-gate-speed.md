# Keep the full gate under two minutes

## Goal

`gate full` takes 444 s on the maintainer's Windows machine; 93% of it is the tests, and half of their time is spent
waiting on git and git-lfs. Building each vault template once per run instead of once per worker, copying it wherever a
test only needs a vault, two fewer git calls per commit, a content step that scans each file once and the static steps
run beside the tests should bring `gate full` to about 85 s here on a quiet machine and about 115 s with other
branches' gates running, with every test still running on all three systems and the coverage floors unchanged. The
quiet-machine number on the maintainer's Windows machine is the one that closes #43; the loaded number and CI's times
per system are reported beside it.

- In scope:
  - the test kit (`docket_testkit.py`): templates built once per session for all workers, and copies per test;
  - the per-test builders (`folder_vault`, `host_repo`, a plain vault, convert's `nested`) copying a session template
    where the test doesn't need its own history;
  - the tests' git config: no auto maintenance, and copies that git sees as clean without hashing them again;
  - `Git.has_identity` and `Vault.uncommitted_runs`: two fewer git calls in every Docket commit, users' included;
  - the gate: the content step reading each file once, the full lane's static steps beside the tests, the slowest
    tests printed on every run;
  - the numbers before and after, in this plan, the PR and the issue.
- Out of scope:
  - Docket's own commits skipping git-lfs's post-commit hook: the biggest cost left, and a product change, filed as
    #55 for phase 1;
  - the Service install (Windows) job, 5.8 minutes, most of it a wait by design, which becomes a PR's slowest check:
    running it less often would loosen a check, so it waits for the maintainer's decision review;
  - the machine: Defender exclusions, other branches' gates running at the same time.

## Design

### What is taken

| Lever | Taken | Expected saving | Why |
|---|---|---|---|
| templates once per session, shared by every worker | yes | measured in pairs: 217 s to 142 s, and 158 s to 139 s; git calls 22,885 to 13,120 | each worker builds a module's template again today |
| per-test builders copying a session template | yes, where the test doesn't need its own history | about 3,300 git calls and 120 git-lfs installs | a copy takes 43 ms, a fresh vault 2 s |
| copies that keep their stat data, on Windows | yes | about 0.6 s on the first commit or status of every copy, the copies made today included | a copy's files are new to the file system (creation time), so git hashes `media/.gitkeep` again, which starts git-lfs's filter |
| two fewer git calls per Docket commit | yes | about 1,700 git calls, two in each of 838 commits | every user's write saves them too |
| `maintenance.auto=false` in the tests' git config | yes | about 50 ms a commit | git starts a maintenance process after each commit that never finds work in a test repo |
| the content step reading each file once | yes | 16 s of the gate's wall time | 17.9 s to 0.5 s in a trial on the real deny list |
| the full lane's static steps beside the tests | yes | about 14 s of wall time | types, secrets and the harness need neither the tests nor each other |
| the longest tests started first | no | none: tried, 142 s against 139 to 142 s | the run is bound by its total work under load, not by one test's tail; step 8 tries again once the suite is shorter |
| a different worker count | measured in the build | | `-n auto` stays unless 8 or 16 wins by a tenth |
| `gate os` on part of the suite | no | | below |
| hooks, fsmonitor or git's template folder off in the tests' git | no | none measured | the tests would stop seeing what a user's git does; git-lfs writes its hooks into any hooks path anyway |
| tests without git-lfs by default | no | three times faster on every vault operation | users have git-lfs and so do CI's runners: the tests would stop running against the filter and hooks users get |
| `--dist loadfile` | no | | one module per worker: test_convert or test_import_notes becomes the tail |
| templates cached on disk across runs | no | | a change to the vault code would be tested against a vault the old code built |
| the Service install (Windows) job only on main and on PRs that touch the service | no | about 5 minutes off a PR's wait | it loosens a check: held for the maintainer's decision review |

Expected after: the run is bound by its total work, so the wall time falls with it. Under the load of the 140 s
runs, git calls go from 13,120 to about 8,000 and the copies drop about 120 git-lfs installs, which puts the tests near
115 s and `gate full` just above them, since its other steps run beside the tests. On a quiet machine, where the suite
took 158 s before any change, about 85 s. CI, roughly: Linux's gate about 90 s, Windows' tests about 200 s, macOS's
about 110 s. Windows stays the slowest test job; #55, the git-lfs hook, is what brings it down further.

### Shared templates

- `docket_testkit.shared(factory, key, build)`: the session's root temp folder (under xdist the parent of a worker's
  base temp, which every worker shares; without xdist the base temp itself), `templates/<key>/`, and a
  `filelock.FileLock` beside it (`filelock` is already the package's dependency). The first worker to ask builds under
  the isolated git settings and writes a done marker last; the others wait and reuse it.
- `template_vault`, `index_template`, `template_with`, `template_project`, `notes_template` and `imported_template` go
  through it, keyed by their name and arguments: a builder function by its module and qualified name, a mapper dict by
  its sorted items. Their signatures stay, so every module fixture, and the new tests on the 24-redact and 31-cuts
  branches, pick it up unedited.
- A template is read-only. A manifest of every path under it (files and links, with size and modification time) is
  written beside it when it is built. Once all workers have finished, the controller (`pytest_sessionfinish` where
  `config` has no `workerinput`), or the one process without xdist, walks each template again: a path added, removed
  or changed fails the run, naming it. Caches a reader leaves (Python's `__pycache__`, SQLite's `-wal` and `-shm`)
  are left out by name. The hook lives in `packages/conftest.py`, since the controller never loads the tests' own
  `conftest.py`. Only test_index_perf and test_mapper_runner's read-only tests read a template in place;
  `test_a_mapper_linked_from_outside_is_refused` writes a folder and links, so it gets a `copy_project`.
- A failed build leaves whatever it wrote, so the next worker to ask clears the template's folder before it builds
  again, and fails with the build's own error, not "already a vault".
- Each build runs in a worker under coverage, so the lines it runs still count.

The trial: a measuring plugin outside the repo wrapped the six builders this way and ran the suite as the full lane
does, alternating with the suite as it is. Template builds went from 2,224 to 173 worker-seconds, waits included;
git calls from 22,885 to 13,120; the tests from 217 s to 142 s under load, and from 158 s to 139 s with less.

### Copies per test

| Builder | Today, per test | After |
|---|---|---|
| `empty_vault(tmp_path, config)`, new: for the `vault` fixtures of test_gate and test_holds, and test_vault's tests that call its `new_vault` only to have a vault | `Vault.init` | a copy of the session's empty vault for that config's text |
| `folder_vault(tmp_path)` | a bare origin, a host, a push, `Vault.init` | a copy |
| `host_repo(tmp_path)` | two inits, a commit, a push | a copy |
| test_convert's `nested(tmp_path)`, moved into the kit | a host, the wizard, four commits, two doc puts | a copy |

- A copy is `shutil.copytree` of the template's folder (vault, host and origin together), which keeps each file's
  modification time.
- A copy has to look clean to git without hashing again. Today it doesn't: its files are new to the file system, so
  the first status or commit in a copy hashes them again, and hashing `media/.gitkeep` starts git-lfs's filter, about
  0.6 s on Windows (632 ms against 50 ms in the template). The fix: the builder refreshes the template's index once, a
  second after its last write, so no entry is as new as the index (git hashes those again whatever the stat says),
  and sets `core.trustctime=false` in the template's own `.git/config`, which its copies carry. Tried by hand: the
  copy's first status took 18 ms with no filter. On Linux and macOS a copy's inodes differ too and it still hashes
  once; git-lfs's filter costs far less there. test_convert compares `.git/index` bytes, so a test checks that a
  status after the copy leaves them alone.
- The only absolute path a copy carries is a remote's URL. The copy sets each remote to its own path with `git remote
  set-url` (git writes a Windows path with its backslashes doubled, so a text replace would miss it), and a test
  pushes from a copy and finds the template's origin unchanged.
- Tests that check init itself keep calling `Vault.init`: test_vault's init tests, test_init_folder, test_home,
  test_folder's init cases, test_source_new. The PR lists each module's choice.

### Two fewer git calls per commit

| Today | After | Calls |
|---|---|---|
| `has_identity`: `git config user.name`, then `user.email` | `git config --get-regexp ^user\.(name\|email)$`, the last value of each key winning, as git's own precedence does | 2 to 1 |
| `uncommitted_runs`: `ls-files --others --exclude-standard -- raw`, then again with `--ignored` | `ls-files --others -- raw` with no excludes, which lists both together | 2 to 1 |

- A Docket commit goes from eleven git processes to nine, plus git-lfs's hook. Every write a user makes saves them,
  about 100 ms on Windows.
- Not batched: `_recover`'s `rev-parse --abbrev-ref HEAD` and `ls-files -u`, since one `git status --branch` would stat
  every tracked file of a large vault; and the `rev-parse HEAD` after the commit, which gives the full commit id.

### The tests' git config

| Setting | Where | Why |
|---|---|---|
| `maintenance.auto=false`, `gc.auto=0` | the global gitconfig `conftest.py` writes, from one constant that `isolated_git` and the template builders write too | git starts housekeeping after a commit, a fetch or a push, which never finds work worth doing in a test repo and, in the background, could repack a template while a test copies it |
| `core.trustctime=false` | each template's own `.git/config`, so only copies differ from a user's git | a copied file keeps its size and times, not its creation time |

`core.checkStat=minimal` would keep copies clean on Linux and macOS too, but on a git that compares sub-second times
it could hide a same-size rewrite within the second of a commit; it isn't taken. Git still compares sizes, whole and
sub-second times and, on Linux and macOS, inodes. Nothing else changes: hooks, fsmonitor, line endings and git's
template folder stay git's defaults. Pointing `core.hooksPath` at an empty folder was tried and saved nothing: `git
lfs install` wrote its hooks into it. The Plaud example's `conftest.py` stays as it is, since it is copied into users'
projects.

### The content step

- Today: 273 names times 294 files, each name a regex with a look-behind that Python can't search for quickly, 17.9 s
  here and 12.2 s in CI.
- After: each file's text is folded once the way `re.IGNORECASE` folds (the simple lowercase, plus the extra
  equivalences Python's `re` adds: dotless i, long s, the Kelvin sign); a name's regex runs only on a file holding its
  first word folded the same way. A file the fold passes over is one the regex finds nothing in, so the step reports
  exactly what it reports today, in 0.5 s.

### The gate's run

- Full lane: the tests start first in a thread; lock, ruff, format, types, docs, commits, content, secrets and harness
  run meanwhile. The lines print in the usual order once all have finished, each with its own time.
- The tests step passes `--durations=15` and prints those lines after the summary, so each CI run lists its slowest
  tests on Linux, Windows and macOS, and the issue gets Linux's from this PR's first run.

### `gate os` keeps the whole suite

The tests that cost the most are the git- and process-heavy ones, and those are the ones that differ between systems:
paths, line endings, file locks, Git for Windows. test_index_perf's time limit is checked only without a tracer, so
only `gate os` checks it. The modules that behave the same everywhere (text, time words, the YAML tools) take a few
seconds in all. Trimming would save little and drop what the job is for.

## Doors and data

None. No one-way door moves: the vault's format, what Docket commits (paths, messages, identity) and the MCP tools stay
as they are. The two batched git calls change how Docket asks git, not what it writes. No user data moves.

Nothing loosens. REVIEW.md's harness section covers the gate: every step still runs, on the same files, and the
content step reports the same hits, so these go ahead under the autonomy grant and the PR records them.

## Steps

1. The gate prints the slowest tests (`--durations=15`) in the full and os lanes. A gate test reads the printed lines
   from a stub run.
2. `shared()` and the six builders through it, with the manifest check. In `test_testkit.py`: two workers simulated
   with two processes build one template once; a builder that writes a file and then fails leaves no marker, and the
   next build runs and gives its own result; a file added to a template, one changed and one removed each fail the
   check, naming the path, while a `__pycache__` doesn't; keys differ for two builders of one name in two modules and
   for different mappers.
3. The copies: `empty_vault`, `folder_vault`, `host_repo` and `nested` through templates; each module's
   per-test fixture moved where its tests don't need their own history. Tests: a copy's remote is its own (a push
   leaves the template's origin as it was); the user's staged and unstaged work in a copied host is as the builder left
   it; `.git/index` is stable across a `git status` after the copy.
4. `has_identity` and `uncommitted_runs` in one call each. Tests: an empty `user.name`, a name only in the repo's
   config, one only in the global config, both set at two levels (the repo's wins); a run file an ignore rule hides
   still counts as uncommitted; the call count of a commit, by a patched `subprocess.run`, is nine.
5. `maintenance.auto=false` from one constant; each template's index refreshed once, a second after its last write,
   and `core.trustctime=false` in its `.git/config`. Tests: on Windows a copy's first status starts no git-lfs filter
   (`GIT_TRACE`); in a copy, a Docket commit, then the run file rewritten at the same size within that second, and
   `changed_against_head` sees it, on all three systems.
6. The content step's fold. In `test_checks.py`: the old scan and the new give the same hits over a table of texts
   (case variants, dotless i, a capital dotted İ inside a name's first word, long s, the Kelvin sign, sharp s, a name
   split across lines, a name in a path).
7. The full lane runs the static steps beside the tests; the output keeps its order. A gate test: a failing static step
   and a failing test both reported, the exit code 1.
8. Measure on a quiet machine (no other gate running) and as it usually is: `gate full`, the tests with durations and
   the counting plugin; `-n 8`, `-n 16` and `-n auto`; the longest tests started first once more. The quiet number
   decides #43; the loaded one, CI's three jobs and Linux's slowest tests from step 1 go beside it in the PR and the
   issue.
9. `finish-work`: `uv run gate full`, a draft PR, `review-code` until it is clean.

## Tests

On temp folders under pytest's own temp area and the isolation `conftest.py` sets: temp `DOCKET_CONFIG_DIR` and
`DOCKET_STATE_DIR`, the failing keyring, `DOCKET_VAULT` unset, an empty global gitconfig. Shared templates live in the
same temp area, never under `%LOCALAPPDATA%\docket`, never on the user's vault.

- New: `test_testkit.py` (the shared builder, the copies, the manifest), the git-call tests in `test_vault.py`, the
  content fold in `test_checks.py`, the gate's parallel lane and durations in `test_checks.py`.
- Changed: per-test `vault` fixtures to `empty_vault`; `nested` into the kit; test_mapper_runner's linked-mapper test
  onto a `copy_project`. test_vault's own `new_vault` keeps calling `Vault.init` for the tests about init, such as
  `test_an_init_whose_real_commit_fails_leaves_nothing`.
- No test is deleted, skipped or weakened. Coverage stays at `docket` 100% and `devkit` 79% or above.

## Risks

| Risk | Status |
|---|---|
| A test writes into a shared template and a test in another module sees it | resolved: the controller walks every template after all workers finish and fails the run, naming the path |
| A test that only reads a template leaves a cache there and fails the check | resolved: Python's and SQLite's cache files are left out of the manifest by name |
| A copy pushes into the template's origin through its remote URL | resolved: the copy sets its remotes with `git remote set-url`; a test pushes from a copy |
| A failed build leaves files, and the next worker's build fails on them | resolved: the folder is cleared before each build; a test |
| A copy's index holds the template's stat data, and the first `git status` rewrites it under a test comparing bytes | resolved: the copy matches the index on size and time; a test checks the bytes stay |
| A copy's git misses a change a user's git would see | resolved: only `core.trustctime=false` differs, in copies only; a test rewrites a file at the same size within the second of a Docket commit, on all three systems |
| A shared template hides a bug a fresh vault per test would show | accepted: each test still gets its own copy; init's own tests still init |
| A line that ran only in a per-test build stops counting | resolved: each build still runs once under coverage; the floors are the check |
| The two parallel branches add tests that build their own vaults | accepted: those using the kit's builders get copies unedited; a test calling `Vault.init` itself keeps its cost until it moves |
| The prefilter passes over a file the regex would have flagged | resolved: the fold is the one `re.IGNORECASE` applies, and a test runs both scans |
| A static step fails while the tests run, and the run takes as long as before | accepted: the gate still fails; the time lost is the tests' |
| Another branch's gate on the same machine doubles the times | accepted: the target is measured on a quiet machine, the usual load beside it |
| The target is missed without the git-lfs hook change | open: the expected 85 s on a quiet machine leaves a third in hand, 115 s under load very little; if step 8 shows more than 120 s on a quiet machine, #55 is the next lever |
