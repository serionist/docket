# Make the sync one file in and one file out

`/docket:sync` gets one folder per sync: `docket sync start` writes each agent's prompt and the ledger it needs, each
agent writes its block to a file, and `docket sync reconcile` drafts the batch from the blocks, leaving Claude only the
unsure lines. Recording notes go to agents of their own off the summary's path; `read` and `suggest` take several at
once. Three PRs; main works after each.

## Goal

- Done: a second rehearsal over the old sync's window takes no longer than the old sync and finds the same asks
  (Success, below). The launch is two short messages, an agent reads the ledger from one file, the reconcile is one
  command and two small batch calls.
- Out: the summary's own read of the ledger (not where the rehearsal's time went), scheduled syncs, a model inside the
  service, any change to a source's run (`run_open`, the capture hook, `ingest`), to the note method (#211) or to the
  block's labels.

## Design

Where the rehearsal's 36 minutes went, and what replaces each part:

| Step | Rehearsal | After |
|---|---|---|
| launch | the skill wrote `fork.md` out five times, 16k tokens | `docket sync start` writes the prompts; each `Agent` call's prompt is one line naming its file |
| an agent's ledger | the snapshot saved to a file, parsed with scripts, then `show` item by item | `context.md`: every open item one line, the meetings with their points, the streams |
| an agent's checks | a `read` per reported rid | one `read` with `more` for all of them; the reconcile drops any line whose locator doesn't open |
| notes | written one after another inside the recording agent | one background agent per recording, launched after the agents, never waited for |
| reconcile | a 45-op batch sent three times; 12 reads and 10 `suggest` calls | `docket sync reconcile` drafts the ops into a file; Claude settles the unsure lines; `ledger_batch` takes the file for the dry run and the write; one `suggest` for every prep meeting |

### Context in: the sync folder

`docket sync start [SOURCE...] --vault <vault>` makes a sync folder in Docket's state folder,
`<state>/sync/<sync id>/` (`paths.state_dir()`, as the service's pid file and `runs.json`), never in the vault and
never committed. The id is `sync-<yyyymmddThhmmss>-<8 hex>`. It works with the service down, as `docket ledger day`
does, and writes nothing else.

| File | What |
|---|---|
| `sync.json` | the sync id, the vault's root, when it was made, today, the owner's zone, the owed-since day, each source with its window, prompt and block paths, Docket's version |
| `context.md` | the sync's head line, then each source's window, the kept recordings with no note yet, the open items, the snoozed ones, the meetings, the streams |
| `agents/<source>.md` | the agent prompt from the package's `docket/sync/agent.md`, filled: `{SOURCE}`, `{VAULT}`, `{TODAY}`, `{ZONE}`, `{OWED_SINCE}`, `{CONTEXT}`, `{BLOCK}` |
| `blocks/<source>.txt` | written by the agent (Blocks out, below) |
| `notes/<slug>.md` | a note agent's prompt each, from `docket sync notes` |
| `draft.jsonl` | from `docket sync reconcile` |

- Sources: the live sources as `docket ledger day --json`'s `syncs` lists them, or the ones named; an unknown name is
  refused before anything is written, the live ones listed; a `sync_problem` is said and nothing is written.
- A window is `cursors.window` for the source with this machine's clock, as `run_open` computes it; the run's own
  answer stays the one the agent follows. Owed since is the window, or 40 working days back while the ledger holds no
  item.
- The open items and meetings come from one `views.read` snapshot whose meetings run from the earliest window's day to
  the fifth working day after today, so a recording from the window's first day and the prep week both find theirs.
- The recordings with no note are each recording source's kept recordings in its window whose transcript no current
  doc covers, by the index, so the agent checks none itself.
- The command prints the folder, then a line per agent with its prompt's absolute path. A start removes sync folders
  over 7 days old; a forget applied on a machine removes all of that machine's, since a block can quote what it
  forgets.

The launch stays one message: one `Agent` call per agent line, side by side, `subagent_type: fork` where Claude Code
offers it, else `general-purpose`, `description` "sync <source>", and the prompt the one line `Read and follow <the
prompt's absolute path>`. The skill no longer reads `fork.md`; `agent.md` and `note.md` live in the package beside
the block's parser, so the prompt and the parser always ship together.

### Blocks out

Each agent writes its block to `{BLOCK}` with the Write tool, the block and nothing else, and returns its RUN line
alone. The eleven labels stay as DR-0687 set them; three lines gain fields at their end, which the reconcile needs to
draft without guessing:

| Label | Gains, at its end |
|---|---|
| OWED | `reply / decision / task`, `<stream>` (one `context.md` lists, else `-`), `<the A- ref it continues, else ->`, `<due: YYYY-MM-DD, else ->` |
| WAITING | `<stream>`, `<the A- ref it continues, else ->`, `<due: YYYY-MM-DD, else ->` |
| INVITES | `<stream>` |

- No field holds ` | `; OUTCOME's two to four lines are joined by ` / `, and MEETINGS' and STREAMS' pairs by `; `,
  `attendees` names by `, `.
- NOTES names the note to be written: the doc id the agent chose by the id rule, the recording's rid, start, end, and
  the M- ref when its content names one of two meetings.
- The agent still reads every locator it reports and drops a line whose locator doesn't open (DR-0686); from PR 3 in
  one `read` with `more` (Batched reads, below).

### `docket sync reconcile <sync>`

It reads `sync.json`, every block file, and the ledger fresh through `ledger_tables`, then writes `draft.jsonl`
(replacing one there) and prints its report. It writes nothing else; the batch stays Claude's. A folder of another
vault is refused.

First, every locator in every line is resolved as `read` resolves it, through one index for the whole run: a line
whose locator doesn't open in raw is dropped and listed. Then the lines become ops in DR-0689's order:

| Line | Draft | Sure when | Unsure when |
|---|---|---|---|
| CLOSES | `done`, the locator in `note`, how in `outcome`; moot: `drop`, why and the locator in `note` | its A- ref is open or snoozed now | the ref names nothing; one already closed is skipped and said |
| OWED, WAITING | `log` on the item it continues, the locator in `note`; a `set` of `due` when the line's due differs from the item's | its continues ref names an open item, and a thread match, if any, names the same | the ref isn't open; the ref and a thread match disagree; two items match the thread |
| OWED, WAITING | a thread match (below) with continues `-` | never | always: the `add` first, the `log` on the matched item its alternative |
| OWED, WAITING | a look-alike: the same `who`, case aside, and DR-0642's title rule, with continues `-` | never | always: the `add` first, the `log` its alternative |
| OWED, WAITING | an ask whose locator's rid, anchor aside, is already an item's source, open or closed, as a recording reported again brings | never | always: each such item's line quoted with its state, read from the ledger, not `context.md`; Claude keeps the add or deletes the line |
| OWED, WAITING | `add`: kind (waiting for WAITING), title the ask, who, stream, source the locator, opened the day asked, due the line's due, else today for "today", else none, the why in `note` | nothing matches | the stream isn't one the ledger holds, or the kind is missing |
| the same ask twice | one op, the other locators in `note`; the report lists every merge with both block lines | the same `who`, case aside, the same side and a DR-0642 look-alike title, and the same continues ref: both lines are logs on that item anyway | the same who, side and title with no shared continues ref: the merge drafted, two adds its alternative, even on one locator, since an agent writes two lines on one message mostly because it holds two asks; the writer's look-alike check still catches a real double. Lines that differ in who, side or title stay separate ops, two asks in one mail or at one recording moment among them, and two lines either side of a CLOSES of the item they continue are never merged |
| an ask on an item a CLOSES line closes | `log` when asked before the evidence's time, `add` after (DR-0689) | the times differ | the same day with no time |
| INVITES | `add` kind invite, source the rid; titled from its meeting's subject when the rid is a calendar event's (DR-0646), else from the index's `records.title`; a `log` when an open invite has that rid | a title is found and the stream is held | no title, or the stream isn't held |
| an ask's meeting | `meeting` on the add: someone in it asked during it or up to 120 minutes after (DR-0651) | one meeting, not cancelled, not the owner's own block | two |
| MEETINGS, STREAMS | `set` of the line's fields | the meeting or stream stands | else |
| NOTES | `material` on the meeting, the recording's rid, label `recording` (DR-0651) | one meeting 10 minutes either side of the start, or the line's M- ref of two | two and no ref; none is said, with no op |
| MINUTES, OUTCOME | `point_set` by point id; `set` of `outcome`, ` / ` made line breaks | the point is open on that meeting; for OUTCOME, the meeting stands with no outcome yet | else; the point's state and answer, or the outcome already there, quoted beside it |
| always | `rollover` after the minutes, a `# prep` line for Claude's points, `archive` last | | |
| RUN, LEARNED | no op: printed | | |

- A thread is the index's `records.thread` of a locator's rid, its `r:` and anchor stripped as `store.locator_rid`
  does, else the rid itself. An open item's trail is its source, its materials' refs and the locators in its ops'
  notes, read by a new `views.trails` beside `matching` and `batch_lines`.
- A thread match counts only with the same `who`, case aside, and on the same side: an OWED line with an item the
  owner owes (reply, decision, task), a WAITING line with a waiting item. It never counts where a record's thread is
  its container, as in a Teams chat or a Plaud recording, where everyone shares one: there a line falls to its
  continues ref and the look-alike rule. A mail conversation or a Slack thread holds several people's asks, so even a
  counted match without the agent's continues ref stays unsure.
- An unsure op carries `"unsure": "<why, and the choice>"`. Above it, a `#` line quotes the block line and its
  `file:line`, and a `#` line per candidate quotes that item's `context.md` line, both where two are candidates, so
  Claude settles every unsure line from the draft alone, with no `show`. Its alternative follows as a `#` line. The
  writer already refuses a key an op doesn't take, so a line left unsettled can't be written: no new check. Claude
  settles each by taking the key out, swapping in the alternative, or deleting the line.

The draft, invented:

```
# docket sync reconcile sync-20261020T091500-1a2b3c4d: 7 ops, 1 unsure
# closes
{"op": "done", "item": "A-0001", "note": "slack:C0PILOT/1791100500.000200", "outcome": "Sent Ben the dates in the pilot channel"}
# asks
{"op": "log", "item": "A-0002", "note": "Cleo: the quote comes on Thursday: outlook:AAMkADquote2"}
# ? blocks/slack.txt:4 OWED: Dan Example | slack:C0PILOT/1791101200.000100 | 2026-10-19 11:05 | Book the room for the pilot's first day | not booked yet | this week | task | pilot | - | 2026-10-23
# ? A-0003 | task | Dan Example | Book the room for the pilot | slack:C0PILOT/1791100800.000300 @M-0002
{"op": "add", "fields": {"kind": "task", "title": "Book the room for the pilot's first day", "who": "Dan Example", "stream": "pilot", "source": "slack:C0PILOT/1791101200.000100", "opened": "2026-10-19", "due": "2026-10-23", "meeting": "M-0001"}, "unsure": "a look-alike of A-0003 by who and title: log it there if it continues that work, else keep the add"}
# {"op": "log", "item": "A-0003", "note": "Dan asked again, for the first day, by the 23rd: slack:C0PILOT/1791101200.000100"}
# meetings, links, minutes
{"op": "material", "item": "M-0001", "ref": "plaud:rec-0101", "label": "recording"}
{"op": "point_set", "item": "M-0001", "point": "01M4QJ9FZ000X93GNMW1YNY5N8", "fields": {"state": "answered", "answer": "the 28th, with Ben's team on site"}, "note": "r:plaud:rec-0101/transcript@12:08"}
{"op": "rollover"}
# prep: the next five working days: M-0002
{"op": "archive"}
```

The report it prints: the RUN lines; the draft's path, its ops and the unsure lines by number; every merge, with both
block lines; the lines dropped and why; the closes skipped; the LEARNED lines whole; the meetings of the next five
working days for prep. An item's source by rid, for any state, comes from one read of the items' sources, so the
check costs no more than the trails.

Then the skill reads the draft once, edits the unsure lines and adds the prep points at `# prep`, and calls
`ledger_batch(ops=[], file="<sync>/draft.jsonl", by="sync", dry_run=true)`, then the same without `dry_run`. A refusal
is fixed in the file and the dry run asked again; a write refused after a clean one means the ledger moved: fix the
lines it names, dry run again. Without the service, `docket ledger batch <file> --by sync --dry-run` already reads a
file. The trust model holds: the owner asked for the sync, each `ledger_batch` shows Claude Code's prompt unless they
allow it, the dry run's result lists every change in chat, and the summary names the batch to undo whole.

### Batched reads

| Tool | Gains | Rule |
|---|---|---|
| `read` | `more`, a list of locators read like `locator` in the same call | `rev` is refused with it; a locator that doesn't open is a problem of its own read, never the call's error; the text is each read under a `== <locator>` line |
| `ledger` | `refs`, several meetings for `suggest`, in order | `ref` or `refs`, not both; every other view refuses it; each item row says the meeting it is for in `suggested_for`; an item for two meetings is listed under each |

- Results gain fields only: `ReadResult.more` (the further reads) and `ReadResult.later`, `LedgerRead.later` and
  `ItemRow.suggested_for`.
- The room is 40,000 characters, counted as the text plus the structured content's JSON, under the 50,000 past which
  Claude Code saves a result to a file (`capture.SAVED_TO_FILE`). The first locator or meeting is always answered;
  each next one only while the whole still fits. The first that doesn't, and every one after it, go to `later` in
  order, and the text's last line says to ask again for them. A single read past the room is as today.
- `recall.read_many` shares one `_Call`, its index opened once; `views` answers several suggests from one `_Reader`.
  `docket ledger suggest` takes several meetings and prints them all; `docket doc read` stays one locator.

### Recording notes in parallel

- The recording agent no longer writes notes. Its scope stays `fork.md`'s and DR-0686's: after its promotion it reads
  whole, and reports from, only the work recordings its run brought and those `context.md` lists with no note yet,
  the vendor's summary and the whole transcript of each, and writes MINUTES, OUTCOME, OWED and the rest from them as
  now, with a NOTES line for each. The rest of a 7-day lookback window, reconciled by earlier syncs, isn't read again.
- After the agents, `docket sync notes <sync>` writes a prompt per note from the NOTES lines, two lines with one doc id
  making one note over both recordings, from the package's `note.md`: #211's method as `fork.md` has it today (both
  views read whole, context searched, every line anchored, the layout from the source's `sync.md`, a read of the
  summary view just before `doc_put`, `verify` of every number, date and commitment). A NOTES line whose recording
  doesn't open gets no prompt and is said.
- The skill launches one `general-purpose` agent per prompt, all in one message, before the reconcile wherever an
  Agent call doesn't hold up the main thread, as Claude Code runs every subagent in the background today; only where
  a call does, after the summary. Each returns one line: the doc id put and its rev, or why not.
- The summary doesn't wait: no op in the batch names a note, since the link is the recording's rid (DR-0651) and the
  minutes come from the recording agent's own reading. The skill says how many notes are still being written, and
  their outcome as they finish. A note that fails leaves its recording without one, which the next sync's recording
  agent reports again.
- Not the recording agent launching them itself: not every Claude Code gives a subagent the Agent tool, and the skill's
  own session is the one sure to outlive them.

### The continuing-work rule

It lives in the plugin's `sync/SKILL.md`, as a general rule: an ask that continues an open item's work (the same
person, and the same thread or the same topic) is a `log` on that item, never a new item; a new item is a new piece
of work. The agent names the item in OWED's continues field; Claude applies the rule when settling an unsure line. The
skill's examples use invented people; an owner's own cases go in their project's `CLAUDE.md` or a source's `sync.md`.
