# Make a redaction rule turned on never split another's match

## Goal

Turning a redaction rule on, or adding a pattern, only ever redacts more. Today each rule reads only the text between
the markers earlier rules left, so an earlier rule cuts a later rule's match and the rest is stored. Probed on main
(ce41a97), invented data:

| Text | Rules on | Stored |
|---|---|---|
| `ticket TCK-123456 is open` | `tck-id` = `TCK-\d{6}` | `ticket [redacted:tck-id] is open` |
| | and `tck` = `TCK`, listed first | `ticket [redacted:tck]-123456 is open` |
| `Dial-in: +1 555 010 0199 PIN 482913#` | `dial-in` = `Dial-in: \+[\d ]+ PIN \d+` | `[redacted:dial-in]#` |
| | and phone, a built-in, which runs first | `Dial-in: [redacted:phone] PIN 482913#` |
| `use postgres://ada:<password>@db7.example.invalid/orders today` | `dsn` = `postgres://\S+`, credentials off | `use [redacted:dsn] today` |
| | and credentials, the default | `use [redacted:dsn][redacted:password]@db7.example.invalid/orders today` |

- `loosens()` calls each of these stricter, so `docket redaction set <name> on`, the Settings page (#145) and, after
  #134, an edit not committed yet all expose the rest. Credentials are on by default, so a pattern that holds a
  credential never matches whole today.
- The guarantee: every character any enabled rule matches on the text as given is redacted, whatever the order, so
  turning a rule on never unredacts one of them. A match a rule finds only at another rule's marker is outside it
  (Risks).
- In scope: `Redactor.text` and `Redactor.segment_texts` in `vault/redact.py`, which every caller goes through (the
  gate, docs line by line, entities, the scan, the staging view); the marker a merged span gets; redacting twice; what
  stored records get.
- Out of scope: fragments a split already stored (they stay, see Doors and data); the never-store screen (#146, merged
  as #148); `derived.py`, which doesn't change.

## Design

Every enabled rule matches the same text, the text as given, and what any rule matches there is redacted whole.

| Step | What `Redactor` does |
|---|---|
| find | every pattern of every rule runs over the text between the markers already in it, as today, never between markers this call adds; a match gives its secret groups or itself, as today |
| merge | spans that overlap (nested, crossing or the same) become one; spans that only touch stay two |
| name | a merged span takes the marker of the rule with the longest span in it; a tie goes to the rule that comes first: private-key, api-key, password, phone, then the patterns in vault.yaml's order |
| repeat | the rules run again on the gaps between the spans, each gap as its own text, as a second redaction reads them; until a pass finds nothing, at most 4 passes |

- `Redactor.spans(text)` gives the merged spans in the text's own offsets with their rule; `text()` writes the markers
  and counts one per marker. `Rule.apply` and `Rule.replace` go.
- Segments and doc lines: `segment_texts` matches the segments joined by line breaks, as today. A merged span over a
  boundary takes each segment it touches whole, under its marker, as one match does today, and the next pass reads
  those segments as markers. Spans stay in the joined text's offsets and boundaries are found by bisect, so the
  shifting bookkeeping goes. `derived.redact` keeps its line count and its anchors, split off before and put back
  byte for byte.
- Text where no two rules' matches overlap, and no match depends on another rule's marker, redacts as today. A
  scratch copy of this design patched into the 26 test files that touch redaction: all 1,038 tests passed unchanged.
- Without an overlap, output changes only where a match depends on a marker (a `\b`, an anchor or a lookbehind at
  it), and both ways:
  - found now: a match an earlier rule's marker cut off from what it looks at (`https://<token>:x-oauth-basic@host`
    hides the part after the token too), and one only a second redaction finds today (next bullet);
  - lost now: one today finds only after an earlier rule's marker, when the first pass puts another rule's span there:
    `TCKX4821` under `TCK`, `\bX\d{4}` and `X48` stores `[redacted:tck][redacted:code]` today and
    `[redacted:tck][redacted:x48]21` after.
- Redacting twice is once, as DR-0190 says; today it isn't. With `\bcode\b` listed before `X`, `see Xcode now` becomes
  `see [redacted:x]code now`, and redacted again `see [redacted:x][redacted:code] now`. Intake redacts once and
  promotion twice, so raw holds a version intake never computes, and the gate stages the record again on every sync:
  probed on a temp vault, three syncs, each ready 1 and written 0. With the repeat it is skipped from the second sync.
- The cap: `\b[0-9a-f]{8}` after a marker finds 8 more characters a pass, so 16 KB of hex took 1.1 s uncapped. 4
  passes bound the cost at 4 times today's. Text with no match runs one pass, text with matches two: 149 ms against
  today's 81 on 5,000 lines with a match each.

| Not taken | Why |
|---|---|
| rules in order, a rule turned on moved last | a rule placed later still splits what runs before it, and a pattern still runs after credentials |
| one pass, no repeat | breaks a case today gets right: `TCK` and `\b\d{6}\b` give `[redacted:tck]123456`, and the record is staged again every sync |
| today's output plus the union | a rule turned on can still take away a match an earlier marker made |
| the first rule names a merged span | turning `tck` on renames every stored `[redacted:tck-id]`: a new version of each record, nothing more redacted |
| a marker naming both, `[redacted:tck+tck-id]` | the marker is one name (DR-0190, DR-0198), and `MARKER` and the counts read it |
| touching spans merged | changes text where nothing overlaps: `x[redacted:a][redacted:b]x` today |

### Decided

Recorded as `proposed` for the maintainer's review.

| Decided | Entry |
|---|---|
| every rule reads the same text; overlapping spans merge; the gaps are read again, at most 4 passes; the guarantee covers what a rule matches on the text as given | DR-0525 |
| a merged span is named by its longest span's rule, a tie by rule order; touching spans stay two | DR-0526 |
| no migration; a changed output is a new version when sent again, as DR-0191; split fragments already stored stay | DR-0527 |

## Doors and data

No one-way door changes. The marker stays `[redacted:<rule>]` (DR-0190, DR-0198), vault.yaml and its redaction keys
(DR-0192) as they are, and so does `loosens()`: its list (DR-0506) now holds for every character a rule matches on the
text as given, which a rule turned on never unredacts.

What stored data gets (DR-0527):

- The output changes only where two enabled rules' matches overlap, or a match depends on a marker (above). In the
  defaults the built-ins nest (a key block holding a password: the block, as today) or match the same span (a token
  after `password:`: api-key, as today).
- raw: a record sent again whose redacted form changed lands as a new version, as turning phone on does (DR-0191);
  mixed and cut ones wait in staging again. Older versions keep what they stored.
- A rule turned on whose matches all sit inside another's makes no new version: turning `tck` on keeps
  `[redacted:tck-id]`.
- docs: the next put, the notes import and `docket doc redact` redact the new way, but a split already stored can't be
  joined again: `[redacted:tck]-123456` keeps `-123456`, since `TCK` is gone. The CHANGELOG line says how to find it.
- `docket scan`: a document whose redacted text changes is a new version at the next scan.
- No schema version, no migration.

- The coverage property holds only for matches on the text as given: with phone and `x` on, `x+36301234567` stores
  `[redacted:x][redacted:phone]`, and with `\d{3}` turned on too `[redacted:x]+[redacted:d3]...67`, since the phone
  match needs `x`'s marker before its `+`.
- Coverage stays at the `docket` floor of 100%.

## Risks

| Risk | Status |
|---|---|
| A match a rule finds only at another rule's marker (a `\b`, `^` or lookbehind there; the built-in phone rule's lookbehind before `+` and the labels' before a word are two) comes from the repeat, and can go: turning `\d{3}` on beside `x` and phone turns `[redacted:x][redacted:phone]` for `x+36301234567` into `[redacted:x]+[redacted:d3]...67`; and with the same settings `TCKX4821` under `TCK`, `\bX\d{4}` and `X48` keeps `21` that today hides | accepted: today has this class too, in other places; every character a rule matches on the text as given stays redacted, which the property test holds |
| A chain of such matches past 4 passes isn't redacted whole, so redacting it again finds more and the record is staged again each sync, as today | accepted: it takes a pattern like `\b[0-9a-f]{8}` and a long run after a marker; `test_a_chain_past_the_cap_stops_at_four_passes` pins it |
| Records whose rules overlap get a new version when sent again; mixed ones wait in staging again | accepted, as DR-0191: once per vault, and it is the fix |
| Fragments a split already stored stay in raw, docs and git history | accepted: raw is written once; the CHANGELOG line says how to find them and fix the docs |
| Text with a match costs about twice today's redaction | accepted: 149 ms against 81 on 5,000 such lines; one pass where nothing matches |
| #134 depends on this: its uncommitted edits count a pattern turned on as stricter | resolved by order: #147 lands first, and #134's builder then drops its rule that a new pattern runs last until committed, and its placement check |
| #146, merged as #148, changed `derived.py` and its tests | resolved: this change leaves them alone; the rebase onto 92cba8b had no conflict |
