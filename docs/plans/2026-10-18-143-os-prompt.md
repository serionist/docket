# Ask for an OS prompt before a release or a loosening

The owner's yes becomes the system's own prompt (Windows Hello; Touch ID, the watch or the login password; polkit)
wherever the machine has one set up, through one call in `docket/console.py`. The code typed back stays where none
is, or where a marker only an admin or root can make says so. The console's refusals stay first, and once a prompt
is set up nothing else falls back to the code.

## Goal

| Part | The issue's "done when" | This plan |
|---|---|---|
| One call | one `docket.console` call asks for the prompt, and the release and the loosening both use it | `console.confirm`, in place of `typed_back` at every caller; confirm-cuts and the key export use it too (Which steps ask, below) |
| Three systems | it works on all three, with the console code as the fallback where no prompt is set up | Windows Hello through ctypes, LocalAuthentication through rubicon-objc, polkit through `pkcheck`; the code only where the system reports none set up and an owner process couldn't have caused it, or where the marker says so |
| Tests | the fallback on each system, and the prompt where CI can fake it | each system's answers with its calls faked, on every runner; the real availability check in CI on each system; the marker's checks; the real polkit path in Linux CI, with a rule that answers |

- In scope: `docket/osprompt/`, `console.confirm`, its four callers, the marker, a line in `docket vault status`, the
  polkit action file, the docs, the CI steps.
- Out of scope:
  - the console's refusals (`CLAUDECODE`, a pipe or a redirect): unchanged;
  - minting a browser session, the key import, `models install --api` and `models key`: no prompt (DR-0575);
  - a yes that Docket's own code can't be tampered with around: nothing running as the owner can promise it (What
    it stops, below);
  - the release line's and the commits' format: unchanged.

## Design

### The call

`console.confirm(act, lines, do, keep, kept)` is the one question (DR-0572):

| Step | A prompt set up | None set up, or the marker |
|---|---|---|
| refused | `CLAUDECODE` set, or no console on stdin and stdout, as today | the same |
| the screen | shown | shown |
| the console asks | `Press Enter to <do> with Windows Hello, n to <keep>, q to stop:` | `the console code: <why>`, then `Type ABCD to <do>, n to <keep>, q to stop:` |
| the yes | the prompt's verified answer | the code typed back |
| a cancel, a failure, no desktop, Ctrl+C, 2 minutes with no answer | a no that names why; never the code | - |

- The prompt shows the act's own line, such as `Docket: release a held recording`, and never a value from the vault.
- Asked outside the vault lock, as the code is (DR-0519). One prompt per question: a release of five recordings asks
  five times.
- `typed_back` stays as the branch without a prompt, and `asker` stays for the reference source's copied tests.

### The three systems

`docket/osprompt/` finds a prompt without showing anything, and asks it (DR-0573):

| System | Set up when | Asks with | Dependency |
|---|---|---|---|
| Windows 10 1709 and later | `CheckAvailabilityAsync` answers `Available` | `IUserConsentVerifierInterop.RequestVerificationForWindowAsync`, the desktop's form, anchored to Docket's own window | none: ctypes into `combase.dll`, the IIDs from the SDK's headers |
| macOS | `canEvaluatePolicy` with `LAPolicyDeviceOwnerAuthentication` | `evaluatePolicy`: Touch ID, an Apple Watch or the login password, a fresh context each time | `rubicon-objc` 0.5.7: BSD-3-Clause, pure Python, 64 KB, no dependencies, macOS only |
| Linux | Docket's action file is in polkit's actions folders, and `/usr/bin/pkcheck` exists | `/usr/bin/pkcheck --process <pid,start-time,uid> --allow-user-interaction --enable-internal-agent`: the desktop's agent, or with none a text agent at the console | none: polkit's own `pkcheck`, by its absolute path |

Windows:

- The dialog's owner is an invisible top-level window Docket makes with `CreateWindowEx` and places over the
  console's window, never Windows Terminal's own window. Docket pumps its messages while it polls the
  `IAsyncOperation` through `IAsyncInfo`, on a worker thread with its own `RoInitialize`.
- `Close` is called on every async object, and every interface is released, on the success, error and timeout paths.
- Every DLL it calls (`combase`, `tbs`, `winbio`, `user32`, `advapi32`, `shell32`) loads from System32 only, through
  `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_SYSTEM32` (ctypes' `winmode`), never from Python's own folder, as Linux
  runs `/usr/bin/pkcheck` by its absolute path.
- The hardware test compares this window with Windows Terminal's (or the foreground) window, under Windows Terminal
  and conhost. If Docket's own window doesn't bring the dialog to the front under both, the Windows backend doesn't
  ship and Windows stays on the code, decided before merge, not at run time.
- Face recognition is accepted: it proves the owner is there, not that they agreed. The README's table says so, and
  advises a fingerprint or the PIN, or face turned off, for an owner who wants consent.

macOS answers:

| Answer | Means |
|---|---|
| success | a yes |
| `userCancel` (-2), `systemCancel` (-4), `appCancel` (-9, Docket's own timeout), `authenticationFailed` (-1) | a no |
| `notInteractive` (-1004) | a no: run it at the Mac |
| anything else: `invalidContext` (-10), the private -1000 range such as -1007 "Caller is not Apple signed" (seen on a macOS 27 beta) | this caller can't use LocalAuthentication: refused, and the refusal names the marker as the way out. One branch: no second route to the code |

Linux:

- One action, `io.github.serionist.docket.confirm`, `auth_self` for any, inactive and active sessions; never
  `auth_self_keep`, which passes again for five minutes. Its message is fixed in the file ("Confirm the step Docket
  shows in your terminal"), as polkit refuses a message from a caller that isn't root.
- The file ships in the package, and `docket vault status` prints `sudo install -m 0644 <file>
  /usr/share/polkit-1/actions/`.

Not chosen:

- pywinrt: a runtime and a package per namespace, and no interop interface for a desktop process.
- CredUI (`CredUIPromptForWindowsCredentials`): it offers face too, hands the PIN or password to Docket's own
  process, where a process running as the owner reads it, and leaves Docket to check what comes back.
- pyobjc (several MB, compiled); a Swift or C helper (a build per system, signing on macOS).
- polkit over D-Bus with jeepney: no text agent, so nothing asks over SSH. pkexec's own action: it asks for an admin
  and says a program runs as root. One action per act: each new act would need the file installed again.

### Fallback, and the one exit

The marker is looked for first, then the system decides, at each question (DR-0574):

| System | The prompt | The code | Refused |
|---|---|---|---|
| Windows | `Available` | `DisabledByPolicy`, which only an admin sets; no interop interface; `NotConfiguredForUser` or `DeviceNotPresent` on a machine with neither a TPM nor a biometric device | `NotConfiguredForUser` or `DeviceNotPresent` on a machine with either: "set up Windows Hello, or see the README for the console code"; `DeviceBusy`, any error |
| macOS | `canEvaluatePolicy` true | `passcodeNotSet` | anything else, naming the marker; rubicon-objc not loading, since removing it must not give the code |
| Linux | the action file and `pkcheck` there | either missing | - |
| any | - | a marker that counts | - |

Why Windows asks about the hardware: Microsoft documents `certutil -DeleteHelloContainer` as deleting the current
user's Hello container, likely without elevation. Mapping `NotConfiguredForUser` to the code would let a process
running as the owner run it, then type the code through its own pseudo-terminal: the route #143 ends.

| Detection | Call, unelevated | What an owner process can do to it |
|---|---|---|
| a TPM | `Tbsi_GetDeviceInfo` (`tbs.dll`) | nothing short of an admin: turning the TPM off or clearing it takes elevation or the firmware |
| a fingerprint or face unit | `WinBioEnumBiometricUnits` (`winbio.dll`), fingerprint and facial features | nothing short of an admin: disabling the device or stopping the biometric service takes elevation |
| either call fails | counts as a device | breaking the call refuses, never gives the code |

The marker, the one exit an agent can't reach without root or elevation:

| System | Path | Made with |
|---|---|---|
| Windows | `Docket\console-code` under ProgramData, the folder `SHGetKnownFolderPath(FOLDERID_ProgramData)` gives, never `%ProgramData%` | an elevated shell, so UAC's secure desktop puts the step in front of the owner. The README's lines remove and remake a `Docket` folder the Administrators don't own, make it, take Users' inherited create right off it with `icacls`, and make the file |
| macOS | `/Library/Application Support/Docket/console-code` | `sudo mkdir -p` and `sudo touch` |
| Linux | `/etc/docket/console-code` | `sudo mkdir -p` and `sudo touch` |

It counts only when no process of the owner's could have put it there or can replace it. The question is whether an
entry on the path can be replaced, not whether the owner can add beside it: stock `C:\` and `C:\ProgramData` let
users make folders, and neither lets them replace these.

| Check, for each entry from the drive or `/` down to the file | Windows | macOS, Linux |
|---|---|---|
| its owner | Administrators, SYSTEM or TrustedInstaller | root |
| it can't be replaced | the owner's token lacks `DELETE`, `WRITE_DAC` and `WRITE_OWNER` on it, and `FILE_DELETE_CHILD` on its folder | its folder isn't writable by the owner, unless sticky; root owns it, so no `chmod` |
| the marker's own folder | no right to add a file either (the `icacls` line) | not writable by the owner |
| links | no reparse point on the path; the file has one link | no symlink on the path; the file has one link |
| judged by | `AccessCheck` against the owner's token, the linked unelevated one when Docket runs elevated | `access(2)`, so ACLs count |

- Never by reading ACL entries by hand: groups, inheritance, deny entries and UAC's filtering are `AccessCheck`'s.
- With UAC off, or as root, every process of the owner is an admin: only the owner and link checks apply, the root
  floor.
- A user can make `C:\ProgramData\Docket` first, as `CREATOR OWNER` lets them. It fails the owner check, `docket vault
  status` names that check, and the README's lines remake it.
- Removed the same way, with sudo or elevated; `docket vault status` names the marker, or the check it failed.
- Once a prompt is set up and no marker counts, the code is never asked: a failed prompt is a no, and the owner runs
  the command at the machine. Over SSH on Linux, `pkcheck`'s text agent asks the password at the console.
- No flag, variable, config key or token picks the code: whatever an owner's switch reads, an agent running as the
  owner flips (DR-0520).
- Root is the floor, named in the README: passwordless sudo, UAC set to never notify, or a UAC bypass when the owner
  is an admin, makes the marker or removes the factor.

### Which steps ask

| Step | Asks the prompt | Why |
|---|---|---|
| `docket hold release` | yes | DR-0202 |
| a loosening through `rewrite`: `redaction set off`, `source new`, `media host add`, `media folder add`, `models allow` | yes | DR-0517 |
| `docket media confirm-cuts` | yes | it lets in for good audio an old private classification may have kept out (DR-0561) |
| `docket media keys export` | yes, before the file is written; the last four letters are still typed back after | every key leaves the clone (DR-0550) |
| `docket media keys import` | no: console only | the passphrase is the factor; no key leaves, nothing reaches git |
| `models install --api`, `models key` | no: console only (DR-0539) | nothing is sent until the vault allows it, and that asks |
| minting a session (`POST /api/session`, `docket open`) | no | below |

Minting a session stays DR-0564's floor (DR-0575):

- a session can't release or loosen (DR-0382, DR-0506); the one thing a session adds over the token and the CLI is a
  decision's click, which lets nothing in, as Staging's and Curate's writes are in the CLI already; and the token
  already reads everything over MCP;
- the route is the service's, with no console or window of the owner's to anchor a prompt;
- `docket open` runs many times a day, and a prompt each time teaches a yes without reading;
- a browser agent works in the owner's own signed-in browser, so it needs no session minted.

### What it stops, and what it doesn't

The prompt says a person answered, not that Docket's code is intact. On every system a process running as the owner
can still patch Docket, or import it and call the internals: the floor DR-0202 accepts. What ends is the common way
round the console check, a pseudo-terminal of the agent's own with `CLAUDECODE` cleared, reading the code and typing
it back.

| System | What a process running as the owner can still do | Human-only |
|---|---|---|
| Windows | start the prompt while the owner faces the camera, where face recognition may pass with no act; type into the PIN box, or log the PIN, if the dialog takes same-user input; delete the Hello container, which now refuses instead of giving the code; with an admin owner and UAC that doesn't ask, or a UAC bypass, make the marker | a fingerprint, yes; the PIN, only if the dialog's input is isolated (the hardware test); face is presence, not consent (accepted) |
| macOS | send keystrokes into the password dialog, if its terminal has Accessibility and the dialog takes them, and only with the password known; with passwordless sudo, make the marker | Touch ID and the watch, yes; the password, yes unless the process knows it |
| Linux | on X11, read or inject keys in the agent's dialog; register an agent of its own, which still needs the password PAM checks; with passwordless sudo, add a rule that says yes, remove the file or make the marker | a fingerprint, yes; the password on Wayland or at the console, yes unless known; on X11, no |

## Doors and data

- Two one-way doors change, both made stricter: the release's yes (DR-0202) and the gate's loosening (DR-0517).
  AGENTS.md's lines read "with the OS prompt, or a code typed back where the machine has none", and the PR's title
  names them.
- Stored data: none. The release line keeps its keys, and the commits keep `confirmed at the console`.
- Two new contracts with what owners make outside Docket, both kept so that one made once keeps working: the polkit
  action's id and defaults under `/usr/share` (DR-0573), and the marker's three paths (DR-0574).
- Existing vaults need nothing: a machine with Hello asks it at its next release. A Windows machine with a TPM and no
  Hello now refuses until the owner sets up Hello or makes the marker; `CHANGELOG.md` says so.

## Steps

1. `docket/osprompt/`: `find() -> Prompt | NoPrompt | Refusal`, `Prompt.ask(line) -> Verified | Refused`, one
   backend per system, each system call behind one function; Windows' TPM and biometric detection. Test:
   `test_osprompt.py`, each system's answers with the calls faked, on every runner.
2. The marker: its path per system (ProgramData from the known-folder call) and its checks (each entry's owner, that
   the owner can't replace it, the marker folder's add-file right, links and reparse points), judged by `AccessCheck`
   or `access(2)`. Test: `test_osprompt_marker.py`, with the file system's and the token's answers faked per system.
3. `console.confirm`; the conftest gains an autouse fixture that makes `osprompt.find` answer no prompt, and the
   `owner` fixture stands in for the prompt too. Test: `test_console.py`'s new cases.
4. The four callers move to `confirm`, and the export gains it. Tests: `test_release.py`,
   `test_console_question.py`, the confirm-cuts tests and `test_media_backup.py`, each with a prompt that verifies and
   one that cancels; `test_settings_scan.py`'s importers.
5. The polkit file as package data, and `docket vault status`'s line. Test: the status line per answer, in
   `test_cli.py`.
6. CI: the real availability and detection calls on each runner, the marker made with sudo on Linux and elevated on
   Windows, and the real `pkcheck` path in the Linux job. Test: the `osprompt`-marked tests.
7. The docs (Docs, below).
8. The hardware checks with the maintainer (Tests, below), their results recorded in the plan.
