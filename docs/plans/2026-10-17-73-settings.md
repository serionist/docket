# Add the Settings page: sources, never-store lists, redaction, models

The page shows every setting the gate obeys and makes only the changes on one short list, all of which keep more out;
every other `vault.yaml` change is named, never made, with its command or its line (DR-0506).

## Goal

| Part | The issue's "done when" (amended in review) | This plan |
|---|---|---|
| Sources | each source's settings shown; the stricter changes made here, the rest named | sensitivity, on or off, tools, the mapper and whether the runner takes it, media hosts, and a folder source's folder, this machine's folder and exclude; made mixed or private, or turned off, in the page; the rest as its line |
| Lists | the never-store people, containers and keywords | counts, values on request; a value added in the page after a view naming what it drops; a value taken off by hand, its line named |
| Redaction | each rule and pattern shown with the warnings `docket redaction set` prints; turned on here, the rest named | turned on in the page; turned off with the command shown; a pattern added, changed or removed by hand, its block shown |
| Models | the embedding and reranker provider per machine | this machine's provider, embedder, reranker and its timing, the environments, the service's worker and the vectors; install, remove and the `models` block as commands and lines |
| Writes | a hand-edited `vault.yaml` is never rewritten | the CLI's rule, through one writer the CLI shares; a page older than the file is refused |

- In scope: `/settings` and three post routes; a `vault.yaml` writer the CLI and the page share, with `loosens()`;
  what the gate's sweep would drop, and what a value reaches in the index; the models' status as data; the door; tests
  over HTTP and in a browser at desktop and phone width.
- Out of scope:
  - the Claude API key and a spend cap the design's table lists: no such feature yet;
  - adding a source, a folder source too: a loosening, named with `docket source new`;
  - the API provider's opt-in (#89);
  - any write to the user's `config.yaml`;
  - the owner, languages, time zone and primary machine, beyond naming the primary machine;
  - a console check on the CLI's own loosening commands: #134.

### What the page writes, and what it only names

Pages make only the changes in the first three rows; every other `vault.yaml` change is named, so a key added later is
named too until a decision moves it up.

| Change | What it does | The page |
|---|---|---|
| a redaction rule or one of the user's patterns turned on | keeps more out | makes it, then names `docket doc redact` for the docs already stored |
| a never-store value added | keeps more out; drops what waits in staging that matches | makes it, after a view naming what it drops |
| a source made stricter (work to mixed to private), or turned off | keeps more out; private drops what waits from it | makes it; private after a view naming what it drops |
| a rule or a pattern turned off | lets more in | `docket redaction set <rule> off`, with the warning it prints |
| a pattern added, changed or removed | either | the block or the line, by hand |
| a never-store value taken off | lets more in | the line to delete, by hand |
| a source added, made looser or turned on; its tools, mapper, media hosts, folder or exclude | lets more in, or changes what the service runs or fetches | `docket source new`, or the line, by hand |
| anything else in `vault.yaml` (owner, storage, primary machine, a new key) | not the page's | the line, by hand |
| models installed or removed; the `models` block | this machine only | the command or the line |

A change outside the first three rows is a loosening, a term the glossary gains (Docs).

### Why loosening is never in a page

A typed confirmation stops no agent, as the Staging plan found for the release. Claude reaches a session through
`docket open` or the token (DR-0152), and Claude in Chrome or Playwright reads and types whatever the page asks.

| Option | What stops Claude loosening through the page | Verdict |
|---|---|---|
| the change behind a typed confirmation | nothing: a browser agent reads the prompt and types it | no |
| a code in a desktop notification, typed in the page | as for the release (DR-0382): a shell reads the notification history; nothing shows on a headless session | no |
| the page names the command or the line | the command runs in Claude Code's shell, where the user's prompts and allow rules see it; a `vault.yaml` edit shows as a diff | **yes** |
| an OS prompt (Windows Hello, Touch ID, polkit) | a human-only factor | later, with the release's |

- Not a wall: Claude can still edit `vault.yaml` or run `docket redaction set` in its shell; #134 gives the CLI's
  loosening commands the release's console check. The door shuts the one path that skips Claude Code's prompts, as
  DR-0202 does for releases.
- Stricter writes ask no agent anything more, as Staging's classify and drop don't (the owner's call on #71); the
  confirm views below guard a slip.

### How the door is held

Two checks, so a missed route check can't loosen.

- `loosens(before, after)` in `vault/settings.py`, an allowlist: it is False only when every difference between the two
  configs is a never-store value added, `credentials` or `phone` turned on, a pattern's `enabled` turned on with
  nothing else of it changed, a source's sensitivity made stricter, or a source turned off. Anything else loosens,
  a source added or removed and a new key included. Every write with `via="page"` passes it, inside the writer.
  It copies `before`'s value back only for those fields and then compares whole models, so a key added later
  anywhere, at the top or inside a list, a rule, a pattern or a source, counts as a change.
- A scan over the whole package, as `test_release.py` scans for the release's writers:

| Call or import | Only in |
|---|---|
| `write_config` | `vault/settings.py` |
| the writer's general entry, `settings.rewrite` | `vault/settings.py`, `vault/redaction.py` (`set_rule`), `sources/scaffold.py` (`_register`) |
| `redaction.set_rule`, `scaffold.new_source`, `scaffold.new_folder_source` | `cli.py` |
| `docket.vault.settings` from `docket.web` and `docket.service` | the stricter operations and the read-only helpers, by name |
| in `docket.web` and `docket.service`: a settings object dumped whole (`.dump()`), or a file written in code that names `CONFIG_FILE` or `vault.yaml` | nowhere |

### Writes

Each write is one call of `vault/settings.py`, the `vault.yaml` writer the CLI shares, run on the writer thread.

| Check | What |
|---|---|
| the Guard | Host, the Strict session cookie, Origin or Sec-Fetch-Site from this origin (DR-0152); the page sends `Referrer-Policy: same-origin`, so a same-origin post never carries `Origin: null` (DR-0381) |
| the form | a plain urlencoded post, at most 64 KB, read with `read_form` and checked before the writer runs; a 303 to the page with `done` when written |
| the file the page showed | each form carries the sha256 of `vault.yaml` as the page read it; under the lock another hash writes nothing and answers 409 with the page as the file stands |
| Docket's form | rewritten only when its text is what Docket writes for it, the old redaction form included (`written_by_docket`); otherwise nothing is written and the answer shows the line, as the CLI prints it |
| the change | built with the schema, read back through `VaultConfig.load`, and held to `loosens()` |
| a change not committed | a `vault.yaml` that differs from HEAD but is still in Docket's form is committed on its own first, `Config: vault.yaml as edited`, so each commit says what it did; the CLI's writes do the same, which `CHANGELOG.md` says |
| the commit | `write_config`'s temp file and rename, then one commit of `vault.yaml`, `Config: <what>` with `via page` in the body; a failure puts the file back |
| after it | the gate's sweep on the writer thread, so what the change now forbids leaves staging at once |

- `GET /settings` writes nothing and reads beside the writer: `vault.yaml`, `config.yaml`, the mapper checks, the
  models' facts, the index's counts.
- When the file isn't in Docket's form the page says so at the top, and every change shows its line instead of a
  button, so no click ends in a refusal.
- Every line to paste is built with `yaml.safe_dump`, as `scaffold.block` builds a source's entry, so a value such as
  `Project: Phoenix` or `Dora #2` stays one value when pasted.
- The done notice says the change is committed, and how other machines get it: `docket sync`, or the user's own push
  for a folder vault.
- Without JavaScript every form posts; there is no htmx-only path. Back never shows a value in the address bar, and a
  resubmitted post writes nothing (Never-store values).

### Never-store values

A value typed into the page lands in `vault.yaml` and nowhere else Docket writes (DR-0508).

| Where | What happens |
|---|---|
| the URL and the browser's history | the value travels only in a post's body; the confirm view is that post's own answer, never a URL; the 303 after the add carries `done=listed-people-1` |
| the browser's form memory | the field has `autocomplete="off"`, `spellcheck="false"`, `autocapitalize="off"` and `autocorrect="off"`: no form history, and no spell check that sends words away (Chrome's enhanced spell check) |
| the log | route templates only, never a body (DR-0155); an error renders in the page, and the log gets its type and frames |
| the commit | `Config: never-store people, 1 added`; the value is in `vault.yaml`'s diff, as every entry is (DR-0021) |
| the page | values only with `show=lists`, so a page read for its sources carries none; autoescaped, `dir="auto"` |
| the CLI | no `docket never-store add <value>`: a value on a command line lands in the shell's history |

- The add form says what an add commits: the value in `vault.yaml`, in the repo's history, pushed wherever the vault
  goes. That is where every machine reads it (DR-0021).
- Each value is checked: not empty, at most 200 characters, no control characters.
- A value already on its list, as the matcher folds it, is a no-op: nothing written, the same 303. So a resubmitted
  confirm post, or the back button and a second click, writes nothing.
- Taking one off: with `show=lists`, each value has its line to delete and what that lets in: records it kept out are
  stored from the next sync; what it dropped before stays dropped.

### Confirm views

A change that drops something asks once more and names what (DR-0509). It guards a slip, not an agent.

| Change | The view names |
|---|---|
| a never-store value | the staged records it drops now; the records and chunks already stored that hold it, which stay in raw until `docket forget` (phase 2); docs that say it stay, and a later put of one is refused |
| a source made private | its staged records, dropped now; from the next sync nothing of it is stored |
| a rule turned on, a source made mixed or turned off | no view: nothing is dropped. Mixed sends ready records back to pending; off stops its syncs and scans, and what waits stays |

- Staged counts: `Gate.would_drop(config)`, the sweep's rules over `Staging.scan()` under the lock, writing nothing.
- Stored counts, said as "at least": `index.query.reach(vault, list, value)`, each candidate held to the rule the gate
  applies, so the count never overstates.
  - people: records' authors and segments' speakers held to the people rule;
  - keywords: the chunks `NameQuery` picks as candidates, each chunk's text then held to
    `neverstore.matches_text(text, NeverStore(keywords=[value]))`;
  - containers: records' container and thread, folded as the gate folds them.
- The share comes with the count ("in 1,240 of 4,213 chunks"), so a keyword like `meeting` shows what it would take.
- The confirm post carries the value and the hash again; a changed file gives the view again with fresh counts.

### Models

The page shows this machine's models and names the commands; it starts nothing (DR-0510).

| Option | Against | Verdict |
|---|---|---|
| install and remove from the page | hundreds of MB of model files and up to 1.3 GB of packages, inside the service; on Windows the service's own worker holds the files they replace; the service reads its models only when it starts; the service has no job runner, progress or cancel | no |
| the page writes the `models` block (reranker or provider none) | applies only after a restart, and `userconfig` rewrites the file without its comments | no: the line |
| status and commands | the user runs them in a terminal, which shows the install's progress as today | **yes** |

- The facts come from `models/report.py`, which `docket models status` prints too, its lines unchanged: the choice or
  why models are off, each device's environment, the files, the reranker's timing or why it is off.
- The service's worker from its own state; vectors from a count, `index.vector_counts`, never `index.status()`, which
  hashes every doc.
- The commands: `docket models install` with `--device` and `--no-reranker`, `docket models remove`, then `docket
  service install` to restart; `docket service stop` first where the worker holds the files.
- The rest of `config.yaml` is shown for this machine and never written: a folder source's own folder (DR-0490).

### The page

Conclusion first: where `vault.yaml` stands, then the parts.

```
+--------------------------------------------------------------------------------------------------+
| Docket  Today Queue Ledger Meetings Outbox | Search Briefs Recording | Staging Curate Sync Set.  |
+--------------------------------------------------------------------------------------------------+
| Settings     vault.yaml is Docket's own, so changes are made here.  laptop-1, the primary machine |
| SOURCES                                                                                          |
|  calls      mixed  on   tools list_files, get_transcript   mapper found                          |
|             [Private...]  [Turn off]          looser: by hand in vault.yaml               [lines] |
|  documents  work   on   folder docs; here E:/Work   exclude archive/*                [Turn off]  |
| NEVER STORE   people 3, containers 1, keywords 2                           [Show the values]     |
|  ( people v ) [                                  ]  [Add...]   committed in vault.yaml, as typed |
| REDACTION                                                                                        |
|  credentials  on   passwords and secrets after a label ...   docket redaction set credentials off|
|  phone        off  phone numbers written with + or ...        [Turn on]                          |
|  ticket-id    on   TCK-\d{6}                                  docket redaction set ticket-id off |
|  names are never redacted; keep one out with the never-store lists                               |
| MODELS ON LAPTOP-1                                                                               |
|  multilingual-e5-small on cuda, 4,213 of 4,213 chunks; reranker bge-reranker-v2-m3, 50 in 0.13 s |
|  the service's worker is up                       docket models install --no-reranker   [copy]  |
+--------------------------------------------------------------------------------------------------+
```

- Sources: a card each, with its sensitivity, on or off, tools ("none: nothing syncs live"), the mapper and whether
  `find_mapper` takes it, or its folder, this machine's folder and exclude; each change it can't make as its line.
- Never store: each list's count and what it matches; values and their lines with `show=lists`.
- Redaction: `redaction.describe`'s rows, the credentials-off warning while credentials are off, the names line; for a
  new pattern, the block to paste with an invented example.
- Each part has its empty and error state: a `vault.yaml` that doesn't load gives the page its message; a `config.yaml`
  that doesn't read gives the models part its reason, as `docket models status` does.

### The URL

| Parameter | What | Default |

| `show` | `lists`: the never-store values | none |
| `done` | what the last post did, kinds and counts only: `listed-people-1`, `phone-on`, `pattern-on`, `calls-private` | none |
