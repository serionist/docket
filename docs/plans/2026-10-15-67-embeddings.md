# Add embeddings in a worker, fused with keyword search by rank

## Goal

Search finds what a question means, not only the words it shares: a multilingual embedding model runs in a worker
process of its own, its vectors sit in the index, and the vector list fuses with the keyword stages by rank. Keyword
search stays whole when no model is installed or the worker is down. On the invented question set this lifts
paraphrase recall at 10 from 0.33 to 0.44 and typo from 0.75 to 1.00, and no kind's MRR falls by more than 0.01; the
reranker (#88) then takes paraphrase to 0.78.

This plan is the issue's first PR. The reranker is #88 and the API provider #89; the plan sets #88's direction from
the same measurements.

| Part | Done when |
|---|---|
| Worker | the embedder runs in a process with its own environment; the service keeps it loaded; the CLI starts one for a command that needs it |
| Providers | `local` on CPU or an NVIDIA GPU, or `none` (keyword search alone, as today), chosen per machine; `api` is an interface only |
| Index | `chunk_vec_<model>` in the index, kept in step with the chunks by every update and rebuild, reused by input hash; a model change builds a new table and drops the old when it is complete |
| Search | the vector stage's top 200 fuse with the FTS stages and the entity list by rank; every stage works when the worker is down |
| Measured | the question set per kind with and without models; the perf test's limits hold with 100,000 vectors |

- In scope: `docket/models/` (catalogue, worker, client, provider), `docket models install|status|remove`, the
  index's vector tables and the embedding pass, the vector stage, the service's and the CLI's wiring, a models CI job
  with floors of its own, the docs.
- Out of scope: the reranker (#88); the API provider (#89); MPS or CoreML on Macs (measured on a Mac first);
  Whisper's environment (phase 2); `docket doctor`; the Settings page (#73).

### The worker

- The service starts one at start when models are installed and keeps it; the CLI starts one when a command needs it
  (about 1 s on CPU, 2 s on GPU), and `--no-models` skips it. Who embeds what is its own section below.
- It runs as `<env python> -I -X utf8 <docket>/models/worker.py`, with an environment holding only what Python needs,
  the model folder and the device, as a mapper runs (DR-0123); on Windows with no console window, since the service
  runs under `pythonw`.
- It speaks JSON lines on stdin and stdout: `hello` (models, device, versions), `embed` (query or passage, texts in,
  float32 vectors out in base64); #88 adds `rerank`. What it prints goes to stderr, kept for `docket models status`
  and never logged; an error names its type only (DR-0155).
- One request at a time. The core's queue puts a search's query ahead of the pass's batches. A batch is sorted by
  length and cut by a token budget worth about 0.3 s, which the install measures on the machine (2,048 tokens at 4
  threads here, 16,384 on the GPU), so a search waits at most one batch. The pass's ONNX Runtime threads are capped at
  half the cores.
- A query not answered in 2 s skips the vector stage for that search, and the worker goes on. The worker is started
  again only when the request it is running passes its own timeout (`hello` 30 s, a batch 60 s), at most once a
  minute; meanwhile search runs without vectors.

### Its environment and the models

- `docket models install [--device auto|cpu|cuda]` makes a uv virtualenv on Docket's own Python under the user's data
  folder (`models/env-<device>`), installs `requirements-<device>.txt` (shipped in the wheel, `--require-hashes`,
  pins at least a week old as DR-0157 asks, Dependabot watching), downloads the catalogue's files at pinned revisions
  with their sha256 into the user's cache folder, resumable, starts the worker once to check it and time a batch, and
  writes the user config's `models:` block.
- The check: a vector of the right size, and on CUDA that ONNX Runtime really runs on the GPU rather than falling back
  to the CPU, else it says why (an NVIDIA driver older than R580 can't load CUDA 13). The install refuses a system
  sqlite-vec has no build for, naming it.
- The CUDA environment takes onnxruntime-gpu from PyPI (Windows x86_64, Linux x86_64 and aarch64) with its `cuda` and
  `cudnn` extras, which bring NVIDIA's CUDA 13 runtime, cuBLAS, cuFFT, cuRAND, NVRTC, nvJitLink and cuDNN wheels
  under NVIDIA's proprietary licences. They are installed only into that environment, when the user asks for it, and
  are never a dependency of Docket.
- `auto` takes CUDA when `nvidia-smi` answers. Macs run the CPU environment: ONNX Runtime runs natively on Apple
  silicon; MPS or CoreML waits until measured on a Mac.
- Downloads: CPU 0.05 GB of packages and 0.49 GB of model files (e5-small's `onnx/model.onnx`, 470 MB, and
  `tokenizer.json`, 17 MB); CUDA 1.27 GB of packages and the same 0.49 GB. #88 adds 0.49 GB (CPU) or 1.15 GB (GPU).
- `docket models status` says the environment, device, files, the worker's state and each model's vectors in this
  vault's index; `docket models remove` deletes the environment, the files and the config block.
- Nothing lands in the vault or a repo. After install nothing touches the network: the worker reads files by path.
- The catalogue is data in the package: per model its repo, revision, files with sha256 and size, dims, pooling and
  prefixes (e5's `query: ` and `passage: `), licence.

### Per machine

```yaml
# the user's config.yaml, beside service:
models:
  provider: local      # local or none; api is refused as not yet
  device: cpu          # cpu or cuda, written by docket models install
  embedder: e5-small
```

- In the user's config, not `vault.yaml`: `vault.yaml` is committed and shared by every machine of a vault and
  refuses unknown keys (DR-0021), so a machine not yet upgraded would refuse the vault, and a per-machine map in it
  would change the vault whenever a machine is added. The index is per machine (DR-0115), so each machine embeds with
  what it has and no vector crosses machines.
- A `models:` block that doesn't read (an unknown key or value, `api`) turns models off and says why in
  `docket models status`, the service's status and search's `models` field. It never stops the service or keyword
  search.
- What does belong to the vault is whether its text may leave the machine: the API provider's opt-in, in #89.

### The index

A vector is made from one string, and keyed by its hash:

```text
passage: <the chunk's title, on a line of its own, unless the text's first 200 characters hold it>
<the chunk's text>
```

The title is what the chunk carries in `chunks.title`: a transcript window carries its recording's name only there,
and windows are most of a call-heavy vault. The query is `query: ` and its words and phrases without its time words.

| Column | What |
|---|---|
| `chunk` | the chunk's id, the key |
| `input_hash` | sha256 of exactly the input above, indexed |
| `ts`, `source` | copied from the chunk, so the search's filters need no join |
| `vec` | float32, little-endian |

- One table per model, `chunk_vec_<key>`, the key from the catalogue's name and revision (`e5_small_614241f6`); a
  `meta` row per table gives its model, revision and dims.
- An update keeps every vector table in step with the chunks inside its own transaction, with no worker call: when a
  chunk is dropped (`drop_owner`), its vector moves to a temp table keyed by input hash and its row goes; when a chunk
  is added (`add_chunks`), a vector for its input hash comes back with the new id, ts and source. A re-put doc, an
  edited record and a re-windowed thread keep their vectors this way, and a reused id never keeps an old vector.
- A rebuild does the same from the old file, read before it is replaced, for the configured embedder's table whenever
  the config names one, worker or not; that includes `docket doc redact`'s rebuild. So a schema bump embeds nothing
  new.
- The embedding pass embeds only inputs with no vector. It reads a batch's chunks and closes the statement before it
  calls the worker, so no open read holds a lock while the worker works (a rollback journal, so an update's COMMIT
  would otherwise wait out its 5 s), then writes the batch under the index lock in a short transaction, only for a
  chunk whose input hash is still the one embedded.
- A model change: the pass fills the new table, search uses the configured model's table as far as it goes, and the
  old table is dropped once the new one covers every chunk.
- Existing indexes need no rebuild: the pass adds the tables. Without models no table is made, so two rebuilds still
  give the same database.
- `docket index status` adds a line: `vectors   e5-small  7350 of 7400 chunks`.

### Who embeds

| Command | Embeds |
|---|---|
| the service | the pass after each of its index updates, in the background |
| `docket index update`, `docket index rebuild` | the update or rebuild, then the pass with a progress line; when the service runs for this vault it leaves the pass to the service and says so |
| `docket search` | only the query |
| `docket eval` | only the queries: it writes nothing (DR-0293) |
| any rebuild, `doc redact`'s too | nothing: it keeps the configured embedder's vectors by input hash, and the pass embeds what is new |

### The vector stage and the fusion

- The query is embedded, then the scan runs on its own reader connection (mapped) in a thread beside the FTS stages:
  `SELECT chunk, vec_distance_cosine(vec, ?) AS d FROM chunk_vec_<key> WHERE <the search's time and source filters>
  ORDER BY d, chunk LIMIT 200`.
- Its 200 ids are checked against `chunks` on the search's own connection, by id and input hash, and a mismatch is
  dropped: the scan's connection may see a moment before or after an update that the search's doesn't, and an id
  `_run` can't find would raise there.
- sqlite-vec's scalar distance over a plain table: one query shape with any filter, a normal table a rebuild writes in
  order, and 67 ms on 100,000 chunks. Not `vec0`, slower with a filter (161 ms) and a virtual table more to rebuild;
  not numpy in the core, which holds 154 MB per 100,000 chunks and loads it in each CLI call.
- sqlite-vec (0.3 MB, MIT or Apache-2.0) joins the core's dependencies with an environment marker for the systems it
  has wheels for (Windows x86_64, macOS, Linux x86_64 and aarch64; none for Windows on Arm or musl, and no sdist), is
  imported only by the vector stage, and loaded on its connection only. Where it is missing, or Python was built
  without SQLite extension loading, the stage is skipped with the reason.
- The vector list is a third list in the reciprocal-rank fusion, k 60 and weight 0.5, beside the FTS cascade (all
  words, any word, prefixes, each ordered by titles' leads and terms held as now: DR-0231, DR-0232, DR-0282) and the
  entity list (DR-0117). A chunk only it found has `found_by: vector`.
- Facets count the FTS and entity candidates, and the vector candidates that reach the fused top k, so the vector top
  200 doesn't swamp the counts.
- Skipped, with the reason in a new `SearchResult.models` field (on or off, the model, why), when models are off or
  their block doesn't read, the worker is down or doesn't answer in 2 s, sqlite-vec or extension loading is missing,
  the query is only time words or filters, or the index has no table for the model yet. The CLI, the MCP text and the
  Search page say it in one line only when models are on and the stage was skipped.
- `docket eval` prints `vectors e5-small: 7350 of 7400 chunks` above its table, and how many questions ran with the
  stage skipped.
- Time: the query's vector takes 3 to 4 ms and the scan runs while the FTS stages do, so a search costs about what it
  costs today; the perf test holds each shape under 1 s with 100,000 vectors.

### The question set in CI

- The gate stays model-free: its eval runs keyword-only and its floors don't move, since keyword search doesn't change.
  The worker, the vector stage and the fusion are tested with a fake: a stdlib-only worker giving deterministic vectors
  (character trigrams hashed into 64 dims) that let a test plant a chunk only the vector list finds.
- The worker's ONNX Runtime backend lives under `src/` like the rest: strict pyright, the 100% floor, never excluded.
  The dev group gains the CPU builds of onnxruntime, tokenizers and numpy (pins a week old), and the backend's tests
  run it against a stubbed session.
- A `models` job in CI on Linux restores the environment and model files from the Actions cache (keyed by the
  requirements and the catalogue), runs `docket models install --device cpu` on a miss (0.5 GB), then runs the
  question set with models on (`DOCKET_TEST_MODELS=1`) and holds each kind against
  `tools/devkit/eval-floors-models.json` through a gate lane of its own, `gate models`. On Windows and macOS the job
  installs and starts the worker, without floors.
- The job is required for merge. A kind below its floor fails. A kind above its floor fails, printing the floor to
  write, only once three runs on CI have given identical numbers, which the PR shows; until then it is printed. Here
  three CPU runs did, and the CPU matched the GPU row for row.
- A cache miss downloads the pinned revision, so a Hugging Face outage blocks merges until it ends: accepted.
- The first floors are what the job measures; on this desktop: exact-name 1.00 / 0.88, paraphrase 0.44 / 0.21,
  inflection 1.00 / 0.85, typo 1.00 / 0.61, time-bound 1.00 / 0.77.
- The maintainer runs `docket eval` on his own set before and after, per kind, with and without `--no-models`, and the

## Doors and data

No one-way door changes:

- `vault.yaml` (DR-0021) is untouched: the choice lives in the user's config, which is not a door before the first
  release, as the REST API isn't (DR-0151).
- The MCP `search` tool (DR-0150) keeps its parameters; its result gains the `models` field and the `found_by` value
  `vector`, both additive. Facets keep their shape and count fewer vector candidates.
- The question file (DR-0290) is untouched; `docket eval` prints the vectors' coverage and the skipped stages.
- The index is a per-machine cache (DR-0115): it gains vector tables, existing indexes need no rebuild, and
  `docket models remove` leaves it working.
- New per-machine state outside any vault: the environment (user data folder), the model files (user cache folder),
  the config's `models:` block.

Named for later: the API provider's opt-in is a `vault.yaml` key, a DR-0021 door, in #89.

## Steps

1. The worker and its client, no models yet: `docket/models/` with `catalogue.py`, `worker.py` (the protocol loop),
   `onnx.py` (the ONNX Runtime backend), `client.py` (the process, the queue, token-budget batches, timeouts,
   restarts) and `provider.py` (`local`, `none`, and the fake for tests); the dev group's CPU onnxruntime, tokenizers
   and numpy. Tests: `test_models_worker.py`, `test_models_onnx.py` and `test_models_client.py`, on all three systems.
2. `docket models install|status|remove`, the requirements files and a devkit command that compiles them, the
   config's `models:` block. Tests: `test_models_install.py` with a stub uv and downloads from a local HTTP server on
   a free port; `test_models_config.py` for the block.
3. The index's vector tables kept in step by updates and rebuilds, the embedding pass, the model change, sqlite-vec in
   the core. Tests: `test_index_vectors.py` with the fake provider; `logical_dump` gains the vector tables.
4. The vector stage, its check against `chunks`, the fusion, the facets, `SearchResult.models`, the render lines, the
   eval lines, and the perf test with 100,000 vectors. Tests: `test_search_vectors.py`, `test_cli_eval.py`,
   `test_index_perf.py`.
5. The service keeps the worker and runs the pass after its updates; the CLI starts one on demand and leaves the pass
   to a running service. Tests: `test_service_models.py`, `test_cli_models.py`.
6. The models CI job, `gate models` and `eval-floors-models.json`: three runs on CI before the floors are set, then
   the maintainer's GPU and own-set numbers in the PR. Tests: `test_eval_set.py`'s models test,
