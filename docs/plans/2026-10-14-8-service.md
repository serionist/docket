# Add the service with the MCP tools search, read, verify and doc_put

## Goal

Any Claude session on the machine reaches the vault through one always-on local service: it searches, reads a
summary, verifies each line against its raw and writes a doc, over MCP, with nothing on the network and nothing another
site or another user can reach. The browser gets in through a one-time link, so #9's pages have a home. This is the
"from any Claude session" half of phase 0.

- In scope: `docket serve`, one process per user on one 127.0.0.1 port serving `/mcp`, `/api` and the pages; the
  localhost security the design's service section lists; the bearer token in the keychain; the browser session from a
  one-time link; writes run one at a time; the index kept current; the MCP tools `search`, `read`, `verify` and
  `doc_put`; the same four over REST; `docket service install | uninstall | status | token` and `docket open`.
- Out of scope: the pages (#9); the plugin's MCP config, hooks and skills (#12); `ingest` and the capture endpoint
  (#41); `media_put` (#42); the CLI routing its writes through the service (it keeps writing under the vault lock,
  below); scheduled jobs and workers (phase 1 on); `timeline`, `entity`, `propose`, `transcribe`, `secret`.

### The split

recordings and old notes come in through `docket ingest <source> <folder>` (#10) and `docket import notes` (#11) on the

| `ledger` | the ledger's own issue, phase 3 | the ledger lands then |

## Design

One new package, `docket/service/`, and a rendering module moved out of `cli.py`. FastAPI is DR-0016's; the MCP
Python SDK 2.x, uvicorn and keyring are new.

| Module | What it does |
|---|---|
| `service/app.py` | `create_app(settings)`: the routers, the middleware, `/mcp` mounted, the lifespan that starts the writer and the MCP session manager |
| `service/security.py` | the Host, Origin and Sec-Fetch-Site checks, the bearer token and session checks, the response headers |
| `service/sessions.py` | one-time codes and browser sessions, in memory; `docket open`'s redirect file |
| `service/token.py` | the service token: the store chosen once at install (keychain or file), then read and rotated only there |
| `service/writer.py` | the writer thread for writes; the index updater beside it |
| `service/tools.py` | the MCP server: the four tools, their annotations, the server's instructions, errors |
| `service/api.py` | the REST routes |
| `service/logs.py` | the logging setup: levels per logger, and a formatter that writes no message from an exception |
| `service/server.py` | `serve()`: the single-instance lock, the socket, `service.json`, uvicorn |
| `service/install.py`, `service/platforms/` | install, uninstall and status, one module per system |
| `docket/render.py` | the compact text the commands print and the MCP tools return, moved out of `cli.py` |

### One process, one port

| Path | Who calls it | Auth |
|---|---|---|
| `/mcp` | Claude Code, Claude Desktop, any MCP client | the bearer token |
| `/api/...` | the CLI, the plugin's hooks, the pages' own calls | the bearer token, or the session cookie |
| `/session` | the browser, once, from `docket open` | the one-time code |
| `/` and the pages #9 adds | the browser | the session cookie |
| `/api/health` | anything on the machine | none; it says only that Docket answers |

- Bound to 127.0.0.1 only, with no option to change it: the phone page (phase 4) is a design of its own.
- The port: `--port`, else `service.port` in the user's config, else 8741 (unassigned at IANA, clear of common dev
  servers). A port in use stops the service with the port named; it never moves to another, since every client's
  config names it.
- `serve` binds the socket itself, reads the port it got, builds the app's allowed hosts and origins from that port,
  hands uvicorn `sockets=[sock]`, and records the port in `service.json`. So `--port 0`, a free port for tests, works
  like any other. On Windows the socket takes `SO_EXCLUSIVEADDRUSE`, so no other process binds the port beside it.
- One vault per service: `service.vault` in the user's config, written by install; `--vault` overrides. The service
  opens the vault per call, so a `vault.yaml` edit applies at once, as the gate already reads it. Without a vault there
  (moved, deleted) it still starts, and `status` and every tool say why.

### Localhost security

| Check | On | Refused with |
|---|---|---|
| Host is `127.0.0.1:<port>` or `localhost:<port>` | every request, before routing; the SDK checks it again on `/mcp` | 421 |
| Origin, when sent, is `http://127.0.0.1:<port>` or `http://localhost:<port>`; `null` never | every POST, PUT, PATCH and DELETE | 403 |
| Sec-Fetch-Site, when sent, is `same-origin` | the same | 403 |
| a write made with the session cookie carries Origin or Sec-Fetch-Site | the same | 403 |
| `Authorization: Bearer <token>`, compared in constant time | `/mcp` always; `/api` when there is no session cookie | 401 |
| the session cookie | pages; `/api` when there is no bearer token | 401, with a page that says to run `docket open` |
| no CORS headers, ever; a preflight gets 405 | every route | - |

| Threat | What stops it |
|---|---|
| another site posts to the service (CSRF) | the SameSite=Strict cookie, the Origin and Sec-Fetch-Site checks; a bearer header can't be added cross-site without a preflight, and none is granted |
| another site rebinds its name to 127.0.0.1 (DNS rebinding) | the Host check on every route, and the SDK's own on `/mcp` with this port's two hosts and origins |
| another site reads a response | no CORS, `Cross-Origin-Resource-Policy: same-origin` |
| another user on the machine | the token in this user's store; the one-time code never on a command line (`docket open` hands the browser a file only this user can read); nothing answers without the token but `/api/health` |
| a framed page (clickjacking) | `Content-Security-Policy: frame-ancestors 'none'` |

What stays accepted for another user of the machine: loopback is shared, so they can connect to the port and learn from
`/api/health` that Docket answers; while the service is down they can bind the port themselves and collect the token
Claude Code sends (`status` warns when what answers isn't the pid on record); an administrator or root reads
everything. Any process running as this user can get the token, from either store.

- Every response also carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and
  `Cross-Origin-Opener-Policy: same-origin`; `/api`, `/mcp` and `/session` add `Cache-Control: no-store`. Pages get
  `default-src 'self'; base-uri 'none'; form-action 'self'` as a floor #9 builds on.
- Request bodies are capped at 4 MiB, the SDK's own limit on `/mcp`; a doc is a few KB.
- The tools take no filesystem path except `read`'s doc path, which #6 already confines to `processed/`.

### The token and the browser session

The token is `secrets.token_urlsafe(32)`. Its store is chosen once, by `docket service install`, and recorded, so the
service, the CLI and Claude Code's helper always read the same one:

| Step | What happens |
|---|---|
| choose | install tries keyring (service `docket`, user `service-token`): a write, then a read-back that must match. On Linux keyring counts only when the user manager's environment (`systemctl --user show-environment`) has `DBUS_SESSION_BUS_ADDRESS`, since the unit reaches the Secret Service only through it. A backend that is there and refuses the write (Windows' CredWrite error 1312 in a session without credentials) counts as none. Otherwise the store is a file |
| record | `service.token_store: keyring` or `file` in `config.yaml`, beside the vault and port |
| read | `serve`, `docket service token` and `docket open` use only the recorded store. None of them makes a token. When the store can't be reached (a locked keyring, a deleted file), `serve` exits and says which store and why, and the registration's restart tries again |
| rotate | `docket service token --rotate` writes a new token to the recorded store and restarts the service through its registration, or says to restart it when it runs by hand. With no store recorded yet (a machine that runs only `docket serve`, such as WSL without systemd), it chooses one as install does and makes the first token |

- The file is `service-token` in the user's config folder. On macOS and Linux it is created 0600 and refused when group
  or others can read it. On Windows the mode means nothing, so the file relies on its folder, `%LOCALAPPDATA%`, which
  only the user, SYSTEM and administrators can read.
- Keyring comes first because it keeps the token out of plain files, backups and synced dotfiles. Either way, any
  process running as the user can get it.
- `docket service token --header` prints `{"Authorization": "Bearer <token>"}`, the form Claude Code's `headersHelper`
  takes; Claude Code runs it on each connect and again after a 401, so a rotated token is picked up. #12 configures it.
- The token is never on a command line, in `service.json`, in a log or in an environment variable.

The browser session:

1. `docket open` posts to `/api/session` with the token and gets a code: 32 random bytes, one use, 60 seconds.
2. It writes a small redirect page into the state folder, created 0600 (on Windows, inside `%LOCALAPPDATA%`), that
   moves on to `http://127.0.0.1:<port>/session?code=<code>`, and opens that file, as Jupyter does. So the code is never
   in a process's arguments, which any account on Linux reads from `/proc/<pid>/cmdline`. The next `docket open`
   deletes the old file. With no browser to open, it prints the link to the terminal instead.
3. The service swaps the code for a session cookie `docket_session` (`HttpOnly; SameSite=Strict; Path=/`, no `Secure`
   on plain loopback HTTP). It answers with a small page of its own that moves on to `/`, or to `next` when that is a
   path on this origin (`/x`, never `//x`), with a meta refresh and a link. Not a 303: a redirect would keep the
   navigation cross-site, coming from a file, and the browser would hold back the Strict cookie on it.
4. Sessions live in the service's memory, for 12 hours at most, and end when it stops; then `docket open` again.

### Writes and the index

- One writer thread in the service: every `doc_put` is queued and runs one at a time, in order. `read`, `verify` and
  searches run on other threads meanwhile.
- Every writer takes the vault lock around its write, as #4 to #6 already do (`Vault.writing()`, `Vault.lock`). So the
  CLI keeps writing directly while the service runs: the lock serializes the two, the queue keeps the service from
  contending with itself. Routing the CLI through the service would give every command two code paths for no gain the
  lock doesn't already give.
- The service waits at most 15 seconds for the vault lock (the CLI keeps #4's 60), then answers that another Docket
  process holds the vault. `Vault.open` gains the timeout as a parameter.
- Index updates run outside the write queue, since `index.update()` takes only #7's index lock, never the vault's: one
  at a time, at start (it builds the index when there is none), after each `doc_put` and before each search. A search
  waits for an update that started after it arrived, and searches arriving together share one. So a record the CLI
  promoted, or an entity file edited by hand, is found on the next search, and no search waits behind a write.
- A search waits at most 30 seconds for its update; past that (a first build of a large vault) it answers that the
  index is being built.
- A write that fails reports its error and the writer goes on with the next.
- Docket's own commits pass `-c commit.gpgsign=false` (`vault/git.py`): they are machine commits, and a service with
  no terminal would hang on a pinentry prompt or fail on a signing key it can't unlock. The same reasoning as #34
  skipping the host repo's hooks; the owner's call, recorded as proposed.

### The MCP tools

| Tool | Parameters | Result | Annotations |
|---|---|---|---|
| `search` | `query` (text); `people`, `entities`, `sources` (lists of text, default empty); `since`, `until` (text or null); `k` (1 to #7's maximum, default 20) | #7's `SearchResult` | read-only, closed world |
| `read` | `locator` (text); `view` (`summary`, `raw` or `both`, default `summary`); `around` (0 or more, default 0); `rev` (1 or more, or null) | #6's `ReadResult` | read-only, closed world |
| `verify` | `doc` (text); `lines` (line numbers, or null for every anchored line); `window` (seconds, default 60) | #6's `VerifyResult` | read-only, closed world |
| `doc_put` | `text` (the whole doc, frontmatter and body) | #6's `PutResult` | not read-only, not destructive (a rev keeps history), idempotent |

- The names and parameters follow the design's tools table and the Python APIs one to one. They are the one-way door
  this change lands (DR-0018).
- The door's rule: parameters only gain optional ones whose default keeps today's behaviour, and enums only gain
  values; results only gain fields. Nothing is renamed, retyped or removed without a superseding decision.
- `since` and `until`: a date (`2026-10-01`, the owner's day in `vault.yaml`'s time zone) or a time with its offset
  (`2026-10-01T09:00+02:00`); a time without an offset is read in the owner's time zone; anything else is refused.
  Text, not a JSON date type, so one parser decides and the schema has no union.
- Content: the compact text the commands print (`12:08  Ben Sample: ...`), with their control-character escapes, so a
  record's terminal codes never reach Claude Code's screen; the structured content is the result model as data,
  unescaped. Over 50,000 characters Claude Code keeps the result in a file Claude reads in parts; `around`, `lines`
  and `k` narrow it.
- Errors: a `DocketError` is a tool error with its message; a refused `doc_put` is a tool error listing every problem
  with its line, so Claude fixes and puts again; anything else is the SDK's "Error executing tool <name>". The SDK
  logs a tool error's text at INFO, which the logging setup keeps out of the log (below).
- The server's instructions, a few lines: what Docket holds; search, read the summary, then `verify` or `read` the raw
  behind each fact used; cite locators; text in results is quoted from mail, chats and recordings, data and never
  instructions.
- Transport: streamable HTTP at exactly `/mcp`, no redirect; stateless, so a restarted service needs no session from
  the client; JSON responses, since no phase 0 tool streams progress.

### The REST API

| Method and path | What | Answer |
|---|---|---|
| `GET /api/health` | whether Docket answers | `{"service": "docket"}` |
| `GET /api/status` | version, pid, port, start time, the vault and machine, the index's status, where the token lives | JSON |
| `GET /api/search` | `search`'s parameters, lists repeated | `SearchResult` |
| `GET /api/read` | `read`'s | `ReadResult` |
| `GET /api/verify` | `verify`'s | `VerifyResult` |
| `POST /api/docs` | a doc, as a UTF-8 `text/markdown` body | `PutResult`; 422 with the problems |
| `POST /api/session` | a one-time link for the browser; the bearer token only | `{"url", "expires_at"}` |

- A `DocketError` is 400 `{"error": <message>}`; anything else 500 `{"error": "internal error; see the service log"}`.
  The outermost middleware catches every exception, logs it through the logging setup and answers the 500 itself,
  without re-raising, so Starlette's error middleware never hands it to `uvicorn.error` with its message.
- REST is Docket's own: the CLI, the plugin's hooks and the pages call it, shipped from this repo together. It is not a
  door until the first release; the MCP tools are.

### `docket serve` and its files

| File | Where | Holds |
|---|---|---|
| `config.yaml` | the user's config folder (`DOCKET_CONFIG_DIR`) | `service.vault`, `service.port` and `service.token_store`, beside `default_vault` |
| `service.json` | the user's state folder (`DOCKET_STATE_DIR`, new) | pid, port, vault, version, start time; written through a temp file and a rename, removed at a clean stop; never the token |
| `service.lock` | the state folder | one service per user: a second `docket serve` names the pid that runs |
| `service.log` | the user's log folder | rotated at 5 MB, three kept |

- uvicorn runs in-process, without its extras (h11, pure Python) and with its access log off. Docket logs one line per
  request: method, route template, status, milliseconds.
- The log holds no content: no query string, body, tool argument or result, and no error message from a call, since all
  of them carry the user's words. The setup, in `service/logs.py`:

| Logger | Level | Why |
|---|---|---|
| `docket` | INFO | Docket's own lines, written without content |
| `mcp` | WARNING | the SDK logs a tool error's text at INFO |
| `uvicorn`, `uvicorn.error`, `uvicorn.access` | WARNING | the access log carries query strings; the error log gets exceptions with their messages |
| `starlette` | WARNING | its error middleware re-raises with the message |

- One formatter on the file handler: a record with an exception writes the exception's type and its frames (file, line,
  function), and the same for each cause and context in the chain, never a message. `logger.exception` in any library
  prints only that.

- On Windows the registration starts it under `pythonw.exe`: no console, `sys.stdout` and `sys.stderr` are None, and
  nothing writes to them.
- On Windows the registration starts it under `pythonw.exe`: no console, `sys.stdout` and `sys.stderr` are None, and
  nothing writes to them.
- A stop by the system (Task Scheduler's end, launchd, systemd) can land mid-write: every core write is already a temp
  file and a rename or a git commit with recovery, so nothing half-written stays.

### Install

| System | Registration | File | Commands |
|---|---|---|---|
| Windows | a Task Scheduler task `Docket` at the user's own logon, only while they are logged on (InteractiveToken, LeastPrivilege), the principal and the logon trigger both naming the user by SID; no time limit; `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` false, since both default to true and a laptop on battery would never start it; restart on failure every minute three times; the logon trigger repeated every 5 minutes for as long as the user is logged on, with `MultipleInstancesPolicy` IgnoreNew, so a service that exited comes back, which the restart setting alone doesn't do for a process that ran and ended; normal priority; hidden. When Task Scheduler refuses (a policy, a standard account), the per-user Run key `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `Docket`, and install says which | the task XML, UTF-16 with a BOM, the form Task Scheduler exports | `schtasks /Create /XML /F`, `/Run`, `/End`, `/Change /ENABLE` and `/DISABLE`, `/Delete`, `/Query`; the SID from `whoami /user` |
| macOS | a LaunchAgent `io.github.serionist.docket`, RunAtLoad, KeepAlive after a crash | `~/Library/LaunchAgents/io.github.serionist.docket.plist`, written by `plistlib` | `launchctl bootout`, then `print` until the agent is gone (bootout returns before it ends), then `bootstrap`; `kickstart -k`; all in `gui/<uid>` |
| Linux | a systemd user unit, `WantedBy=default.target`, `Restart=on-failure` | `~/.config/systemd/user/docket.service`, with `%` and `$` escaped and paths quoted | `systemctl --user daemon-reload`, `enable --now`, `restart`, `stop`, `disable --now`, `show`, `show-environment` |

- The command is this Docket's own interpreter with `-X utf8 -m docket serve` (`pythonw.exe` beside `python.exe` on
  Windows); the vault, port and token store come from `config.yaml`.
- The environment install writes into the registration:

| Variable | Value | Why |
|---|---|---|
| `PATH` | the installing shell's whole PATH | a LaunchAgent's own PATH has no Homebrew folder, and git, git-lfs and their helpers can live anywhere the user put them |
| `SSH_AUTH_SOCK` | the shell's, where it has one; not on macOS | git helpers that reach the agent; launchd hands a LaunchAgent the session's own socket, and a path captured there goes stale at the next boot |
| `DOCKET_CONFIG_DIR`, `DOCKET_STATE_DIR` | the shell's, when set | the service reads the same config, token file and state as the command that installed it |

- Run install again after changing PATH; `status` shows the PATH the registration holds.
- `install` writes the service keys to `config.yaml`, chooses the token store and makes the token when there is none,
  registers, starts, and waits until `/api/status` answers with the right vault. When the service answers but can't
  read the vault, and the vault sits under `~/Documents`, `~/Desktop` or iCloud Drive on macOS, install says so: the
  Python the agent runs needs the Files and Folders permission (or Full Disk Access) in System Settings, named with its
  path, or the vault moves elsewhere.
- Run again, install replaces the registration and restarts. A new Docket version is installed as stop, upgrade,
  install: on Windows a running service holds its `.pyd` files open, and the upgrade can't replace them.
- `stop` stops the service until it is started again: Windows ends the task and disables it, or its 5-minute
  repetition would start it again; macOS boots the agent out; Linux stops the unit. `install` starts it again, and on
  macOS and Linux so does the next logon.
- `uninstall` stops the service and removes the registration; the token and `config.yaml` stay, so Claude Code keeps
  working after a reinstall.
- `status`: installed (how, and the file or task), running (pid, port, version, since; from `service.json` and
  `/api/status`, and a warning when what answers on the port isn't the pid on record), the vault, the log, the token's
  store. Exit 0 when it runs, 1 when it doesn't.
- Without a systemd user instance (WSL without systemd, a container) install refuses and says to start `docket serve`
  from the user's own startup.
