# Make redaction optional and redact docs; changes vault.yaml and anchors

## Goal

Redaction becomes the user's choice, rule by rule, and it runs on everything Docket commits: raw records at the gate,
as today, and every doc, so a credential Claude copies into a note, or one sitting in an old note, never reaches the
vault's history. Credentials are redacted unless the user turns that off; phone numbers only when the user turns them
on. Names are never redacted. A redaction never moves a line or an anchor.

What runs today:

| Route | Never-store | Redaction |
|---|---|---|
| the gate (raw records) | the lists, as the user sets them | all four built-in rules under one switch, `builtin: true`, and every user pattern |
| `doc_put` over MCP, REST and `docket doc put` (`DocStore.put`) | none | none |
| `docket import notes` (`put_many`) | keywords on the old path, the slug and the text | `Redactor.text` on the whole body: a key block's lines fold into one marker |
| a hand edit taken in before a put (`_take_in`) | none | none |
| docs already in a vault | none | none |

- In scope: redaction set rule by rule in `vault.yaml` (credentials on, phone numbers off, each user pattern on or off),
  followed by the gate and derived text alike; init's flags, the setup skill's question and `docket redaction` to
  change it later; one guard for derived text, called by `DocStore` on every text it commits; the anchor grammar
  reading a marker as text; what `doc_put` tells its writer; the import's redaction keeping lines and reporting
  counts; `docket doc redact` for docs already stored; the index after that pass.
- Out of scope: raw records under a rule added later (raw is written once, DR-0014); removing old revs from history
  and `read` with a rev (forget, a later phase); later writers of derived text (Whisper transcripts in phase 2, entity
  proposals in phase 1, ledger ops in phase 3), which call the same guard when they land; an MCP tool for the pass.

## Design

The settings live in `vault.yaml` and build one `Redactor` that the gate and derived text share. One new module holds
the rules for derived text; `DocStore` calls it on every text it commits, so every route gets it, the import included.

| Module | Change |
|---|---|
| `docket/vault/config.py` | `redaction.credentials`, `redaction.phone`, a pattern's `enabled`; `builtin` read as `credentials`; the dump writes the new keys |
| `docket/vault/redact.py` | `Redactor.from_config` builds the credential rules, the phone rule and the enabled patterns, each with its `native` key labels, as the settings say |
| `docket/vault/wizard.py`, `cli.py` | init's `--redact-credentials/--no-redact-credentials` and `--redact-phone/--no-redact-phone`; `docket redaction` and `docket redaction set` |
| `plugin/skills/setup/SKILL.md` | the credentials question in its one round, phone numbers named as an option, the answers passed as init's flags |
| `docket/vault/derived.py` (new) | `screen(doc, lists, rules)`: the never-store problems, lines and the list only; `redact(doc_type, body, redactor)`: the body with its lines and anchors kept, the markers added per rule, the lines they are on; `check_written(text, last, lists, redactor)`: a hand edit's frontmatter as written, for a take-in and the pass |
| `docket/vault/anchors.py` | `[redacted:<rule>]` is text, never an anchor-like token |
| `docket/vault/docstore.py` | `put`, `put_many` and the take-in screen and redact; `PutResult` gains two fields; `redact_all` for the pass |
| `docket/imports/notes.py` | the body through `derived.redact`; `ImportReport.redactions` |
| `render.py`, `cli.py` | the put's redaction line; `docket doc redact`; the import's redacted line |
| `service/tools.py` | `doc_put`'s description and the server instructions say what it redacts and refuses |

### Redaction settings

Each rule is on or off in `vault.yaml`, and the gate and every derived write follow the same settings:

```yaml
redaction:
  credentials: true      # passwords and secrets after a label, API keys and tokens, private key blocks
  phone: false           # phone numbers written with + or after a label
  patterns:              # the user's own; none by default
    - name: door code
      pattern: 'door code (?P<secret>\d+)'
      enabled: true
```

| Key | Default | Turns on or off |
|---|---|---|
| `redaction.credentials` | `true` | the built-in password, api-key and private-key rules, and a `native` key labelled as one of them |
| `redaction.phone` | `false` | the built-in phone rule, and a `native` key labelled as a phone |
| `redaction.patterns[].enabled` | `true` | that one pattern |

- All three keys are optional and `schema_version` stays 1 (DR-0021): a file without them loads with the defaults.
- `redaction.builtin`, which every `vault.yaml` written so far holds as `builtin: true`, reads as `credentials`; a
  file with both is refused, naming the two keys. Docket writes `credentials` and `phone` from now on. A file in the
  old form still counts as Docket's own, so `docket source new` and `docket redaction set` rewrite it in the new form
  rather than printing the lines to paste.
- Existing vaults: `builtin: true` turned on all four rules, so from the next sync phone numbers reach raw and docs as
  written until the user turns phone on.
- Turning a rule off, which every existing vault does for phone numbers at its first sync or import after the
  upgrade, changes what Docket writes for things it already stored:
  - markers already stored stay;
  - a record a source sends again (the lookback window, or `docket ingest` again) gets a new version under the new
    rules, since the gate skips only a version it already has, and lands in raw as a second version holding the
    value as written;
  - a mixed source's records wait in pending again, and so do records the user classified private or cut, a cut one
    uncut in staging, since a record decided by hand waits for the user (DR-0025);
  - the next `docket import notes` writes a new rev of each note the rule matched, and reports a note also edited in
    the vault as kept, to settle with `--take` (DR-0132).
- That churn is accepted over skip logic: the values are wanted, it happens once per vault, and skipping would add a
  comparison of versions under old and new rules to the gate for a one-time effect. Turning a rule on works the same
  way the other way: a record sent again lands as a redacted new version.
- The gate reads the settings on every call (DR-0025), so a rule turned on applies from the next promotion; `docket doc
  redact` applies it to the docs already stored; raw already stored keeps what it has (DR-0014).
- Names are never redacted, by any rule. Keeping a name, a topic or a chat out of the vault is the never-store lists'
  job: the user's own lists, empty by default, which drop a record or refuse a doc whole. The README says so plainly.
- An older Docket refuses a `vault.yaml` holding the new keys, as it refuses any key it doesn't know, and stops writing
  until it is updated. Every existing vault keeps `builtin: true` until `docket redaction set` or `docket source new`
  rewrites the file; until then an older Docket on another machine loads it and still redacts phone numbers, so the
  same record harvested on both machines lands in raw as two versions. An older Docket fails closed only once the file
  is in the new form, and before then it redacts more, never less.

Setting it:

- `docket init` takes `--redact-credentials` or `--no-redact-credentials` (on by default) and `--redact-phone` or
  `--no-redact-phone` (off by default), and its summary prints the settings.
- Turning credentials off, with `--no-redact-credentials` or `docket redaction set credentials off`, prints: "from the
  next sync, passwords, keys and tokens are stored as written, in raw, docs and git history; turning it back on
  doesn't remove them from raw". They stay at the tip until forget, and in a folder vault they go out with the host
  repo's next push.
- The plugin's setup skill adds one question to its round: redact credentials (passwords, keys, tokens) before
  anything is stored, yes recommended. The question says phone numbers can be redacted too, off unless the user
  turns them on, as a second option. The answers go to init as these flags.
- `docket redaction` prints the settings. `docket redaction set <rule> on|off`, where the rule is `credentials`,
  `phone` or a pattern's name, changes one under the vault lock and commits it as `Config: redaction <rule> on|off`.
  It rewrites the file only when it is as Docket wrote it, and otherwise prints the line to change, as `source new`
  does (DR-0166). Turning a rule on says to run `docket doc redact` for the docs already stored, and that raw records
  stored while it was off keep what they hold.
- A rule name `set` can't place is refused, with the `vault.yaml` line to change printed: a user pattern named
  `credentials` or `phone`, or two patterns sharing a name.
- Not chosen: one `builtin` switch (phone couldn't be off while credentials are on); a switch per credential rule
  (users decide on credentials as one thing); keeping `builtin` as the credentials key (its name hides that phone is
  apart); a schema 2 (every file would need migrating for keys that are optional); asking in init's own prompts (the
  setup skill runs init with flags, DR-0103).

### What is screened and what is redacted

| Part of a doc | Never-store keywords | Redaction |
|---|---|---|
| a content line's text, before its anchors | yes | yes |
| a content line's trailing anchors | no: rids the raw log holds | no: ids, kept byte for byte |
| free and skip lines (headings, a table's header, fenced code, comments) | yes, whole | yes, whole |
| a legacy note's lines | yes, whole | yes, whole |
| the id's slug, `entities`, the slugs in `supersedes`, `old_paths` | yes | no: ids and locators (DR-0131) |
| `type`, `covers`, `rev`, `by`, `import_hash` | no | no |
| in a take-in and the pass only: the file's frontmatter as written, that is its comments, unknown keys with their values, and `by` and `covers` where the hand edit changed them | yes | checked, never redacted: a match refuses |

- The rules are `vault.yaml`'s as the call opens the vault, as the gate's are (DR-0021, DR-0025): the never-store
  lists, and the redaction rules the settings turn on.
- The frontmatter is never redacted, as a record's ids never are (DR-0027). `by` isn't screened in a put: it names
  the writer and its run (`docket import` is fixed), not what the doc says, and a keyword like `sync` would refuse
  every doc.
- The screen runs on the text as it would be committed, after redaction (in memory, nothing written yet): a keyword
  that sat inside a secret is gone, and a marker that says one is caught. The built-in rules' markers
  (`[redacted:phone]` and the rest) are left out, since their words are Docket's own, so the keyword `phone` doesn't
  refuse every doc they mark. A user pattern's marker is screened like any text: a pattern named `Dora Example
  account` writes `[redacted:dora-example-account]`, so the docs it fires on are refused under the keyword `dora
  example`, and the problem says the pattern needs another name. A marker naming no rule is screened as text.

### A hand edit's frontmatter

A put commits Docket's own render of the parsed keys, so only the rows above reach a commit. A take-in, and the pass,
commit the file's own text with only its rev line set: a lenient read moves an unknown key such as `title:` into
`extra` and drops comments, so neither is seen by the checks on the parsed keys.

- In a take-in and in the pass the frontmatter is screened as written, line by line: comment lines and comments after
  a value, unknown keys with their values, the keys the table screens, and `by` and `covers` where the hand edit
  changed them from the last rev (all of them when there is none).
- The comments, the unknown keys with their values, and every key the hand edit changed are checked against the
  redaction rules. No marker is ever written into YAML: a part redaction would change refuses, like a keyword. Keys
  left as Docket wrote them are ids and locators, as in a put.
- A match refuses the take-in, and so the put, the way a keyword in the body does; the pass leaves the doc and names
  it. The edit stays on disk, uncommitted.

### Never-store: the doc is refused

- A match refuses the whole doc before its anchors are checked. The problems name each line it is on (both lines
  when a keyword runs over a line break) or the frontmatter key, say "says something on the never-store keywords
  list; leave it out", and carry no excerpt. Nothing is written, committed or logged.
- Why refuse: the gate drops a whole record and the import skips a whole note on a match (DR-0026, DR-0135); the words
  around a keyword still tell what it was; and Claude can write the doc again without it, which a source can't.
- Not chosen: redacting the keyword (its context stays, and the marker says something private was there); dropping
  the lines (a summary changes silently and its line numbers move).

### Redaction keeps lines and anchors

A marker changes a line's length only. Anchors belong to a line (DR-0110), `verify` takes line numbers, and the index
keeps a doc's anchors by line, built from the stored text, so nothing moves.

1. Split each content line into its text and its trailing run of anchors, as `trailing_anchors` reads it; the run is
   kept byte for byte with the spaces before it. A line whose run holds a malformed anchor, and every other line, is
   all text.
2. Redact the text parts joined by line breaks, as a transcript's segments are (DR-0027, `Redactor.segment_texts`): a
   label at the end of one line and its value on the next still match, and a match that runs over a line break (a key
   block, a user pattern over lines) turns each line it touches into its marker whole.
3. Put each line back: its redacted text, then its anchors. A line whose text was empty (an anchor-only line inside a
   key block) and became a marker gets one space before its anchors, or `[redacted:private-key]@00:20` would read as
   text and the line would lose its anchor.

```markdown
- Cleo's direct line is +1 555 010 0188 @13:40
```

is stored, with phone redaction on, as

```markdown
- Cleo's direct line is [redacted:phone] @13:40
```

- Redacting twice is once (DR-0027): the same doc put again is unchanged, so `doc_put` stays idempotent.
- Not chosen: `Redactor.text` over the whole body, as the import does today: a key block's lines fold into one marker,
  every later line number moves, and the anchors on the folded lines are lost. Each line alone: a label on one line
  and its value on the next would be stored.

### The anchor grammar reads a marker as text

- Today the example above is refused. DR-0110 keeps `[<letters>:...]` at a line's end for later anchor kinds, so the
  trailing parser reads `[redacted:phone]` as a bad anchor. Every line whose secret sat right before its anchors
  would be refused, and `verify` would flag the lines a take-in or the pass wrote.
- The change: DR-0027's marker `[redacted:<rule>]` is text wherever it stands, and no anchor kind is ever named
  `redacted`. This supersedes DR-0110, a one-way door (Doors and data).
- Stored docs: every doc valid before stays valid with the same anchors; only docs that were refused become possible.
  An older Docket reading a newer doc reports such a line as a bad anchor in `verify`, and still reads its anchors;
  it also refuses to put a doc holding a marker right before its anchors, so a doc read back from the vault can't be
  put again on a machine that wasn't updated.
- Not chosen: a second marker shape in docs, such as `(redacted: phone)` (two forms, and redacting twice would no
  longer be once); refusing and asking the writer to move the secret (the writer can't see where a marker lands).

### What the writer is told

No route ever echoes a redacted value or a keyword.

| Route | Told |
|---|---|
| `doc_put`, stored | `PutResult` gains `redactions` (rule to markers added) and `redacted_lines` (the lines, numbered as `read` numbers the stored doc); the compact text adds `redacted on lines 12, 14: 1 password, 1 phone`; the same on an unchanged put whose text held them |
| `doc_put`, never-store | the problems above: an MCP tool error, a REST 422, `docket doc put` exit 1 |
| `doc_put`, other refusals | as today, their excerpts taken from the redacted lines, so an anchor problem never quotes a secret back |
| a hand edit taken in | its body redacted in its file and committed as today's `(edited by hand)` rev; one that says a keyword, or whose frontmatter as written holds one or what redaction hides, refuses the put with `processed/<path> was edited by hand, and its line 4 says something on the never-store keywords list` (or `holds what the phone rule redacts`) `; edit it or check it out again`, and stays on disk, uncommitted |
| `docket import notes` | `ImportReport.redactions`, printed as `redacted  2 password, 1 phone` |

- `PutResult` only gains fields, as DR-0150 allows. The MCP golden file holds names, parameters and annotations, so
  it doesn't change; `doc_put`'s description and the instructions say what it redacts and refuses.
- A take-in's own markers aren't in `PutResult`: they belong to the user's edit, the file shows them, and the put is
  refused at the old rev anyway, so its writer reads the doc again.

### Docs already in a vault: `docket doc redact`

Every write redacts from now on, and a one-off pass redacts what is already there. Run it once after upgrading, and
again after turning a rule on or adding a pattern or a keyword to `vault.yaml`.

```
$ docket doc redact
redacted  3 docs: 4 password, 1 phone
          minutes:2026-10-02-supplier-call rev 4, recording-note:2026-10-09-site-visit rev 2, digest:2026-w41 rev 6
left      1 doc says something on the never-store lists: processed/brief/dora-example.md
          edit or delete it, then run docket doc redact again
history   earlier revs still hold what was redacted, in this vault's git history
index     rebuilt
```

- Under the vault lock, one commit, `Redact docs: <n>`, with a `Doc: <id> rev <n>` line for each doc (DR-0112).
- Only the body is redacted, in the file's own text, and the rev line set as the take-in sets it, so a doc from a
  newer Docket keeps the keys and types this one doesn't know.
- A doc whose file differs from its last rev goes in first through the take-in, which now redacts, as its own
  `(edited by hand)` rev.
- Left as they are and named by path, with exit 1: a doc the never-store lists forbid (the pass never commits one, and
  removing it is the user's call), one whose frontmatter as written holds a keyword or what redaction hides (A hand
  edit's frontmatter), and a file that doesn't parse or sits where its id doesn't say.
- The history line follows the storage: a repo of its own keeps the old revs in its history; in a folder, the host
  repo's history keeps them, and Docket never rewrites that repo (the design's Retention section).
- `--dry-run` prints the same and writes nothing. No MCP tool: a terminal one-off, like the import.
- Not chosen: only on each doc's next rev (a doc nobody touches keeps its secret in the tree for good); at service
  start or index rebuild (a write nobody asked for).

### The index

- `doc_put` and the import never put unredacted text on disk, so the index never reads it.
- The pass rebuilds this machine's index when it wrote anything. A rebuild writes a new file (DR-0115), so the old text
  isn't left in free pages or in the full-text index's deleted entries, as it would be after an update.
- Another machine follows the changed docs with an update when it pulls: search stops finding the old text at once,
  and its bytes can stay in that index file until `docket index rebuild` there, which the pass's output says to run.
- A hand edit sits on disk before its take-in, and an update may index it: the index holds what this machine's
  working tree holds, and is never committed.
- Not chosen: `secure_delete` and an FTS optimize on every update: slower updates, and old FTS segments stay until a
  merge anyway.

Users' data:

- `vault.yaml`: every existing file loads unchanged, its `builtin: true` read as credentials on, phone off. From the
  next sync, phone numbers are stored as written until the user runs `docket redaction set phone on`; markers already
  stored stay. The file moves to the new keys the next time Docket writes it.
- The first sync after the upgrade: a record holding a phone number that a source sends again lands in raw as a second
  version holding the number, and mixed, cut and private-classified records wait in pending again (the churn
  decision).
- An older Docket loads a file still in the old form and keeps redacting phone numbers, so a record harvested there
  and here lands as two versions; once the file is in the new form, it can't load it and stops writing until it is
  updated.
- A doc changes only when it is written: by a put, a take-in or the pass, each as its next rev. Earlier revs stay in
  history.
- Legacy notes: the first import after the upgrade writes a new rev of each note holding a phone number, now kept as
  written, and of each note with a match over lines (a key block), since the import's redaction keeps lines now. A
  note also edited in the vault is reported as kept, to settle with `--take` (DR-0132). Any other note hashes the
  same, and nothing is written.
- Unchanged: the doc format (DR-0109), revs (DR-0112), old paths (DR-0130, DR-0131), `vault.yaml`'s other keys and
  its schema version (DR-0021), the MCP tools' names and parameters (DR-0150).
- `AGENTS.md`'s doors line cites the new grammar decision in place of DR-0110, and names the redaction keys beside
  `vault.yaml` (DR-0021).

## Open questions

Answered after round 1: all six as recommended. The grammar change is recorded as proposed for the maintainer's end
review. They stay here as the record. After round 1 the maintainer changed the scope in #24: names and phone numbers
need no redaction, and redaction is optional; Redaction settings carries it, and the choices made for it are its Not
chosen line and the decisions above.

| Question | Recommended | Why |
|---|---|---|
| Change the anchor grammar so a marker reads as text? | yes, agreed in #24 at the end review | it only accepts more: no stored doc changes meaning; without it, a secret right before a line's anchors refuses the doc |
| A doc that says a never-store keyword: refuse or redact? | refuse | the gate and the import drop the whole thing; the words around a keyword still tell; Claude can write it again |
| `read` with a rev returns an earlier rev's unredacted text: redact it on the way out? | no, leave it to forget | DR-0112 binds `read(rev=n)` to the commit's own text, and the history holds it either way |
| A hand edit holding a secret: redact it in place, or refuse the put until the user removes it? | redact in place | the gate redacts rather than refuses; a refusal blocks every put to that doc |
| Raw records stored before a rule was added: redact them too? | no, a follow-up with forget | raw is written once (DR-0014); rewriting it is a history rewrite |
| Other machines' indexes after a pass: rebuild them automatically? | no, the output says to run `docket index rebuild` | search is right after an update; the bytes left are in a local cache beside a history that holds the same text |

## Risks

- Existing vaults stop redacting phone numbers at their next sync, so phone numbers reach raw and docs. Accepted: the
  maintainer's call in #24; the CHANGELOG, init's summary and `docket redaction` say how to turn it on.
- Turning a rule off churns once: records sent again land as new versions holding the value, decided records wait in
  pending again, and the next import writes new revs of the notes it matched. Every existing vault does this for
  phone numbers at its first sync and import after the upgrade. Accepted over skip logic (the churn decision).
- A user who turns credentials off stores passwords and keys in git, and on a remote. Turning it back on leaves them
  in the raw records stored meanwhile, at the tip until forget; in a folder vault they go out with the host repo's
  next push. Accepted: it is their choice; setup recommends on, and turning it off prints exactly this.
- An older Docket loads a `vault.yaml` still in the old form and keeps redacting phone numbers, so a record harvested
  on both machines lands in raw as two versions; once the file is in the new form, it refuses it and stops writing.
  Accepted: before the rewrite it redacts more, never less, and after it fails closed; the CHANGELOG says to update
  every machine first.
- A match over lines turns every line it touches into its marker, the words before or after the secret on those lines
  included; an unclosed key block takes every line to the end. Accepted: it fails closed, and lines and anchors stay.
- Such a match through a fence or comment line changes how the lines after it read, so a put can be refused for a
  missing anchor on a line that was code. Accepted: it needs a key block or a pattern over lines crossing a fence, and
  the problem names the line.
- With anchors left out of the join, a label ending one line takes the first word of the next as its value. Accepted:
  it fails closed, as DR-0027's labels over line breaks do.
- Frontmatter isn't redacted, so a phone number in a note's file name stays in `old_paths`. Accepted: old paths are
  locators and ids, as a record's ids are.
- A frontmatter that doesn't parse is refused with #6's messages before the screen runs, and they can quote a
  frontmatter value back. Accepted: it is the writer's own text, never stored, and the service log keeps no results
  (DR-0155).
- A machine still on an older Docket keeps writing unredacted docs, and its `doc_put` refuses a doc holding a marker
  right before its anchors. Accepted: the CHANGELOG says to update every machine, then run the pass.
- A refused take-in blocks every put to that doc until the user edits the file or checks it out again. Accepted: the
  edit is the user's own, and the problem names the line and what to do.
- The pass holds the vault lock while it writes, and the service's puts wait 15 seconds, then fail with the lock's
  message. Accepted for a one-off.
- Earlier revs keep the secret, and `read` with a rev shows it. Accepted until forget (Open questions).
- The gate screens staged records that already hold markers, so the keyword `phone` drops a record whose number was
  redacted, and a user pattern named after a keyword drops every record it fires on; the doc screen leaves the
  built-in rules' markers out. Not changed here: a false drop is accepted by DR-0026.
