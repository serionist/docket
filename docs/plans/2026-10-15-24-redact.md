# Redact docs before commit; the anchor grammar reads markers as text

## Goal

Every doc Docket commits passes the gate's never-store keywords and redaction first, so a credential Claude copies into
a note, or one sitting in an old note, never reaches the vault's history. A redaction never moves a line or an anchor.

What runs today:

| Route | Never-store | Redaction |
|---|---|---|
| `doc_put` over MCP, REST and `docket doc put` (`DocStore.put`) | none | none |
| `docket import notes` (`put_many`) | keywords on the old path, the slug and the text | `Redactor.text` on the whole body: a key block's lines fold into one marker |
| a hand edit taken in before a put (`_take_in`) | none | none |
| docs already in a vault | none | none |

- In scope: one guard for derived text, called by `DocStore` on every text it commits; the anchor grammar reading a
  marker as text; what `doc_put` tells its writer; the import's redaction keeping lines and reporting counts;
  `docket doc redact` for docs already stored; the index after that pass.
- Out of scope: raw records under a rule added later (raw is written once, DR-0014); removing old revs from history
  and `read` with a rev (forget, a later phase); later writers of derived text (Whisper transcripts in phase 2, entity
  proposals in phase 1, ledger ops in phase 3), which call the same guard when they land; an MCP tool for the pass.

## Design

One new module holds the rules; `DocStore` calls it on every text it commits, so every route gets it, the import
included.

| Module | Change |
|---|---|
| `docket/vault/derived.py` (new) | `screen(doc, lists, rules)`: the never-store problems, lines and the list only; `redact(doc_type, body, redactor)`: the body with its lines and anchors kept, the markers added per rule, the lines they are on |
| `docket/vault/anchors.py` | `[redacted:<rule>]` is text, never an anchor-like token |
| `docket/vault/docstore.py` | `put`, `put_many` and the take-in screen and redact; `PutResult` gains two fields; `redact_all` for the pass |
| `docket/imports/notes.py` | the body through `derived.redact`; `ImportReport.redactions` |
| `render.py`, `cli.py` | the put's redaction line; `docket doc redact`; the import's redacted line |
| `service/tools.py` | `doc_put`'s description and the server instructions say what it redacts and refuses |

### What is screened and what is redacted

| Part of a doc | Never-store keywords | Redaction |
|---|---|---|
| a content line's text, before its anchors | yes | yes |
| a content line's trailing anchors | no: rids the raw log holds | no: ids, kept byte for byte |
| free and skip lines (headings, a table's header, fenced code, comments) | yes, whole | yes, whole |
| a legacy note's lines | yes, whole | yes, whole |
| the id's slug, `entities`, the slugs in `supersedes`, `old_paths` | yes | no: ids and locators (DR-0131) |
| `type`, `covers`, `rev`, `by`, `import_hash` | no | no |

- The rules are `vault.yaml`'s as the call opens the vault, as the gate's are (DR-0021, DR-0025).
- The frontmatter is never redacted, as a record's ids never are (DR-0027). `by` isn't screened either: it names the
  writer and its run (`docket import` is fixed), not what the doc says, and a keyword like `sync` would refuse every
  doc.
- The screen runs on the text as given, before redaction. A marker of a known rule (the built-in ones and the user's
  pattern names) is left out of it, so the keyword `phone` doesn't refuse every doc holding `[redacted:phone]`; a
  marker naming any other rule is screened as text.

### Never-store: the doc is refused

- A match refuses the whole doc before any other check runs. The problems name each line it is on (both lines when a
  keyword runs over a line break) or the frontmatter key, say "says something on the never-store keywords list; leave
  it out", and carry no excerpt. Nothing is written, committed or logged.
- Why refuse: the gate drops a whole record and the import skips a whole note on a match (DR-0026, DR-0135); the words
  around a keyword still tell what it was; and Claude can write the doc again without it, which a source can't.
- Not chosen: redacting the keyword (its context stays, and the marker says something private was there); dropping
  the lines (a summary changes silently and its line numbers move).

### Redaction keeps lines and anchors

A marker changes a line's length only. Anchors belong to a line (DR-0110), `verify` takes line numbers, and the index
keeps a doc's anchors by line, built from the stored text, so nothing moves.

1. Split each content line into its text and its trailing run of anchors, as `trailing_anchors` reads it; the run is
   kept byte for byte with the spaces before it. A line whose run holds a malformed anchor, and every other line, is
   all text.
2. Redact the text parts joined by line breaks, as a transcript's segments are (DR-0027, `Redactor.segment_texts`): a
   label at the end of one line and its value on the next still match, and a match that runs over a line break (a key
   block, a user pattern over lines) turns each line it touches into its marker whole.
3. Put each line back: its redacted text, then its anchors.

```markdown
- Cleo's direct line is +1 555 010 0188 @13:40
```

is stored as

```markdown
- Cleo's direct line is [redacted:phone] @13:40
```

- Redacting twice is once (DR-0027): the same doc put again is unchanged, so `doc_put` stays idempotent.
- Not chosen: `Redactor.text` over the whole body, as the import does today: a key block's lines fold into one marker,
  every later line number moves, and the anchors on the folded lines are lost. Each line alone: a label on one line
  and its value on the next would be stored.

### The anchor grammar reads a marker as text

- Today the example above is refused. DR-0110 keeps `[<letters>:...]` at a line's end for later anchor kinds, so the
  trailing parser reads `[redacted:phone]` as a bad anchor. Every line whose secret sat right before its anchors
  would be refused, and `verify` would flag the lines a take-in or the pass wrote.
- The change: DR-0027's marker `[redacted:<rule>]` is text wherever it stands, and no anchor kind is ever named
  `redacted`. This supersedes DR-0110, a one-way door (Doors and data).
- Stored docs: every doc valid before stays valid with the same anchors; only docs that were refused become possible.
  An older Docket reading a newer doc reports such a line as a bad anchor in `verify`, and still reads its anchors.
- Not chosen: a second marker shape in docs, such as `(redacted: phone)` (two forms, and redacting twice would no
  longer be once); refusing and asking the writer to move the secret (the writer can't see where a marker lands).

### What the writer is told

No route ever echoes a redacted value or a keyword.

| Route | Told |
|---|---|
| `doc_put`, stored | `PutResult` gains `redactions` (rule to markers added) and `redacted_lines` (the lines, numbered as `read` numbers the stored doc); the compact text adds `redacted on lines 12, 14: 1 password, 1 phone`; the same on an unchanged put whose text held them |
| `doc_put`, never-store | the problems above: an MCP tool error, a REST 422, `docket doc put` exit 1 |
| `doc_put`, other refusals | as today, their excerpts taken from the redacted lines, so an anchor problem never quotes a secret back |
| a hand edit taken in | redacted in its file and committed as today's `(edited by hand)` rev; one that says a keyword refuses the put with `processed/<path> was edited by hand, and its line 14 says something on the never-store keywords list; edit it or check it out again`, and stays on disk, uncommitted |
| `docket import notes` | `ImportReport.redactions`, printed as `redacted  2 password, 1 phone` |

- `PutResult` only gains fields, as DR-0150 allows. The MCP golden file holds names, parameters and annotations, so
  it doesn't change; `doc_put`'s description and the instructions say what it redacts and refuses.
- A take-in's own markers aren't in `PutResult`: they belong to the user's edit, the file shows them, and the put is
  refused at the old rev anyway, so its writer reads the doc again.

### Docs already in a vault: `docket doc redact`

Every write redacts from now on, and a one-off pass redacts what is already there. Run it once after upgrading, and
again after adding a rule or a keyword to `vault.yaml`.

```
$ docket doc redact
redacted  3 docs: 4 password, 1 phone
          minutes:2026-10-02-supplier-call rev 4, recording-note:2026-10-09-site-visit rev 2, digest:2026-w41 rev 6
left      1 doc says something on the never-store lists: processed/brief/dora-example.md
          edit or delete it, then run docket doc redact again
history   earlier revs still hold what was redacted, in this vault's git history
index     rebuilt
```

- Under the vault lock, one commit, `Redact docs: <n>`, with a `Doc: <id> rev <n>` line for each doc (DR-0112).
- Only the body is redacted, in the file's own text, and the rev line set as the take-in sets it, so a doc from a
  newer Docket keeps the keys and types this one doesn't know.
- A doc whose file differs from its last rev goes in first through the take-in, which now redacts, as its own
  `(edited by hand)` rev.
- Left as they are and named by path, with exit 1: a doc the never-store lists forbid (the pass never commits one, and
  removing it is the user's call) and a file that doesn't parse or sits where its id doesn't say.
- The history line follows the storage: a repo of its own keeps the old revs in its history; in a folder, the host
  repo's history keeps them, and Docket never rewrites that repo (the design's Retention section).
- `--dry-run` prints the same and writes nothing. No MCP tool: a terminal one-off, like the import.
- Not chosen: only on each doc's next rev (a doc nobody touches keeps its secret in the tree for good); at service
  start or index rebuild (a write nobody asked for).

### The index

- `doc_put` and the import never put unredacted text on disk, so the index never reads it.
- The pass rebuilds this machine's index when it wrote anything. A rebuild writes a new file (DR-0115), so the old text
  isn't left in free pages or in the full-text index's deleted entries, as it would be after an update.
- Another machine follows the changed docs with an update when it pulls: search stops finding the old text at once,
  and its bytes can stay in that index file until `docket index rebuild` there, which the pass's output says to run.
- A hand edit sits on disk before its take-in, and an update may index it: the index holds what this machine's
  working tree holds, and is never committed.
- Not chosen: `secure_delete` and an FTS optimize on every update: slower updates, and old FTS segments stay until a
  merge anyway.

build starts.

Each decision goes into `packages/docket/index.yaml` at build time, `proposed`, `by: Claude (autonomy grant)`,

| Decision (label) | Cost | Holds |
|---|---|---|
| Every doc Docket commits passes never-store and redaction first (derived) | medium | the routes: `doc_put` over MCP, REST and the CLI, `put_many` and the import, the take-in, the pass; `vault.yaml`'s rules at the call. Binds: a test sends an invented credential and phone number through each route and finds neither in the vault's files or `git log -p` |
| A doc that says something on the never-store keywords list is refused (refuse) | medium | what is screened, refused before any other check, lines and the list only, known markers left out |
| A doc's lines are redacted with their count and anchors kept (lines) | medium | the split, the joined redaction through `segment_texts`, a line a match runs into made its marker whole, the frontmatter never redacted |
| A redaction marker is text in the anchor grammar (grammar) | one-way | DR-0110's whole rule, plus `[redacted:<rule>]` read as text wherever it stands and no anchor kind named `redacted`; supersedes DR-0110 |
| `doc_put` says what it redacted (result) | one-way | `PutResult.redactions` and `redacted_lines`, kept for good under DR-0150 |
| `docket doc redact` redacts the docs already stored (pass) | medium | the lock, one commit, the take-in, unknown keys kept, forbidden and broken docs left and named, the dry run, the history line, the index rebuilt |

Users' data:

- A doc changes only when it is written: by a put, a take-in or the pass, each as its next rev. Earlier revs stay in
  history.
- Legacy notes: the import's redaction keeps lines now, so a note with a match over lines (a key block) gets a new
  body hash once. The next import writes it as its next rev, or reports it as kept when it was also edited in the vault
  (DR-0132). A note without one hashes the same, and nothing is written.
- Unchanged: the doc format (DR-0109), revs (DR-0112), old paths (DR-0130, DR-0131), `vault.yaml` (DR-0021), the MCP
  tools' names and parameters (DR-0150).
- `AGENTS.md`'s doors line cites the new grammar decision in place of DR-0110.

## Open questions

| Question | Recommended | Why |
|---|---|---|
| Change the anchor grammar so a marker reads as text? | yes, in #24 before the build | it only accepts more: no stored doc changes meaning; without it, a secret right before a line's anchors refuses the doc |
| A doc that says a never-store keyword: refuse or redact? | refuse | the gate and the import drop the whole thing; the words around a keyword still tell; Claude can write it again |
| `read` with a rev returns an earlier rev's unredacted text: redact it on the way out? | no, leave it to forget | DR-0112 binds `read(rev=n)` to the commit's own text, and the history holds it either way |
| A hand edit holding a secret: redact it in place, or refuse the put until the user removes it? | redact in place | the gate redacts rather than refuses; a refusal blocks every put to that doc |
| Raw records stored before a rule was added: redact them too? | no, a follow-up with forget | raw is written once (DR-0014); rewriting it is a history rewrite |
| Other machines' indexes after a pass: rebuild them automatically? | no, the output says to run `docket index rebuild` | search is right after an update; the bytes left are in a local cache beside a history that holds the same text |

   error; `[redacted:api-key]` alone at a line's end gives no anchor and no error; `[x:foo]` and `[redacted:Phone]`
   at the end are still errors; a table row with a marker in its last cell.

   number (`[r:calls:+15550100188@00:12]`) included; a label at a line's end with its value on the next; a key block
   over lines, each line its marker with its anchors kept; an unclosed key block to the end; a table row; fenced code;
   a legacy note's lines whole; a line with a malformed anchor redacted whole; twice is once; counts and lines. The
   screen: a keyword in a body line, the slug, `entities`, `supersedes` and `old_paths`, each refused with its line
   and no excerpt; one only inside an anchor's rid, or in `by`, not refused; `[redacted:phone]` with the keyword
   `phone` not refused, `[redacted:dora-example]` with `dora example` refused; a keyword over two lines naming both.

## Risks

- A match over lines turns every line it touches into its marker, the words before or after the secret on those lines
  included; an unclosed key block takes every line to the end. Accepted: it fails closed, and lines and anchors stay.
- Such a match through a fence or comment line changes how the lines after it read, so a put can be refused for a
  missing anchor on a line that was code. Accepted: it needs a key block or a pattern over lines crossing a fence, and
  the problem names the line.
- With anchors left out of the join, a label ending one line takes the first word of the next as its value. Accepted:
  it fails closed, as DR-0027's labels over line breaks do.
- Frontmatter isn't redacted, so a phone number in a note's file name stays in `old_paths`. Accepted: old paths are
  locators and ids, as a record's ids are.
- A frontmatter that doesn't parse is refused with #6's messages before the screen runs, and they can quote a
  frontmatter value back. Accepted: it is the writer's own text, never stored, and the service log keeps no results
  (DR-0155).
- A machine still on an older Docket keeps writing unredacted docs. Accepted: the CHANGELOG says to update every
  machine, then run the pass.
- The pass holds the vault lock while it writes, and the service's puts wait 15 seconds, then fail with the lock's
  message. Accepted for a one-off.
- Earlier revs keep the secret, and `read` with a rev shows it. Accepted until forget (Open questions).
- The gate screens staged records that already hold markers, so the keyword `phone` drops a record whose number was
  redacted; the doc screen leaves known markers out. Not changed here: a false drop is accepted by DR-0026.
